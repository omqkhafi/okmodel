# OKModel — Decisions log (companion to okmodel-api-design.md, draft 19)

Every decision states what was chosen and why. The spec states the rules; this file keeps the history.


| # | Topic | Decision |
|---|---|---|
| D1 | Internal goal | Understandability is measured in CI with type budgets; safety and correctness are measured by the isolation check and the migration linter (section 1). A feature that makes the model harder to understand as it grows is removed or redesigned |
| D2 | Positioning | Independent library (like sently). OKE will later replace Drizzle in `store.sql` with OKModel and adapt to it; OKModel's design is not constrained by OKE |
| D3 | Versioning | All work in 0.x through milestones M0–M5; 1.0 is a gate with conditions |
| D4 | Databases | Postgres, then SQLite, then MySQL/MariaDB, all within 0.x; others as community dialect packages |
| D5 | Dialect separation | Import paths `okmodel/pg`, `okmodel/sqlite`, `okmodel/mysql`; common subset `okmodel/sql` |
| D6 | Drivers | Not built in; zero-dependency adapters at `okmodel/<dialect>/<driver>` |
| D7 | Responsibilities | `defineConfig` = tooling; `schema()` = the model; `connect()` = runtime |
| D8 | Tables | One file per table; `table(name, fields, options)`; references by name; types via `Register`, with explicit-schema types for multi-schema projects |
| D9 | Column types | `t.*` = database types only, per dialect; codecs in the schema; `bigint` codec defaults to `"string"` |
| D10 | Picklists | `.picklist([...])` compiles to a `CHECK` constraint, not a database enum |
| D11 | Validation | Inline `.validate([...])` or options section; one place per field; base rules derived from the type; transforms in the rule array |
| D12 | Validation at write time | `validation: false` by default; overridable per table and per call; validated values are not re-validated |
| D13 | Standalone validation | `tasks.insert.validate(x)` throws; `tasks.insert.check(x)` returns a result; `tasks.insert` is a Standard Schema |
| D14 | Input and output protection | Unknown keys stripped; `.guarded()` fields never filled from input (keys and trait fields automatically); `.hidden()` fields excluded unless selected by name |
| D15 | Operators | Tagged helpers (`lt(x)`, `startsWith(x)`, `has({...})`), never plain objects; runtime identifier validation; allowlisted `filters()` for user-driven filtering |
| D16 | Traits | Replace spreads; defaults in the schema; explicit opt-out |
| D16a | Presets | Named, typed query refinements on a table are called `presets` (formerly scopes); `tasks.filters()` is the allowlisted builder for client-supplied filters |
| D17 | Record lifecycle | Three operations with fixed meanings: `delete` = permanent removal of the matched records (active or archived), `archive` = reversible removal from the active dataset, `restore` = return to the active dataset. The `archivable()` trait provides the capability; how archived rows are stored is a strategy, not a different meaning |
| D18 | Tenancy vs ownership | Ownership is a field plus a preset; tenancy is an isolation concept with strategies |
| D19 | Tenancy inheritance | Defined in the schema; every table isolated by default; `via` or `global(reason)` exceptions; tenant-scoped uniques and composite FKs |
| D20 | Errors | One `OkmError`; six categories with default HTTP statuses; `from`, `summary`, `fields`, `toHttp`, `log`, `match` |
| D21 | Generics | Types keyed by table name; `TablesWith`, `TablesWithColumn`; `Tx` is a `Client` |
| D22 | Extension | Two user mechanisms: traits (table level) and read-only hookm in `connect()`. Custom types via `t.custom()`, custom operators as tagged helpers. Internally one contribution protocol, kept private until 1.0. No `plugin` concept |
| D23 | Transactions | Capability `interactive` or `batch`; `db.batch()` everywhere |
| D24 | Migrations | Declared renames; expand/contract classification; compatibility-based drift check; linter seeded from Squawk, strong_migrations and Atlas; safe rewrites generated |
| D25 | Type strategy | Decided by the M0 spike (inferred vs emitted row types), measured as described in D114. **Decided: emitted by default (D120)**; inferred stays as the zero-build mode |
| D26 | Programmatic schema API | Exposed in M2 (the catalog builder already exists for `okm pull`) |
| D27 | General rule | Defaults flow down from schema to table to call; exceptions are declared where they happen |
| D28 | Client entry | `connect()` |
| D29 | Removed | Branded IDs (added type weight for rare benefit) |
| D30 | Architecture | The catalog is the center; queries flow logical intent → rules with provenance → final safety verification → physical plan → dialect SQL |
| D31 | Operation guarantee | One logical operation per call; for reads and relation loading the statement count depends on query shape, never on result size; writes may be chunked by input size inside one transaction. A logical operation is not a method name: one method may carry several modes |
| D38 | API taxonomy | Core operations `find`/`insert`/`update`/`delete`; lifecycle operations `archive`/`restore` on archivable tables; variants are modes of those operations; `sync` is a relationship operation; `tx`/`batch` are execution primitives; guarantees are listed separately. A separate method exists only when the result shape or the logical intent differs |
| D40 | Archive strategy | `archivable()` defaults to the `column` strategy (M1). The `table` strategy is deferred until archived snapshots can follow schema migrations |
| D39 | Engine requirement | `schema({ requires: { postgres: ">=17" } })`; no user-facing schema version or edition |
| D32 | Inspection | `inspect()`, `sql()`, `explain()`; every implicit behavior carries its source; the internal IR stays private in 0.x |
| D33 | Fingerprints | Deterministic, parameter-free fingerprints for every query |
| D34 | Object identity | Deterministic, stable constraint and index names stored in the catalog; ownership states `managed` / `external` / `ignored` (M2) |
| D35 | Semantics | Behavior of small, dangerous APIs specified up front and tested on every driver |
| D36 | Conformance | Driver conformance suite; migrations verified against an empty database and the previous release's catalog |
| D37 | Non-goals | Identity map, lazy loading, nested writes by default, authorization framework, lowest-common-denominator API, cache in the kernel |
| D41 | Presets naming | Presets stay bare methods (`tasks.pending()`); collisions fail with OKM1040, a reserved-name list protects future methods, and `okm upgrade` renames on collision |
| D42 | Documents | The spec is normative; decisions live in `okmodel-decisions.md`; research in `okmodel-gap-research.md` |
| D43 | Extensions | One `extension()` contract with three sources: built-in (Postgres versions, and outside Postgres such as pgvector and PostGIS), and developer-provided (project file or npm). Listed in `schema({ extensions })` |
| D44 | Extension TS | Types are immediately available from the definition; `okm generate` produces SQL only, never TS |
| D45 | Extension built-ins | Definitions are produced by our CI from real Postgres containers per major version plus a naming overlay, and shipped as source; users never run the generator |
| D46 | Extension lifecycle | add/upgrade/move/remove through migrations with expand/contract classes; no `CASCADE`; no downgrade; owned objects are `external`; `CREATE EXTENSION` runs only from the migration role |
| D47 | Extension settings | Runtime settings are per operation (`SET LOCAL` in a short transaction), not per connection |
| D48 | Extension safety | Extensions add types, operators, functions and index methods only; they cannot alter queries; duplicates and undeclared use fail at build |
| D49 | Database objects | The catalog family includes views, materialized views, functions, triggers, policies and grants, on one contract (kind, identity, owner, canonical definition, column-level dependencies, provenance). Raw SQL is an escape hatch, not a second object system; the contract is frozen only after the M0 catalog-object spike |
| D50 | Views | Materialized views are a separate kind (no replace; refresh and indexes). Views are defined with the query builder or SQL with declared columns; read-only in the client |
| D51 | Functions | `fn()` with signature identity, volatility and typed calls; the same kind as extension functions; plpgsql needs `dependsOn`; `SECURITY DEFINER` needs `search_path` |
| D52 | Triggers | Top-level `triggers` list (one place); traits contribute triggers and functions with provenance |
| D53 | Object planning | Incompatible replace and column changes under a dependent view are planned as drop dependents, alter, recreate; never `CASCADE` |
| D54 | View tenancy | Views over tenant tables inherit tenancy; the tenant key or `global` is required; `security_invoker` by default under `rls` |
| D55 | Roles and grants | `roles: { migration, app }`; the catalog emits grants and default privileges for the app role |
| D56 | Cancellation | Every operation accepts `{ signal, timeout }`; kind `cancelled`, never retried |
| D57 | Row locks | `find` accepts `lock` and `wait` inside a transaction; advisory locks on `tx` |
| D58 | Sensitive fields | `.sensitive()` redacts values from logs, errors, inspection and fixtures |
| D59 | Backfill | `backfill()` is a planned migration step: batched, resumable, tenant-aware |
| D60 | Materialized views | Materialized views are in M1 with views: they share the dependency, ordering and recreate machinery; they stay a separate kind; populate is a planned data step |
| D61 | Ownership | Ownership (`managed` / `external` / `ignored`) is part of the catalog contract for every object kind from M1; M1 implements `managed` and `external`, M2 adds `ignored` and explicit `owner:` |
| D62 | M0 rule | M0 validates and measures; findings are classified (bug, contradiction, DX, performance, missing capability); no new API surface for imagined edge cases |
| D63 | Driver capabilities | Same semantics, not same features. Dialect (SQL capabilities) and driver (execution capabilities) are separate axes; every driver flag gates the API in types and fails clearly at runtime; every declared capability has a passing conformance test (CI); the compatibility table is generated from test results |
| D64 | Separation | Catalog (`schema()`), connection and routing (`connect()`), migration target (`defineConfig()`) are separate; no connection details in `schema()`; `connect()` first argument is a string or a topology (revised by D90: the registry is `tenancy.registry`) |
| D65 | Namespaces | Every object has an explicit namespace, emitted SQL is always qualified, the default namespace is a recorded setting; namespace is static or a template stored logically in snapshots; no `microservice` concept |
| D66 | Cross-catalog | Other catalogs' objects are `external`, verified against an exported catalog, foreign keys only within one database |
| D67 | Routing | Superseded by D91. Original: default primary, explicit `.replica()`, WAL-position read-your-writes, capability gate, primary-required operations structural in the taxonomy (the last three carry over) |
| D68 | Migration targets | The engine works on a list of primary targets from M1; shared and tenant classes; history and checkpoints per target; new tenants provisioned from the snapshot; migrations never touch replicas |
| D69 | Runner | One `TargetRunner` for `migrate apply` and `backfill()`; run state in the control database |
| D70 | Registry | One tenant registry shared by runtime and tooling; tenant ids are sanitized before entering identifiers. Its shape and place in `connect()` are revised by D90 and D98 |
| D71 | Release trains | M1 ships as trains 0.1–0.4, each tested and published; execution follows `okmodel-execution-plan.md` |
| D72 | Prepared statements | Driver flag `prepared` (`named`, `unnamed`, `none`); fingerprints name statements only where allowed |
| D73 | Catalog hash | The hash is stored in `okm_meta` for an O(1) startup check; a serialised catalog is emitted for cold start |
| D74 | Portable core | No `node:*` in the core, explicit context, `erasableSyntaxOnly`-compatible API, no runtime dependencies, provenance with source locations |
| D75 | Dev experience | `okm dev` uses PGlite when no database is configured; dev N+1 warning from fingerprints; nearest-name hints; `fix` on errors; per-code docs generated from the registry |
| D76 | Agents | `okm catalog export --json` ships; an MCP server for coding agents is deferred (D85) |
| D77 | Plan output | The plan shows locks with row estimates; classification is advisory |
| D78 | Escape ladder | Each escape step keeps the maximum safety it can (rule 15) |
| D79 | Repository checks | `docs:check`, `publint`, `arethetypeswrong`, API report, core purity and size budget run in CI |
| D80 | Observability and PR tooling | `okmodel/otel` and a GitHub Action in M2 |
| D81 | Layers | Five layers with downward-only dependencies (contracts, dialects, adapters, runtime, tooling); enforced by an import-graph check in CI |
| D82 | Driver contract | Public `Driver` contract: `execute` returning `{ rows, count, notices }`, `DriverError`, capability flags; codecs stay in the dialect; conformance covers value representation |
| D83 | Error mapping | Adapters normalise to `DriverError`; the dialect maps it to `OkmError` kinds; drivers never construct `OkmError` |
| D84 | Normalisation | Comparison pipeline introspect, normalise, compare; database-rewritten expressions are compared through a scratch-database round trip, not as text |
| D85 | MCP | Deferred: a separate package outside the core if ever built |
| D86 | Protected targets | `protected` belongs to the Target; blocked operations need `--allow-protected` (OKM1850); not tied to `NODE_ENV`. The exact operation policy is D100 |
| D87 | Execution lifecycle | `timeouts` keys (`acquire`, `statement`, `transaction`, `idleInTransaction`); cancelling inside `tx` rolls back; `onNotice` hook |
| D88 | Testing principles | Behavioural tests on real databases, no database mocks, file checks only for artifacts; capability registry is data (a manifest per dialect and version) |
| D89 | Vocabulary | Target = logical deployment destination (migrations, registry); Topology = one primary plus replicas of a Target; Endpoint = one physical address with a role, owning one pool; Pool; Connection. Chains: Tenant → registry → Target → Topology → Endpoint; Operation → Router → Endpoint → Pool → Connection. Reason: "target" meant both the migration destination and the primary or replica, which would blur the design and the docs. Endpoint is internal, never public API |
| D90 | connect() shapes | `connect()` takes a string or a topology; the tenant registry is not a connection and is passed as `tenancy: { registry }`. Reason: registry, connection and routing are different concerns; a registry as first argument reads as if it were a connection. Revises D64 and D70 |
| D91 | Automatic read routing | Configured replicas automatically take eligible reads; `.primary()` requires the primary; `.replica()` requires a replica and fails with OKM1843 rather than reading the primary (also with no replicas configured); normal reads fall back to the primary or fail (`fallback: "error"`, OKM1844); an operation is routed once; internal read-only transactions follow the operation's routing; only user `tx()` and writes require the primary. Reason: making the developer write `.replica()` on every read defeats configuring replicas; consistency, not a default, is what protects correctness. Supersedes D67 |
| D92 | Replica selection | Candidate filtering (health, consistency and lag, capacity) then a selection strategy (`weighted` default, `roundRobin`, `leastConnections`, `latencyAware`, or a function). Lag is a constraint, not a strategy; weight, in-flight count and latency are strategy inputs |
| D93 | Pools | One pool per endpoint; endpoint selection and connection selection are separate; queries never see URLs, pools or connections; acquire waits up to `timeouts.acquire` then OKM1846 and never spills into another endpoint's pool |
| D94 | Transaction affinity | `tx()` reserves one connection on the primary; statements, savepoints and batches inside stay on it; not subject to replica selection |
| D95 | Commit position | Session watermark = WAL position read after commit on the committing connection (`pg_current_wal_insert_lsn()`, an upper bound, safe); replicas are eligible when their replay position reaches it; replay positions are monotonic, so a cached value is a lower bound; position read failure marks the session position-unknown; root client has a conservative client-wide watermark; `consistency: "session"` default, `"eventual"` and `.replica({ consistency })` opt out; position reading is a dialect/engine capability. M0 verifies the mechanism and its cost. Reason: PostgreSQL returns no commit LSN to clients, so the honest mechanism is stated and measured, not assumed **Confirmed by M0, wording amended (D121).** |
| D96 | Atomic batch | Atomic `batch` is part of the Driver contract, not a capability: all-or-nothing, ordered results, failing index, whole-batch timeout and cancellation, savepoint inside `tx()`, primary-required; an adapter that cannot provide it is not a driver; conformance `batch.atomic` runs on every adapter. Reason: the same API must not have weaker atomicity on one driver |
| D97 | Outcome unknown | A commit or batch whose result never arrived raises `outcome_unknown` (OKM1401, category `internal`, never retried), never a claim of rollback. Reason: automatic retry could apply a write twice |
| D98 | Target resolution | Plans and run state hold Target names, never connection details; each Target is resolved at execution time by its resolver; pools are keyed by resolved configuration and capped with LRU eviction; an authentication failure re-resolves once (credential rotation); the registry resolves per role (`app`, `migration`) and may `create(id)` databases |
| D99 | Provisioning | A new Target is provisioned from the head snapshot on an empty target (`migrate apply`, `provision()`), without replaying history; `okm migrate check` proves snapshot ≡ replayed history (OKM1521); required rows are declared with the table option `reference` (insert-if-missing, `expand`); other data DML in migrations is flagged (OKM1542); non-empty targets are refused (OKM1851). Reason: history replay would drop reference data and re-run backfills against empty tenants |
| D100 | Protection policy | One `assertTargetPolicy` for the CLI, engine, backfill, seed, runner and provision. Allowed: read-only commands, `expand`, `reference`, `provision` on an empty target. Blocked: `contract`, unclassified steps, `push`, `backfill`, `seed`, history repair, unless `--allow-protected` (per invocation, no environment variable, selected targets only). Protection never affects runtime `connect()` |
| D101 | Placement | The Target / Topology / Endpoint / Pool / Router runtime, one pool per endpoint, transaction affinity, the atomic batch contract, the resolver, the protection policy and snapshot provisioning are M1 foundations from the first train; replica behaviour (routing, selection, position, `connect({ primary, replicas })`) is train 0.5 inside M1 (no longer M2); the registry, multi-target runner and tenant provisioning API stay M5 |
| D102 | Driver contract shape | `open(config)` returns a `DriverPool` per endpoint (`execute`, `batch`, `reserve`, `stats`, `close`); a reserved `DriverConnection` carries every transaction; pool statistics feed selection strategies |
| D103 | Migration failure | A migration is atomic in one transaction where PostgreSQL allows it; steps that cannot be transactional are split out by the planner and marked; every step checkpoints in the target's history; a failed run stops at the failing step and a later `apply` resumes without repeating finished steps (a failed concurrent index is dropped and rebuilt); `apply` holds a session-level advisory lock per target, a second concurrent apply fails with OKM1522. Reason: partial failure is the normal case on large databases and must be resumable and non-racing |
| D104 | Forward-only | No down migrations. Recovery is a new forward migration or an application rollback, which `expand` keeps safe; `contract` runs only after the new release is confirmed. Reason: down scripts are rarely correct on real data |
| D105 | Rollout control | With many targets: `--target`, `--class`, `--canary <n>`, `--concurrency <n>` (defaults 2 for schema-per-tenant, 8 for database-per-tenant), `--max-failures <n>` (default 3, halts a migration that breaks every tenant); `okm migrate status` shows every target's version and state (single-target status ships in M1). Reason: staged rollout and early halt are how a fleet-wide migration is made safe |
| D106 | Contract gating | A `contract` step applies to a tenant only if it has every earlier migration, and to the shared target only after it succeeded on every tenant in scope. Reason: no tenant may reference something already removed **Amended by D123 (gating over the whole registry).** |
| D107 | Second pass | After a multi-target run the runner reads the registry again and processes tenants created during the run |
| D108 | Environments and previews | An environment is a named Target: `targets` in `defineConfig` (M1; `database` is the shorthand for `default`), the tenant registry is `tenants`; with several targets `--target` is required (OKM1853); an unprotected target aliasing a protected database is refused (OKM1852). Previews are ephemeral databases created by infrastructure and filled by `migrate apply` from the snapshot (plus optional seed); rehearsal is applying pending migrations to a clone of production; OKModel never drops a database. Reason: nothing about an environment is inferred from `NODE_ENV` or a URL, and a preview must not be able to act on production by omission **Amended by D122 (protection per physical database).** |
| D109 | Repository conventions | The package `okmodel` is the repository root; other packages under `packages/*` (private ones for spikes, reference app and benchmarks); `files` whitelist controls the tarball; repository owner `omqkhafi`, copyright Omq Khafi, Apache-2.0; every commit carries exactly the DCO sign-off (`Omq Khafi <omqkhafi@gmail.com>`) and the Ali Alnaghmoush co-author trailer, nothing else. Reason: heavy spike and benchmark dependencies must stay out of the published package, and attribution must be deliberate |
| D110 | Name and npm package | The project is named **OKModel** (short **OKM**), published as the unscoped npm package `okmodel`, repository `omqkhafi/okmodel`; CLI bins `okm` and `okmodel` (two thin wrapper files, `dist/okm.js` and `dist/okmodel.js`, written by `scripts/write-bin-wrappers.ts`, because `bun pm pack` lists a file twice when both bins point at one file); error class `OkmError`, codes `OKM1xxx`, config `okm.config.ts`, generated folder `.okm/`, metadata table `okm_meta`. Reason: the name is registrable on npm, short and neutral about the feature set |
| D111 | Toolchain: TypeScript 7 | The repository is fully TypeScript 7 (native compiler, `tsc`; nightly builds are `@typescript/native-preview`/`tsgo`): typecheck, declaration emit, editor. TypeScript 7.0 (released 2026-08-03) has no stable programmatic API until 7.1, so no OKModel tool uses the compiler API; type tests and type measurement follow D114, and the M0 spikes record TypeScript 7 results for editor-facing checks (autocomplete, `Register`, circularity). Lint and format use a tool that does not need the compiler API (Biome or oxlint, chosen in P01). TypeScript 7 defaults apply (`strict`, stable type ordering, no `baseUrl`, no legacy module resolution). Reason: one compiler for the user-facing experience, and no hidden dependency on an API that is still unstable |
| D112 | Module format | The package is ESM only, with TypeScript declarations from `tsc`. There is no CommonJS build and no dual-package hazard; CommonJS consumers use dynamic `import()` or `require()` of ES modules where their Node version supports it. The attw profile is `esm-only` (`node10` and `node16`-from-CJS resolutions are expected to be ignored). Reason: the core is runtime-agnostic and the catalog identity must not exist twice in one process |
| D113 | Versioning and changelog | Every merged prompt adds notes under `## Unreleased` in `changelog.md` and bumps the version with `bun run bump next`, which moves `package.json` to `<next release>-next.N` (for example `0.1.0-next.3`); the gate prompt of a release train ends with `bun run bump release`, which drops the suffix and promotes `Unreleased` to a dated heading. The first releases are 0.1.0 at P17, 0.2.0 at P30, 0.3.0 at P44, 0.4.0 at P55 and 0.5.0 at P66. Only released versions are published and tagged. CI fails a pull request whose version equals the one on `main` or whose `changelog.md` has no new entry. The `okm-ship` skill writes the notes and ends with `bun run bump next`; `bun run bump` gains the `next` and `release` kinds next to `patch`, `minor`, `major` and `--set`. Changelog area headings use the plain layer names (`contracts`, `dialects`, `adapters`, `runtime`, `tooling`, `docs`). Reason: the version and the notes must follow the work without anyone remembering to update them, and pre-release versions do not pretend to be patches of a release that has not happened |
| D114 | Type tests and type measurement | Type correctness is tested with `expect-type` style assertions (`expectTypeOf`) in `*.test-d.ts` files that the normal `tsc` typecheck compiles, so a wrong type fails the existing check on TypeScript 7 without a second runner. Type cost (instantiations, check time) is measured from the compiler's own diagnostics (`tsc --extendedDiagnostics`, and a trace when needed) by a script that runs each benchmark query on the 10, 50 and 200-table fixtures and compares with recorded ceilings. `@ark/attest` needs the TypeScript compiler API, which TypeScript 7.0 does not offer; it is used only if it runs on the TypeScript 6 compatibility package in a separate job, and is dropped otherwise. Vitest is not adopted for this: its type mode calls `tsc` and parses the output and does not measure type cost. P02 records which diagnostics TypeScript 7 actually reports, and the ceilings are set from M0 evidence. Reason: type experience is the product, so it is measured and tested with tools that work on the compiler we build with |
| D115 | Hygiene rounds | After P09 a cleanup prompt (P09A) removes spike leftovers, dedupes helpers, stabilises flaky tests and syncs docs. Every later gate (P17, P30, P44, P55, P66) ends with a lighter hygiene step before the release bump. Reason: spike code and workarounds accumulate across prompt chains and are cheapest to remove right after the evidence is recorded |
| D116 | M0 gate outcome | M0 evidence (`docs/m0-findings.md`, 68 findings) passes the gate. The catalog contract is frozen: one envelope (`kind, identity, owner, definition, dependencies, provenance`), per-kind identity as spec §5.7, declared `dependsOn` for plpgsql bodies (OKM1824), `BEGIN ATOMIC` bodies inferred, copied partition objects dropped on introspection. Findings that need a decision are D117–D127; the rest are implementation tasks already placed in the plan |
| D117 | Hash form | The drift hash is over the normalised structure, never over authoring text. View, materialized view and function bodies are judged by a scratch reprint (the server prints both sides). Reason: M0-01 and M0-34 showed text hashes drift on harmless reformatting |
| D118 | Extensions | Extension version is unpinned by default (installed version recorded for information, ignored by drift unless pinned). The raise-version path is checked against `pg_extension_update_paths` at plan time when a server is attached; offline plans mark the step `path-unverified` and apply preflight checks before any step. A non-relocatable extension `SET SCHEMA` is refused at planning (OKM1814). Members found through `pg_depend` deptype `e` are excluded from introspection (never loaded, never diffed); objects declared in `provides` stay `external`. Reason: M0-40, M0-41, M0-47 |
| D119 | Roles and grants | Roles are cluster objects: a role named in `roles` must exist and is `external` by default (checked by `okm doctor`). A declared managed role is created if missing, altered in place, and never dropped by a plan. Default privileges are keyed `(forRole, namespace, objectKind, grantee, privilege)` and emitted `ALTER DEFAULT PRIVILEGES FOR ROLE <migration role>`. Migrations run as the migration role (login, or one `SET ROLE` at session start recorded in the run report, never inside a plan); `CREATEROLE` is checked in doctor and apply preflight. Grant identity is a structured key exempt from the 63-byte rule. Reason: M0-42, M0-45, M0-48 |
| D120 | Row types emitted by default | `okm build`/`okm dev` emit row types into `.okm/types.d.ts` (config `types: "emitted" or "inferred"`, default emitted); inferred is the zero-build mode; both give the same shapes (CI `expectTypeOf` test). Emitted names derive from table names (`Tasks`, `TasksInsert`, `TasksUpdate`); duplicate table names are rejected (OKM1023), unknown references reported at build (OKM1021). Reason: M0-08, M0-09, M0-12: emitted costs 0 consumer instantiations against 53,410 inferred at 200 tables (43,676 unbranded; ~250 per table). Supersedes the D25 wording; hover quality is unmeasured (D111), so P12 adds a manual editor check |
| D121 | Commit position confirmed | The after-commit position read is confirmed by M0 (`pg_current_wal_insert_lsn()` after commit is 40 bytes past the start of a 34-byte commit record; reading inside the transaction gives the record start, which a replica can reach before applying the commit; `pg_current_wal_lsn()` lags under `synchronous_commit=off`; 0 read-your-writes violations). Cost is one extra statement per write; pipelining (`COMMIT; SELECT ...` as one simple-query message) is optional and evaluated in P13/P63. Fallback rate under write load is measured in P64. Reason: M0-51, M0-55 |
| D122 | Protection per physical database | Protection belongs to the physical database. Under `schemaPerTenant` all tenants share one database so protection must be uniform (mixed gives OKM1852); per-tenant protection requires `databasePerTenant`. Targets that resolve to the same host/port/database must have the same protection; two unprotected targets may share a database. Amends D108. Reason: M0-58, M0-59, M0-63 |
| D123 | Contract gating over the whole registry | A shared `contract` step runs only when every registered tenant has the migration. Any partial scope (`--canary`, `--class`, `--target` subset) skips contract steps and reports "contract pending (N tenants not at this migration)". Amends D106.
