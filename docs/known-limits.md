# Known limits

What this version does not do, or does differently from what you might expect. Each item says what happens, so none of them is a surprise at runtime. A limit that has a version is listed in the release train. `later` means the plan has not assigned a 0.x release.

`okmodel/internal` has no stability promise. Names on that subpath can change or disappear in any release. Its exports are marked `@internal`.

## okm pull

`okm pull` reads a database and writes table files plus a schema file (D275, D278). The selected namespaces are only read, so a protected target is allowed. A scratch schema is created and dropped to verify routines. It never overwrites a file (OKM1855). `--out <directory>` writes somewhere else. There is no prompt.

Written: tables, columns (type, default, nullability, identity, stored generated), primary and composite keys, unique constraints, checks, foreign keys with one local column, indexes that have a column (a partial predicate and an expression stay), the sequence an identity column owns, enums, domains, extensions, functions, triggers, views, and materialized views. A view is the SQL-string form (`pg_get_viewdef` text and its columns), not `q.from`. A view and a `BEGIN ATOMIC` body take edges from `pg_depend`. A plpgsql or SQL-string body gets `dependsOn` candidates by a lexical match of pulled table names. `dependsOn` cannot name a view or a function. A pulled plpgsql function lists `dependsOn`, so OKM1824 passes.

The scratch replay creates those objects from empty, in dependency order, with `check_function_bodies` on. A view query is matched with the same lexer, so a view over a view is created after the view it names when `pg_depend` recorded no column edge. A SQL function or a view whose dependency is missing fails creation. The report and a comment say `verified` when that creation succeeded, `candidate-only` when the function is plpgsql (creation does not prove the body), and `unverified` when creation failed. The comment does not claim more than that run proved.

Printed under `not pulled yet`, with a count, and not written: policies, roles, grants, default privileges, aggregates, procedures, event triggers, and rules. The catalog has no kind for the last four. The same list holds a partition, a composite foreign key, a standalone sequence, an expression index with no column, a column type `table()` has no builder for, a deferrable or nulls-not-distinct constraint, a non-default collation, an identity that is not generated always as the only primary key, a security-definer function with no `search_path`, a `security_invoker` view, and an expression or partial index on a materialized view. Comments are not pulled: the catalog does not store them. A domain with no check is not in the catalog, so it is not pulled. The logical namespace is `public`, because `schema()` has one namespace. Nothing in that list is dropped without a line.

## GitHub Action

The composite action `.github/actions/migrate` posts one sticky pull-request comment from `okm migrate plan --json` and can run the preview recipe (D279, §19.8). It does not create a database and it does not drop one. The caller passes the URL. A fork pull request receives no secrets, so `preview: true` is for a pull request in the same repository. See [GitHub Action](github-action.md).

## okm import drizzle

`okm import drizzle <path>` converts a Drizzle schema into table files (D280). It imports that file, so the command runs the project's code. It uses the project's own `drizzle-orm` (`getTableConfig`). okmodel does not depend on it. A project that cannot resolve `drizzle-orm` fails with OKM1856. The fix is to install it in that project. The command needs no database. It never overwrites a file (OKM1855). `--out <directory>` writes somewhere else.

The files are the same ones `okm pull` writes. SQL names stay. TypeScript fields follow the Drizzle property names. The report starts with `namespace <name>`. When that name is not `public`, set `defineConfig({ namespace })`. `schema()` still compiles `public`.

Not imported, each with the table and the reason: a composite foreign key, `relations()` (they are not turned into `references()`), a custom column type, a view, a policy, a sequence `table()` cannot map, and the sequence behind `serial`, `smallserial`, or `bigserial`. Those columns are written as `integer`, `smallint`, or `bigint` and not null, without the sequence. A second Postgres schema is listed too: one import writes one namespace.

## Programmatic schema API

`describe(schema)` and `buildCatalog(description)` are on `okmodel/migrate` (D284, D300). The description is JSON: `logical` (`namespace`, `name`, `format`), the catalog document, `minPostgres`, and `extensions` (each with a reason). `logical` stays `public` when `defineConfig({ namespace })` places the catalog. The catalog hash changes with that placement. Codecs, client generators, and relation helpers are not in the description. `okm catalog export` (including `--json`) is still the column snapshot a dependent verifies: table names plus each column's name, type, and nullability. It is not the full catalog. The full catalog is `describe(schema)`. There is no sync API.

The CLI loads `okmodel.config.ts` (not `okm.config.ts`). Pass `--config <path>` (or `options.config` on `plan` / `apply` / `status`) to load another file; a missing file names `okmodel.config.ts` and `--config`.

`provision(target)` installs one configured target. Creating a schema per tenant, creating a database per tenant, and the tenant registry are M5. See [provisioning](provisioning.md).

Also not in this version:

- **On Bun.sql and PGlite a positive `timeout` is OKM1120.** Neither driver can cancel a statement that is already running, including one waiting on a lock (D224, D239, D241). The error kind is `invalid` and the message is `timeout`. That includes a per-call timeout, `tx({ timeout })`, and `batch({ timeout })`. `.stream()` is not that check: a positive `timeout` on the find is the budget for the whole stream. Passing `timeout` used to wait until the statement ended. It now fails before the statement starts. `timeout: 0` is still kind `timeout`. A `signal` on its own is not refused and does not settle a statement that is already running. postgres.js and node-postgres cancel. The real cancel is not in this version: it costs bytes on the connect graphs.
- **Row-level security does not stop the application role, and the reporting role is not tenant-safe against its own SQL.** `rlsTenancy()` keeps the column predicate and adds policies (section 9.4). Code that can run arbitrary SQL as the application role can set `app.tenant` itself. The reporting role can set `app.unscoped` itself and read every tenant through the select policy. It still cannot write. `via()` and `compositeTenancy()` do not combine with `rlsTenancy()`. `table({ policies })` is still later. `isolation()` checks the policy expressions, not only that the policies are present (D238).
- **Schema-per-tenant and database-per-tenant are M5.** `isolation()` checks column tenancy, composite tenancy (one key at a time, and every key when seeding views), and a path table whose parent is in the other tenant. It also reads tenant views and materialized views. A global table or view is skipped and listed. A factory row is the inserted record, not a generated row type. Factories under `compositeTenancy()` treat every tenancy key as part of the scope and generate a distinct uuid per key when omitted; an explicit composite key is honoured, and a partial key is refused (B-32). `x.ref` still needs one non-tenant primary-key column. Concurrent `create` calls do not share an in-flight marker, so they are not reported as a factory cycle. A materialized view is created `WITH NO DATA`. `testing()` plain-populates each one after migrate so `refresh: "concurrently"` is not refused as "not populated"; `isolation()` refreshes before it reads and falls back to a plain refresh when the view was never populated (`migrate: false`) (B-34, D295). Outside that helper, a concurrent `refresh()` on an unpopulated view is still kind `driver` with reason `not_populated`.
- **A path ends on a unique declared key.** The table a path points at gains `UNIQUE` on its declared primary key only. That unique does not include a tenant column. Two tenants cannot share that id. Column or composite tenancy is the choice when they must. A path table's own primary key is not widened. `onConflict` on a path table is OKM1120. An insert or an update that sets the path column checks the new parent in that same statement and throws OKM1705 when the parent is outside the tenant. `batch()` refuses that update.
- **`archivable()` and a path target do not combine.** The table a path ends on is refused when the schema is built (OKM1705). The fix names that table. A path child can still be archivable: archive and restore leave its foreign key unchanged.
- **Two registered codes are not thrown in this version** (D183). OKM1110 (a feature needs a newer engine than `minPostgres`): the engine-dependent feature is an explicit `uuidv7()` database default. It fails as OKM1812 when the schema is built with a floor below 18, and `okm migrate apply` raises it before any statement when the server is older than 18 (D184, D261). A bare `t.id()` stores `gen_random_uuid()` (D262). OKM1191 (no snapshot plan inside READ COMMITTED): every read is one statement, so a plan always exists. OKM1702 is thrown: a raw write on a scoped tenant table, and a raw read that does not select the primary key with `ident` (D268).
- **A morph include is the matching target, or null.** `morph("commentable", ["tasks", "lists"])` and `morphMany` are in this version (D255). `has`, `none`, and `every` on the morph itself, `select`, `where`, `orderBy`, and `limit` on that include, a nested morph include, `sync` of a morph, and `descendants` through a morph are OKM1120. A hit includes the type field set to the table name. The value is also null when the target is archived or outside the tenant. A write can store another tenant's id. The include reads as the caller, so that target is null. Setting one of the pair without the other, or clearing one and setting the other, is OKM1121. Clearing both is allowed. A type outside the list is OKM1120. A preset on the target table does not filter the include. A preset on the query does. The reverse many takes a limit, an order, and `has` / `none` / `every`.
- **`vector` is not a built-in** (D281). The CI images are official `postgres` images and do not ship pgvector. `unaccent`, `hstore`, `ltree`, `btree_gist`, `btree_gin`, `fuzzystrmatch`, and `pgcrypto` are their own subpaths. Default versions are in [extension compatibility](extension-compatibility.md). `uuid-ossp` stays `extension("uuid-ossp")`. `ltree`'s `ancestorOf` and `descendantOf` are operators. They are not the parent-column walk (D252). `requires` and `provides` are checked by `okm ext test` and are not part of the catalog hash. A feature a declared version lacks fails when the method is called (OKM1812), not inside `contribute()`.
- **JSON Schema export is absent.** `insert` and `update` are Standard Schemas; they do not emit JSON Schema.
- **`onRead` is stored and not applied.** `validation: { onRead: true }` is accepted and read values are not validated.
- **`iStartsWith`, `iContains` and `iEndsWith` are not in this version** (D176). Use `ilike()` with an escaped pattern.
- **`dec` and `mul` are not in this version.** `inc` is the arithmetic write. A null number stays null. Appending to a null array stays null. A `numeric` or `bigint` column stored as a string does not accept `inc` in the types; `as: "number"` or `as: "bigint"` does. The statement still accepts `inc` when the database type is numeric (D249).
- **A claim does not take `orderBy`.** `update` with `lock: "skip"` and `limit` lets the database choose which unlocked rows, up to `limit` (D249). A `version: "any"` claim orders by the primary key so the locked set is stable. `{ returning: true }` returns those rows and honors `select`. The default result is `{ count }` (D260). `version: "any"` returns the claimed rows instead, and an empty claim is `[]`. Setting a tree parent to the row's own id, or to a descendant, is OKM1120 when `where` is the primary key. A filter that is not the key is not checked (D295).
- **Bun.sql refuses a wire integer outside int8.** An id of 2^64 is kind `invalid` on every driver. The Bun.sql check looks at the wire text, so a numeric value written as that integer is refused too (D260). A PGlite client that adopted a pool does not close the pool. `close()` marks that client closed, and a later call is `unavailable` (D260).
- **`aggregate()` ordering and `having`.** `having` names `count` and the `select` names, not a list-form aggregate (`sum: [...]`), and `orderBy` takes group keys, `count`, and the `select` names, not a list-form aggregate (D313, D314). `bucket()` groups a `timestamptz` or `date` (D247). `second`, `minute`, and `hour` on a `date` are OKM1120. An `as` that matches another bucket is OKM1120. A NULL timestamp is one group: the `as` key is present and the value is null. There is no gap filling. An `as` of `__proto__`, `constructor`, `toString`, or `hasOwnProperty` is OKM1120 (D257). Time-zone date helpers (`onDay` and the rest of tool 5) are deferred.
- **Search does not highlight, scan a plain text column, or page.** `find({ search })` and `count({ search })` match a column built for search (D250). A highlighted snippet, a search of a plain text column, and a helper that fills a search column from text are not in this version. `page()` refuses `search` (OKM1120). A missing text search configuration is OKM1122, including `public.english`. A malformed advanced search is OKM1120 and names the search input. That is a `42601` whose message names `tsquery`, or a `42601` on a search statement (`to_tsquery`), including an unescaped backslash. Other syntax errors stay `driver`. A `language` that is not text is OKM1120. A named query is a preset, or a function that returns `find` options. There is no separate call for one. `search` is not a key on an include. `matches` and `relevance` in that include's `where` or `orderBy` do apply (D251).
- **Window helpers are four.** `rowNumber`, `rank`, `denseRank`, and `runningTotal` go in `select` on `find` or `one` (D251). `lag` and `lead`, a frame (`ROWS` or `RANGE`), `ntile`, `percent_rank`, `cume_dist`, `first_value`, `last_value`, and `nth_value` are not in this version. A window inside an include's `select` is not. `page()` refuses a window when the call runs (OKM1120). An `as` of `__proto__`, `constructor`, `toString`, or `hasOwnProperty` is OKM1120 before any SQL (D258). The type of `page` still accepts one in `select`. Ordering by the helper's `as` name works when the call runs and is not part of the `orderBy` type. A nested include is in the rows. The result type names the selected columns of the first include and does not add the nested relation.
- **A refused replica holds reads that are already queued on postgres.js.** A read queued behind a refused replica waits for postgres.js's reconnect backoff before it falls back to the primary. The adapter caps that backoff well under 1 s per attempt with jitter (D294). Reads that start after the failure go to the primary at once. Before the cap, postgres.js could wait up to 19.6 s on a refused replica (QA-M1, D214).
- **Cloudflare D1 has no adapter yet.** Neon HTTP is `okmodel/pg/neon` with `mode: "http"`. D1 is still covered only by the driver contract. A Neon transaction-mode pooler does not promise session state. With one small compute it reused a backend, so a custom `SET`, `LISTEN`, and `PREPARE` stayed visible, and a second connection saw the `SET`. Do not rely on that reuse (D269).
- **`listen` is a driver capability, not a client member.** The driver contract may set `listen: true` or `false`. There is no `db.listen` / `client.listen` in this version. Spec text that lists `listen` next to `tx()` on the client type is describing the capability flag only.
- **`inspect()` on a string or a pool reports `single-endpoint`.** That call stays synchronous. On a topology client, `inspect().routing.reason` is the same string `onRoute` receives, including `auto:<name>`, `fallback:behind`, and `fallback:saturated`. The preview does not call `onRoute` and does not move the selector (D268). A string or pool client has no `using` and serves either `route` from its one endpoint. See [topology](topology.md).
- **Minimum Bun for `okmodel/pg/bun` is 1.4.** CI installs Bun 1.4.3. `Query.cancel()` does not abort an in-flight statement on Bun 1.4, and notices are not surfaced. Older Bun is not a supported floor.
- **Deno is not supported.**

## Topology

- **The watermark is client-wide.** The root, `for()`, `unscoped()`, `using()`, and `reserve()` share one commit position (D204). A write on any of them moves the watermark for the others. A watermark per `for()` client is deferred: the router cannot see which client issued the statement.
- **Statement class for a built query is the statement text.** A leading `select` is a read. That includes a `select` whose body calls `nextval`, and a view defined that way: `find` sends it to a replica, and the hot standby rejects it as read-only. The classifier stays text-based (D205). `raw` takes `"read"` or `"write"` and does not infer the class from the text alone: a read that does not start with `select`, and a write that does not start with `insert`, `update`, or `delete`, are OKM1602 (D268). A raw read can still select columns from other tables in the fragment: the wrapper binds the row key, not the joined columns.
- **`raw` is typed only through the result class (B-07, B-08).** There is no untyped `sql.raw(text, reason)` in this version. Each result column is an own enumerable key of that class, in initializer order. A key that is a field of the handle's table uses that field's decode. Any other key (a joined column, an expression, a count) uses the initializer: a number, a boolean, or driver text. `null` stays `null`. The fragment is not a second schema: joined columns are not projected through another table's codecs.
- **A fragment template refuses a backslash (OKM1125).** Postgres treats `\` as an escape in `E'...'` and when `standard_conforming_strings` is off. The guard only doubles quotes, so a backslash would desync it from the server and let a fragment close the tenant predicate. Pass the value as an interpolation. Dollar quotes, `;`, `--`, and `/*` stay refused outside quotes; inside quotes they are plain text (D287).
- **A committed write costs one extra round trip** when replicas are configured and `consistency` is `"session"`. That read is `pg_current_wal_insert_lsn()` after the commit, and it finishes before the write's promise resolves. `"eventual"`, and a connect with no replicas, do not read it.
- **A position is not carried across processes.** A cookie or a header that would keep read-your-writes across servers stays deferred (spec section 25).

## Views

- **A view is SQL plus a declared column list, or `view(name, (q) => q.from(table))`.** `view()` and `materializedView()` live on `okmodel/view`. `db.views` keys are camelCased: `active_projects` is `db.views.activeProjects`. `db.views.<name>.find(...)` is read-only. Its type comes from `schema({ views })`: each field is the camel-cased column name, typed `string | null`, because every view column is read as text. A view that reads a tenant table and does not expose the tenant key is OKM1820 unless declared `global("reason")`. The builder selects the named fields, or every field when the list is omitted. `.where(sql`...`)` appends that text. `.tenancy(global("reason"))` is the opt-out. The builder form is `public` only. It has no schema option. `materializedView()` stays the SQL form (D271).
- **`db.views.name.refresh()` refreshes a materialized view.** No arguments, and it returns `void`. The statement is `REFRESH MATERIALIZED VIEW`, with `CONCURRENTLY` when the view declares `refresh: "concurrently"`. Any other `refresh` value is OKM1120. Calling `refresh()` does not start the statement; the first `await` does. `batch([view.refresh()])` is OKM1121 before any statement. It reserves the primary and sets `app.unscoped` in that transaction, so an owner refresh under `FORCE ROW LEVEL SECURITY` sees the table. `CONCURRENTLY` cannot run inside a transaction, so that form sets the session value and clears it before the connection is released. A plain view has no `refresh` at runtime (`db.views.v.refresh` is `undefined`). The refresh runs as the owner, the migration role. The application role is kind `driver` with reason `not_owner`, and the fix says to connect as that role. A populated materialized view is not RLS-protected. It is guarded by the column predicate and by OKM1820 when the query hides the tenant key. `security_invoker` is not set on it (D227, D231, D239).
- **Column dependencies come from `pg_depend`.** Scratch verification (`sealViews`) creates the view and reads those edges. A plan from two author catalogs does not see them until that read.
- **`okm check` reprints a view on the connected server before it compares.** `pg_get_viewdef` replaces the author text, so a spelling that server prints differently is not drift after push. A query that reprints to something else still is. Two introspections of the same view match. A plan between two author catalogs still compares the text that was written.
- **`refresh: "concurrently"` is not stored by Postgres.** Introspection leaves it unset. Equality ignores it, so a later plan does not recreate the materialized view only because the mode was declared. `REFRESH ... CONCURRENTLY` still needs a unique index (OKM1822). The plan's first populate is a plain `REFRESH`, because Postgres rejects `CONCURRENTLY` until the view has rows. An index on the view is stored against the view, not against a column. `okm generate`, apply, and `okm check` round-trip a unique or non-unique index on one column or several (D236).
- **`security_invoker` is set only under `rls`.** A view over tenant tables is created `WITH (security_invoker = true)`. Other strategies omit the option. A materialized view does not set it.

## Functions and triggers

- **A call is `slugify(ident("title"))` in `where`, and `.as("slug")` in `select`.** The value `fn()` returns is that call. A numeric return is a number. A boolean return is read as text, as is any other non-numeric return. `orderBy` does not accept it: adding the call to that union measured 6,932 composite types, one over 6,931. That call in `orderBy`, and computed fields (`table({ computed })`, OKM1061), are after M2 (D282). They are not in this version. A string, number, boolean, or null is a parameter. The wrong arity is OKM1120. A value that cannot be bound is OKM1121 (D271).
- **`timestamps()` installs a trigger only with `enforce: "trigger"`.** The client otherwise sets `updatedAt` to `now()` on update. The trigger is `<table>_touch` and the function is `okm_touch_<column>`, so a table named `lists` gets `lists_touch`. `archivable()` installs no trigger. `timestamps()` together with `archivable()` installs `lists_touch` only when `enforce` is `"trigger"` (QA-L13, D215).
- **`inspect()` does not list triggers.** `okm doctor` lists the triggers on each table. A code argument prints that code.
- **A plpgsql body is the source text.** Introspection reads `prosrc`. A round trip has no steps when the declared body is that text.
- **`LANGUAGE sql` with `BEGIN ATOMIC` stores the author text.** `prosrc` is empty, so introspection reads the `BEGIN ATOMIC` block from `pg_get_functiondef`. Postgres qualifies an argument as `function.argument` when the body names a table, and it may add parentheses or an `AS` alias. `okm migrate check` and `okm check` create the function on a scratch schema and read that block back before they plan, so the qualifier is not OKM1547 or drift (D273). The match is the function name plus its identity arguments, so two overloads of one name do not share a body. A body that reprints to different SQL still is. A plan between two author catalogs still compares the text that was written. `okm migrate check` warns OKM1552 when the stored `LANGUAGE sql` body differs from the catalog (D276). plpgsql is not that warning. Dependencies are the `pg_depend` edges. Two introspections of the same function match.
- **A trigger `WHEN` is stored as written.** Introspection reads the predicate from `pg_get_triggerdef` (not `pg_get_expr`), because `OLD` and `NEW` are two relations and `pg_get_expr(tgqual, tgrelid)` fails with "expression contains variables of more than one relation". Columns named through `OLD` / `NEW` are ordinary column dependencies on the trigger's table. A predicate Postgres reprints differently (extra parentheses, folded identifiers) is planned as a trigger change. A round trip has no steps when the stored text is already that printed form. `defineConfig({ namespace })` places the trigger's called function with the rest of the catalog; apply no longer fails OKM1020 for a missing function in `public`.

## Roles and grants

- **The application role's grants stay the fixed set.** `roles: { migration, app }` grants `SELECT`, `INSERT`, `UPDATE`, and `DELETE` on tables and views; `SELECT` on materialized views; `EXECUTE` on functions; `USAGE` and `SELECT` on sequences. Default privileges use that set, `FOR ROLE` the migration role, in the target schema. Privileges outside that set, and outside a declared column grant, are not diffed. Postgres also applies the table default privileges to a new materialized view, so the application role would keep `INSERT`, `UPDATE`, and `DELETE` there. The plan revokes those three after it grants `SELECT`. The catalog stays select only (D236).
- **Column grants are `roles.columns`.** Each entry is `{ role, on, select?, update? }`. `on` is the SQL name of a table, view, or materialized view. The privilege is `SELECT(email,status)` or `UPDATE(...)`, columns sorted, no spaces. The grant and the revoke lowercase the privilege keyword and quote each column with its stored bytes, so `tenantId` stays `"tenantId"` and a reserved word stays quoted (D241). The grant key stays `(role, object, privilege)`. A hidden column is not in the reporting role's select unless that entry names it. A view's listed columns replace table `SELECT` for the reporting role. A table the migration role creates by hand keeps the default table `SELECT` until a plan grants column `SELECT` and revokes the table privilege (D232).
- **`roles.reporting` is select only, and it is not tenant-safe against its own SQL.** It gets `SELECT` on tables, views, and materialized views, `USAGE` on schemas, and default `SELECT` on later tables. It does not get `INSERT`, `UPDATE`, `DELETE`, or `EXECUTE`. Giving it `UPDATE`, or using the migration or application role as its name, is kind `invalid` (`reason` `reporting_write` or `reporting_distinct`). It is not `BYPASSRLS`. Under `rlsTenancy` it sees no tenant rows unless the session sets `app.tenant` or `app.unscoped`. The role can set `app.unscoped` itself and then read every tenant. `unscoped()` is the application client's read escape and is not given to this role (D232, D238).
- **The migration role must own the schema before `roles.reporting` is applied.** `GRANT USAGE ON SCHEMA` is a silent no-op when the acting role does not own the schema, and Postgres only warns. Apply then fails with OKM1825 and the fix is `ALTER SCHEMA <schema> OWNER TO <migration role>`. When apply creates the migration role, it grants `CREATE` on the database and transfers schema ownership when the connecting role can (superuser, or the schema owner with `CREATEROLE`). Before `SET ROLE` or `OWNER TO` it grants itself membership (`WITH SET TRUE` on Postgres 16+; a plain grant on Postgres 15, where `CREATE ROLE` leaves no membership). Create that role first (`NOLOGIN`, `CREATEROLE` when the plan also creates the other roles) if you connect as someone else. A superuser satisfies the `CREATEROLE` preflight when `rolcreaterole` is false. Managed-provider admins (RDS, Cloud SQL, Supabase) are not guessed here (M-4). Introspection still treats an ACL entry for `PUBLIC` as the reporting role's `USAGE` on a schema that already records it. A new schema whose ACL is null does not. `okm migrate check` makes the migration role the owner of its scratch schema when that role already exists, and it replays `GRANT USAGE ON SCHEMA` there (D236, D293).
- **With `roles` set, functions are not `PUBLIC EXECUTE`.** Apply revokes `EXECUTE` from `PUBLIC` on managed functions and from default privileges for the migration role, and grants `EXECUTE` only to the app role. The reporting role still has no execute. Without `roles`, Postgres keeps the default `PUBLIC` execute (D293).
- **`okm migrate status` queries every target and stops at the first unreachable one.** It does not require `--target`. `okm check` and `okm doctor` with several targets and no `--target` only lint (and list triggers); they print `server checks skipped: N targets, pass --target <name>` and do not connect. Commands that must pick one database still refuse with OKM1853 when `--target` is omitted (D293).
- **A `?pgbouncer=true` query parameter is stripped before migrate opens a connection.** It is still a pooler signal for the migrate URL guard. Other pooler hints in the URL are not interpreted. The pid probe uses eight reads on the apply session; two or more distinct backend pids are OKM1854. That catches a rotating transaction-mode pooler on any port. Default LIFO PgBouncer (`server_round_robin=0`) on a port other than `6432` / `6543`, without `pooler` / `pgbouncer` in the host and without `?pgbouncer=true`, can pass the URL guard and the pid probe and let apply run (B-41). Warm-and-hold for LIFO is not run during apply/seed (extra connections deadlock PGlite wire and other single-session targets). Mark such a URL with `?pgbouncer=true`, or use a direct connection (D293).
- **`withOwner(table(...), "ignored" | "external")` is the ownership mark.** `ignored` is invisible to diffs, plans, and `okm check`. `external` is never created, altered, or dropped. `external(table)` is that mark. `okm check` and `okm migrate check` verify an external table against the snapshot named by `defineConfig({ external })`. When that list is omitted, the mark is not compared with a file. A stale or missing snapshot is OKM1841. `okm generate` and provisioning omit both. Neither appears in the SQL. A managed table that becomes either stays in the database and the plan has no DDL. Removing the declaration while the stored snapshot still says `managed` drops it. After a snapshot stores the mark, removing the declaration does not drop it. Keep the declaration, or drop the table while it is still managed, when it should go away. Dependents follow the table. The ownership mark itself is outside the startup hash; the external table's columns are inside it (D232, D277, D289). When the owner adds a column and the dependent exports a new snapshot, the plan may have no DDL and `okm push` / `okm migrate apply` re-stamp `okm_meta` so `connect()` matches. After that re-stamp, `okm migrate status` stays `current`, `generate` stays `no changes`, and `okm migrate check` does not OKM1549 for the external-only catalog drift (B-45).
- **A foreign key across catalogs stays inside one database.** `defineConfig({ namespace })` places the catalog and, on apply, creates that schema and sets the session search path so `okm_meta`, `okm_history`, and `okm_backfill` land there. `public` is unchanged. `connect()` reads those tables in that namespace (D283). A foreign key across those catalogs is allowed on one database. Another database is OKM1842. `okm check` lists the key as a `coupling` warning (D277).
- **A role is never dropped.** A plan creates a managed role when `pg_roles` does not have it (`CREATE ROLE` has no `IF NOT EXISTS`) and alters `LOGIN` and `INHERIT` in place. Roles belong to the cluster, so apply runs that `CREATE ROLE` in a `DO` block that ignores a role another database's apply created first. Two databases provisioned at once both apply. A password, `GRANT OPTION`, and any other attribute are not stored. A name in `roles` is external unless it is also listed in `managed`.
- **Two applies that alter the same role at once can fail.** When two databases on one cluster run the same `ALTER ROLE` step concurrently, Postgres fails the second with `tuple concurrently updated`. Run apply again. A provision from the head snapshot only creates roles, so parallel previews are not affected.
- **OKM1825 is `okm doctor` only.** `connect()` does not check roles. Putting that check on `connect()` measured +2,690 minified bytes and +917 gzip on `okmodel/pg/postgresjs` (the same minified increase on the other connect entries) and +2,699 / +941 on the featureless app, which is past the budget. `okm doctor` checks the application role, the reporting role, and each declared grant, including column grants. `okm_meta` is not a catalog object. Apply grants the application role `SELECT` on it and no other privilege, on an empty target and again when the table is already there (D232).
- **A function grant is `name(argTypes)`.** Argument types are joined without spaces. Introspection and `okm doctor` read `oidvectortypes(proargtypes)` with the spaces removed, so argument names are not part of the grant (D208).
- **Roles and grants are not in the startup hash** (D208). `connect()` compares the schema's catalog without them. A role or grant that drifted is found by `okm check` and `okm doctor`, not at startup.
- **Creating the migration role grants it the schema, then `SET ROLE`.** Those statements are runner actions, not plan steps. The role is `NOSUPERUSER NOCREATEDB NOCREATEROLE`. The schema grant is `USAGE` and `CREATE` on the schema the migration targets (`public` unless apply was given another). The same run grants that role `SELECT`, `INSERT`, and `UPDATE` on `okm_meta`, `okm_history`, and `okm_backfill` when this run created them as another role. On an empty database, `okm migrate apply` installs the head snapshot (provision). That path commits each `CREATE ROLE` before it transfers schema ownership, so ownership runs outside the role unit's transaction and does not use a savepoint when none is open. A failed provision that left only empty bootstrap tables drops them so a retry sees an empty target again; when another object remains, the bootstrap tables stay and the next apply is OKM1851 naming that object. Managed roles are cluster objects and stay (the next apply ignores duplicates and re-applies schema and meta grants). `CREATEROLE` is always checked on the connecting user, never on the managed migration role.

## Domains

- **The base type of a domain cannot change.** A plan that replaces `t.domain("pos", t.integer(), …)` with `t.domain("pos", t.text(), …)` fails with OKM1020 and names both types. The base stays as it was created. Add a new domain when the column needs another type.
- **An enum cannot be the base of a domain.** `t.domain("shade", t.enum("color", ["red"]), …)` is OKM1060. Use a scalar column type.
- **A domain check is stored as written.** Introspection reads the check Postgres prints (`pg_get_constraintdef`, with the leading `CHECK` removed). `okm check`, `okm push`, and `okm migrate check` reprint each domain check on the connected server before they plan, so an author spelling such as `VALUE > 0` is not permanent live drift or OKM1547 against `((VALUE > 0))` (D289, B-37). `okm migrate check` still warns OKM1552 when the stored text differs (D276). The catalog hash keeps the author text.
- **A table check and a picklist are stored as written.** Postgres reprints `IN (...)` as `= ANY (ARRAY[...])`, and `varchar(n)` adds casts. The same commands reprint each table check on the connected server before they plan, so a picklist or an `IN (...)` check is not permanent OKM1547 or a NOT VALID/VALIDATE swap (D128, §19.3). The catalog hash keeps the author text. Check `columns` are not part of the plan comparison: an author check may omit column handles while introspection lists `conkey`.

## Safety and tenancy

- **`UNIQUE (id, tenant_id)` stays beside `PRIMARY KEY (id, tenant_id)`** (D168, D171, D223, D234). The primary key is the declared key plus the tenant key, so two tenants can share an id. The extra unique is the same columns. Composite foreign keys and `onConflict` target that unique. `archivable()` turns it into a partial unique index, which a primary key cannot be. D234 renamed it. It is not dropped.
- **A unique that a trait adds after the tenancy rewrite is not widened** (D168). `columnTenancy().rewrite()` runs first and widens uniques the table already declared. Trait `apply` runs after that, so a unique introduced by the trait stays on the trait's columns only. `timestamps()` adds no unique. `archivable()` adds no unique either: it turns uniques that already exist into partial unique indexes (`WHERE archived_at IS NULL`) after the rewrite, so a tenant unique stays `(tenant key, column)` with that predicate. The primary key stays a full constraint. `sortable()` names the tenant columns on its position index itself (D254).
- **Archive cascades to direct children only.** `archivable({ cascade: ["projects"] })` archives the active projects of an archived org in the same statement, with the same `archiveId`. It does not archive the tasks of those projects. A grandchild stays active under an archived parent until you archive it, or until its own parent has `cascade` for it. Restore follows the same rule: it restores the children that share the row's `archiveId`.
- **A table named `tx` or `batch` is shadowed.** On the client, `db.tx` and `db.batch` are the methods. A table with either name is unreachable by that property; rename the table.
- **The row-level security guard runs once per endpoint and generation.** The first scoped statement on that endpoint checks the role and the policies. A policy weakened while the process keeps running is noticed when the endpoint reconnects and the generation changes, not on the next statement of the open pool (D238, D241). The check resolves each tenant table with `to_regclass`, so a schema named after the connected role does not hide the tables okm created.
- **`.stream()` does not use a server cursor (D256).** The postgres.js `FETCH` loop measured 15,781 adapter-incremental bytes against 15,093 and stays unbuilt (D245). `.stream()` walks keyset batches on every driver, including PGlite, so a lost connection fails the batch the same way a `find` fails. A server cursor is a later opt-in.
- **Row-level security adds latency.** A scoped read is about 0.3 ms. The same read with column tenancy is about 0.06 ms. A statement inside `tx()` is about 1 ms slower. Those are one sample, not a gate (D241). Reducing the extra round trips stays deferred. 0.8 did not change them.
- **`okmodel/session` does not authenticate (D312).** `db.with({ userId })` sets `app.user_id` for the unit. Nothing proves the caller is that user. Your application decides the value, and a database role that can run SQL can run `set_config('app.user_id', ..., true)` itself and read any row the policy lets that setting see. It is a way to hand an identity to a policy or a trigger, not a credential. A policy reads it as `NULLIF(current_setting('app.user_id', true), '')` before a cast, because the setting reads as an empty string after the transaction. It is Postgres only. The MySQL family has connection-level variables that a pooled connection hands to the next client, and SQLite has none, so both refuse and name column, composite, or path tenancy. No MySQL or SQLite pack exists in this version: the refusal is `assertSessionSettings()` in the capability registry.

## Reads and types

- **`allow: ["id"]` on a database-default id typechecks and throws (D272).** `insert({ id }, { allow: ["id"] })` on `t.id()` or `t.id({ default: "uuidv7" })` is accepted by the type. The runtime is OKM1190. The server still assigns `gen_random_uuid()` or `uuidv7()` when the insert omits `id`. A list opens `id` in the type only when `allow` is exactly `["id"]`. A longer list does not. There is no row-type flag that separates a client generator from a database default.
- **`.stream()` needs a primary key and a stable order (D256).** No primary key is OKM1120. The order is `orderBy`, then the primary key. No `orderBy` is the primary key, ascending. `limit` is the total number of rows. The default batch is 1000. `search` and a window are OKM1120. `one()`, `count()`, and `exists()` are OKM1120. A `timeout` that is not a number above 0 is OKM1121. A row committed while the stream runs can be seen or missed. `tx({ isolation: "repeatable read" })` reads one snapshot of the primary, because the transaction holds that connection. On `connect({ primary, replicas })` the first batch chooses the endpoint and later batches stay there. They do not rotate, and a failure does not continue on another replica. `timeout` is the budget for the whole stream. A driver that cannot cancel does not abort a batch that is already running.
- **`descendants` and `ancestors` do not read `ltree` (D252).** The walk is a recursive statement on the self-relation's parent column. `ltree` stays a column type. An index that uses it is not built. There is no `include`. The statement starts with `WITH`, so it runs on the primary. `where` and a preset filter the rows that come back and do not cut the walk short. Tenancy and the active set apply at every step, so an archived row is not crossed and the rows under it are not returned. A primary key that is not exactly one column besides the tenant key is OKM1120. A missing id returns no rows.
- **`sync` is two statements in one transaction, and it is not a batch member (D252).** The first locks the parent. The second changes the links and sees what a sync that just committed wrote. `expect` throws after those statements. Outside `tx()` the change is already committed. Inside `tx()` the throw rolls the transaction back. A join column the client fills, with no database default, is OKM1120. A non-nullable foreign key is OKM1120, because clearing the link would delete the row.
- **`sum` and `avg` over a `text` column pass the types and fail when the call runs (OKM1124).** The row types cannot tell a `numeric` string from a `text` string.
- **`bigint` as `bigint` aggregates are refused (OKM1124).** `sum` and `avg` over a `bigint` column that reads as a JavaScript `bigint` do not run (the total has no honest `bigint` type). Map the column as a string or a number, or read the rows and add them in the application. `min` and `max` work.
- **Date and time columns need a `Temporal` global.** Bun and Node 26 provide it. Node 22 and 24 need a polyfill assigned to `globalThis.Temporal` before those codecs run (for example `temporal-polyfill`). okmodel does not ship one. A missing global fails with OKM1210 and that fix.
- **Some intervals and times cannot be read.** An `interval` that mixes signs, such as `1 day -01:00:00`, cannot be one `Temporal.Duration`, so a read that selects it fails with OKM1210. The decoders take the default `IntervalStyle` (`postgres`) and ISO-8601; `sql_standard` and `postgres_verbose` output is not read, and that is OKM1210 too. A `timetz` with a seconds offset such as `+05:30:15` is OKM1210 (D179).
- **Finer than microseconds does not survive a write.** A value keeps microseconds (QA-L1). Digits past the sixth are rounded by Postgres on write: `2020-01-02T03:04:05.123456789Z` reads back as `.123457`. An explicit precision truncates client-side instead. Either way a read-back differs from the written value past microseconds, with no warning.

## Transactions, cancellation and batch

- **`idleInTransaction` is a client-side timer,** not the server's `idle_in_transaction_session_timeout`. The client fails the transaction when it has sat idle that long; the server setting is untouched.
- **On PGlite and Bun.sql a `signal` cannot kill a statement waiting on a lock.** `tx({ timeout })` and `batch({ timeout })` with a positive timeout are OKM1120 before the call starts, the same as a per-call timeout (D241). A `signal` is not refused. It does not settle a statement that is already running, and the rollback queues behind the waiting statement. PGlite has one connection and no `cancel`; Bun.sql has no `cancel` on Bun 1.4 (D181).
- **A positive `timeout` on Bun.sql and PGlite is OKM1120, listed on the first screen** (D224, D239, D241). That is a per-call timeout, `tx({ timeout })`, and `batch({ timeout })`. A `signal` still does not settle a statement that is already running. A call that is still queued, rather than running, is refused with kind `timeout` or `cancelled` before it starts.
- **On PGlite a call made on the outer client from inside a `tx()` callback queues behind the transaction (QA-M3, D216).** The transaction holds the single connection, so the outer call waits for the callback that waits for it. It is not refused: OKM1192 stays reserved for the refusal and is not thrown in this version. A call from unrelated code that merely runs while a transaction is open queues the same way. Set `timeouts.acquire` when that wait should fail instead. Use the client the callback received.
- **Bun.sql has no notices.** It does not surface `RAISE NOTICE`, so `hookm.onNotice` never fires on `okmodel/pg/bun`.
- **`connect({ hookm })` is an array of observers.** Pass `hookm: [observer]`. A single observer object is not iterable as a list, so observers never run usefully; use an array. The misspelled key `hooks` is not a connect option and is ignored; use `hookm`.
- **`restore` and any write with `expect` are not allowed in `batch`** (D183). Both are checked against the result of their statement, and a batch cannot report that after it commits. A batch that holds either is refused with OKM1121 before any statement is sent, with the error naming `tx()`. Use `tx()` for them. A statement the database refuses (a unique, a foreign key, a check) still rolls the whole batch back.
- **The types still accept `restore` and `expect` inside `batch`; only the runtime refuses them** (D184). Narrowing the types so the compiler refuses both was measured in 0.2.1 and not built: refusing the `{ expect }` option takes a second overload on every write method, which moved the `query-200-validate` probe from 25,047 to 27,366 instantiations against a ceiling of 25,631. A `restore` or a `.expect()` call on its own costs +2 / +1 on every probe; the option form is the part that does not fit.

## Drivers

- **The first call after a backend kill on an idle connection is `unavailable` and retryable.** Bun.sql retries a client read once at transaction depth 0. postgres.js and node-postgres do not.
- **A reserved Bun.sql handle fails closed after its backend is killed.** Once the pool has drained the closed socket, the next statement is `unavailable` (SQLSTATE `08006`). It does not run on the new connection, so a scoped read does not come back empty. A client that answers `connection must be a PostgresSQLConnection` is replaced. Bun 1.4.3 still does this, and `close()` on that client may not return, so the adapter drops it, bounds pool `close()` at one second, and the next call dials a new pool (oven-sh/bun#46166). Reserved handles always return to Bun's pool after reset; the adapter does not park a session for the next checkout. A reset or release failure after the statement or `COMMIT` completed destroys the connection and does not fail the call, so `afterCommit` still runs. A failure after the send and before the result is `outcome_unknown` (OKM1401): it is not retried, and `afterCommit` does not run (D288).
- **postgres.js rejects a wait on a close only when that wait can no longer succeed.** The wait has no call deadline, and every slot in its pool has closed, or the closed connection is the reserved one that wait is using. A close of another slot, including an idle timeout or a max lifetime, does not reject it. A wait that already has a call deadline is not on the close hook. It ends at that deadline.
- **postgres.js can emit an unhandled rejection when the backend dies during connect.** Its type-catalog query rejects with `write CONNECTION_CLOSED` and nothing handles that rejection. Calls okmodel started still settle.
- **postgres.js raises uncaught exceptions under a backend kill storm (B-02, upstream).** With postgres.js 3.4.9 alone (no OKModel), concurrent queries plus `pg_terminate_backend` produce uncaught `TypeError` from `connection.js` `nextWrite` (`socket.write` on null: Bun `evaluating 'socket.write'`, Node `reading 'write'`) and unhandled rejections (`CONNECTION_CLOSED`, 57P01). Measured on this tree: Bun 20 events over 5 runs (0 clean), Node 22 20 over 5 (0 clean). Through `okmodel/pg/postgresjs`: Bun 152 over 5 (124 socket), Node 102 over 3 (90 socket), 0 clean. The reserved-connection `lost` guard and reserve-only traffic do not stop it; the write is scheduled inside postgres.js. A process-level `uncaughtException` listener (D294) can keep the process alive and rebuild the pool, but it does not remove the exception and is not a fix. Prefer `okmodel/pg/pg` or `okmodel/pg/bun` where failover or kill storms are expected. Minimal reproduction: `postgresjs-kill-storm.md` and `postgresjs-kill-storm.mjs` in the repository source. Neither file is part of the published package. Reconnect backoff stays capped under 1 s per attempt with jitter; `timeouts.acquire` defaults to 10 s (OKM1846). The upstream `fetchArrayTypes` unhandled rejection on connect-loss stays.
- **A queued `sql.reserve()` is dropped without settling when a connection slot closes.** Repro: `max: 2`, hold one connection, queue `sql.reserve()`, `pg_terminate_backend` on the other backend. okmodel starts that reserve again.
- **A lost connection is released without a rollback (D244).** Classification uses the driver `code` or a SQLSTATE in class `08` or `57P01`–`57P03`, not the error text. A live session is rolled back and then released. A session that is gone is destroyed on release, and nothing more is sent to it. A backend that is actually gone holds no locks.

A postgres.js pool opened with `ssl` still uses the driver's socket and its 30 s idle timer (D152). Measured on Postgres 17 with TLS 1.3, one query, and no `close()`: the process exited in 30.10 s on Bun and 30.07 s on Node 26. A plain pool (no `ssl`) exits on its own. `close()` or `await using` releases a TLS pool without waiting. A missing table is reason `undefined_table` and a missing column is reason `undefined_column`. The fix names `okm migrate apply` and `okm migrate status`. A TLS or certificate failure is kind `unavailable` with reason `tls`, and the fix names `sslmode`.

node-postgres sets `allowExitOnIdle` and `idleTimeoutMillis: 0`. A plain pool exits after the last query, and an idle connection stays open while the process is alive. The same unref applies to the TLS stream `pg` uses after the handshake. This tree has no TLS server, so that path is unread. `pg` cannot describe a statement without running it. That conformance case is skipped.

Bun.sql keeps `idleTimeout` at 0, which is Bun's default (no idle timer). A finished Bun script exits without `close()`. `Query.cancel()` does not abort the backend statement on Bun 1.4, and Bun.sql does not surface `RAISE NOTICE`. Those conformance cases are skipped. Bun.sql also cannot describe a statement without running it. `okmodel/pg/bun` loads only on Bun.

## Migrations

- **A volatile default is a batched backfill** (D193, D195). The planner adds the column nullable, sets the default, then fills existing rows with an idempotent `UPDATE` (`where` the column is null) in key-range batches. A removed picklist or enum value uses the same step (`where` the old value). A stable or constant default stays a plain `ADD COLUMN`. The step format, the pause, and resume are in [backfill](backfill.md).
- **A backfill does not iterate tenants.** Column tenancy is one pass over the whole table. Iterating tenants belongs to schema-per-tenant and database-per-tenant (M5).
- **The backfill checkpoint is on the target, not in a control database.** `okm_backfill` is created by apply. The control database in §19.5 arrives with the multi-target runner (M5).
- **On a protected target, a migration with a backfill stops after its expand steps.** `okm migrate apply` runs the steps before the backfill (adding the column and its default), then refuses the backfill with OKM1850. `okm migrate status` prints `failed at step N (resume with okm migrate apply)`. Running apply again with `--allow-protected` resumes at the backfill. Rehearse on a clone first (see [example app](example-app.md)).
- **There is no `okm backfill` command.** The step is in the migration file. `okm migrate apply` runs it. Progress lines print a 1-based step index (`backfill <id> step 1 batch …`), matching apply's `failed at step N`. `okm migrate status` still prints the stored (0-based) step index in `failed at step N` and in the unfinished-backfill table.
- **A committed step that fails is resumed from the database, not by running the statement again.** `okm_history` is still the only done record. `okm_steps` holds the step only while it is in flight or broken. The next apply probes that step. A built-in probe covers concurrent index create and drop, `add-constraint`, `validate-constraint`, and `add-enum-value`. A hand-written step can declare `-- probe:`, one read-only `SELECT` that returns true when the step is already applied. A declared probe has no cleanup. A probe that cannot decide stops with OKM1553. OKM1557 refuses a committed step with neither kind of probe. OKM1558 refuses a probe that is not one read-only `SELECT` or that sits on a transactional step. `okm migrate resolve` records a step a person finished, or marks it to run again. There is no skip. The resume table, the journal columns, and the step id are in [When a migration fails](migration-failure.md).
- **A backfill does not store the row estimate.** `about N rows, about M batches` is plan output only (D194). Resume reads the last key in `okm_backfill`.
- **Row estimates are `pg_class.reltuples` on the selected target** (D194). `okm migrate plan` prints them when that target is reachable. It does not run `count(*)`. A table that has not been analyzed prints `rows unknown (table not analyzed)`. A table the target does not have yet prints `new table`. The number is only as fresh as the last analyze. A partitioned table, or a parent with inheritance children, is estimated from that relation's own `reltuples`, not by adding the children. Estimates are plan output only: the linter does not read them, and they are not written into SQL, catalog files, or `okm_history`. `okm generate` stays offline.
- **A path foreign key is created after the unique it references** (D236). Tenancy keeps a separate unique on the path end's declared primary key. The plan pulls that unique in front of the foreign key. The order does not depend on table names. Drops reverse that order, so the foreign key goes before the unique.
- **A declared table rename renames default names only** (D194). `renamedFrom` on a table plans `ALTER TABLE … RENAME TO`, then renames a primary key, unique or check constraint, foreign key, index, or identity sequence when its name is the default `{table}_…`. A custom name stays. An add and a drop with no declaration is OKM1530. The recreate check covers every object kind the planner handles; no generator shape was excluded.
- **Generated unique and foreign-key names use SQL columns** (D234, superseding the TypeScript spelling in D223). The name is `{table}_{every SQL column}_key` or `_fkey`, after `casing` and `sqlName`. The extra tenant unique is `tasks_id_tenant_id_key` on `(id, tenant_id)`. A column `.unique()` on `title` is `tasks_tenant_id_title_key`. The stored name key stays the token the schema already kept (`id_tenantId`, `title`, `email_taken`). A primary key stays `{table}_pkey`. A picklist check uses the SQL column. A named check keeps the author's name. Indexes already use SQL names. A name longer than 63 bytes keeps a hash suffix. `renamedFrom` renames the constraint. It does not drop it. A database created before this spelling plans only those renames, and the next plan is empty. `connect()` on the old catalog is OKM1520 until apply. `.unique()` and `index()` do not take a `name` option. The catalog builder already accepts one. `column.ts` and `table.ts` are on the featureless-app startup path, so the option is later. `mapPostgresError` returns the stored name key when the caller passes the schema, and the TypeScript fields when that key is only the SQL column list of a composite constraint. With no columns in the error, the stored name key is the reason. `connect()` passes the schema it already holds, so a violation through the client reasons the stored name key.
- **The linter does not connect, and it is not data-aware.** It reads the plan and the catalogs. An existing table is one present in the catalog before the plan. It cannot see how many rows are stored.
- **A type change that rewrites the table is not rewritten** (D193, D276). OKM1538 stays a warning, and only when the heap rewrites. It does not fire for `varchar(n)` widening, `varchar` to `text`, `text` or `varchar` to unconstrained `varchar` or `bpchar`, a numeric precision increase at the same scale, `numeric(p,s)` to `numeric`, `integer` to `oid`, `cidr` to `inet`, `xml` to `text`, an unconstrained domain over the old type, or any domain to its base. A `USING` expression that is not a plain cast of the column still fires. `timestamp` to `timestamptz` still fires, because Postgres skips that rewrite only when `TimeZone` is UTC and the linter does not connect. `varchar(n)` shrinking and `character(n)` widening do rewrite. `numeric(p,s)` to unconstrained `numeric` still fires OKM1533: that rule still reads unconstrained numeric as precision 1000 scale 0. There is no safe form in this version. The documented answer is the expand/contract recipe in [a type change that rewrites the table](type-change.md): add the new column, backfill it, dual-write, switch reads, then drop the old column, each as its own migration (D285). `okm migrate type-change` is not a command. OKM1524 already requires a reason for the type change.
- **OKM1706 and OKM1823 are not linter rules.** With `indexes: false`, or `tenantIndexes: false`, an index on a tenant table that does not lead with the tenant key is OKM1706 when the schema is built. The default prefixes that key instead (D306). `.global("reason")` is the opt-out and does not raise OKM1706. `security: "definer"` without `searchPath` is OKM1823 on `fn()`. Both fail at declaration time, which is stronger than a lint, and the linter does not copy them.
- **OKM1542 flags a data statement outside `backfill()`.** `insert`, `update`, `delete`, `merge`, `truncate`, and a `with` that writes, are errors. `DO` and `CALL` are errors too: the body is not analysed (D211). A backfill `update` is not. Reference rows are not migration steps, so they are not flagged. See [provisioning](provisioning.md).
- **`okm migrate check --with-data` is a proposal.** The command stays an empty-table replay. It does not copy the target's rows into the scratch schema, so a step that fails only on real data is not caught: `NOT NULL` on a populated column, a unique index over duplicates, or a check over existing rows. A passing run prints that limit after `ok N migrations`. A later mode would replay against a copy of that data. It is not a flag in this version.
- **`okm migrate check` reuses an extension that is already installed.** `CREATE EXTENSION` is database-wide, so a second create after apply fails with already exists. The replay moves that extension into the scratch schema for the transaction. `ROLLBACK` puts it back. The extension's schema after the command is the one apply left.
- **`okm migrate check` does not change the selected database.** Lint runs before the replay. The replay creates a scratch schema inside one transaction, sets `search_path` to that schema, and ends with `ROLLBACK`. It does not leave a system catalog or a real ACL changed. An extension that is already installed is moved into the scratch schema for the replay; rollback restores its schema. Run it as a non-superuser. A superuser replay executes the step as written, and that step can reach `COPY ... PROGRAM` and `lo_import`. A `NOSUPERUSER` owner of the database cannot. `CREATEROLE` is not required for the replay. `COMMIT`, `END`, `ABORT`, `ROLLBACK`, `BEGIN`, `START TRANSACTION`, `PREPARE TRANSACTION`, and `COMMIT PREPARED` in a step are OKM1551, including a `DO` body and including when `-- okm-allow` silenced the lint. A `COMMIT` or `ROLLBACK` inside `CREATE FUNCTION` or `CREATE PROCEDURE` is not OKM1551. A SQL-standard `BEGIN ATOMIC` body on those statements is supported and stays one statement, so its semicolons and closing `END` are not OKM1551. `BEGIN ATOMIC` outside them is still refused. Apply still honors an allow for a step check refused. `VACUUM`, `CREATE DATABASE`, `DROP DATABASE`, and `ALTER SYSTEM` are not executed; the output names them. `CREATE INDEX CONCURRENTLY` and the other concurrent forms run without `CONCURRENTLY`. A check passes as a superuser and as a `NOSUPERUSER` `NOCREATEROLE` owner of the schema (D242). A replay that rolls back does not open a second connection to drop the scratch schema. A step that commits still drops that schema on a new connection, and a lost connection still confirms the drop (D245).
- **`okm migrate check` does not check tenant targets.** Tenant targets and schema-per-tenant checking are M5. The command checks the selected target's history in one scratch schema.
- **The previous-catalog check is schema-level only.** It requires every table, column, constraint, and type from catalog N−1 to remain in N, with the same type, and it refuses a tighter nullability that has no default unless the migration's recomputed class is `contract`. It does not prove application behaviour.
- **Upgrade: an archivable unique index created before D208.** `archivable()` now writes the partial index predicate the way Postgres prints it, `(archived_at IS NULL)`. On a database created with the old text, after the upgrade `connect()` is OKM1520 ("behind the app") and `okm check` is OKM1510 with `OKM1529 creates a unique index`. Clear it with `okm generate archive_predicate`, add `-- okm-allow OKM1529: rebuilds the same index` above the `create unique index concurrently` line, then run `okm migrate apply`. The index is dropped and created again with the same definition. `okm migrate check` still fails with OKM1547 at the migration that first created the index, because that migration's stored catalog keeps the old text. It failed the same way before the upgrade. `lintFrom` does not change it: it only skips lint. No command rewrites a shipped migration.
- **Upgrade: a database applied with `roles` before D208.** It stores a hash that counted roles and grants, so after the upgrade `connect()` is OKM1520 until `okm migrate apply` runs once. That apply prints `restamped <migration id>` and needs `--allow-protected` on a protected target.
- **A migrate target cannot be a replica** (D201). `database` or `targets` that carries `primary`, `replicas`, `weight`, or `pool` is OKM1845. The command does not resolve that URL. A string URL is still the primary.

## Windows

- **Migration SQL is read as LF.** `\r\n` and a lone `\r` are normalized when the file is read, including inside a SQL string literal. Apply, `okm migrate check`, the linter, and `okm migrate status` see the same steps as an LF file. A literal that must contain a carriage return does not survive that read (D237, D241). A non-empty file that still has no steps, and no `-- no steps` line, fails with kind `invalid` and reason `no-steps` instead of printing `nothing to apply`.
- **Save files as UTF-8.** A leading BOM is stripped from migration SQL, catalog JSON, and `catalog.hash`. UTF-16 is refused.
- **`.okm/catalog.json` is hashed after `\r` is removed.** An LF file keeps the hash `okm build` wrote. `okm generate init` writes `.gitattributes` when the project has none: `migrations/*.sql text eol=lf`, `*.catalog.json text eol=lf`, and `.okm/** text eol=lf`. An existing `.gitattributes` is left as it is. Add those lines when the file is already there.
- **Config paths are resolved from the project directory.** `schema`, `tables`, `migrations`, `out`, and a seed file may be absolute or begin with `..`.
- **Use a TCP URL.** `postgres://localhost:5432/app` is a direct connection. A Windows named pipe is not a URL this version opens.
- **Keep file names in the same case as the disk.** The catalog treats `Schema.ts` and `schema.ts` as different modules. Windows does not. `okm pull` and `okm import drizzle` avoid that collision for generated table files: stems are unique when folded to lowercase, and a Windows-reserved stem (`con`, `aux`, `nul`, `com1`–`com9`, `lpt1`–`lpt9`) gets a `_` prefix (D290).
- **Three Windows surfaces stay unknown.** The Windows CI job ([`.github/workflows/windows.yml`](../.github/workflows/windows.yml)) does not cover them: two spellings of one module inside the catalog hash, `okm driver test` spawning `bun` from a source checkout, and an idle postgres.js or node-postgres socket letting a finished script exit. The job does not start Postgres, so the socket step is skipped. The detail is the OKE Windows audit in the repository, which is not part of the published package.

- **First-or-create sees a concurrent insert in read committed (D246).** The lookup is a second statement and does not set isolation. Repeatable read and serializable can still miss the row another transaction committed while the insert waited.
- **`versioned()` does not cover delete, archive, or restore (D254, D305).** An update checks the version you read and bumps it. `delete`, `archive`, and `restore` do not. An upsert (`onConflict` update) is OKM1120. `.all()` is OKM1120. Omitting `version` is a TypeScript error on a versioned table and OKM1120 at runtime when types are bypassed. `version: "any"` is the exception, and only together with `lock: "skip"` and `limit`: the check is skipped, `version` still becomes `version + 1`, and the call returns the claimed rows (an empty array when none match, not `conflict`). The statement locks the primary key once (`ORDER BY` the key, `LIMIT`, `FOR UPDATE SKIP LOCKED`) and repeats the caller's predicate on the `UPDATE ... FROM`, so a row whose state changed is dropped and the write never changes more than `limit` rows. Run that claim in `READ COMMITTED`. Under `REPEATABLE READ` or `SERIALIZABLE` the same race can raise SQLSTATE 40001 (kind `serialization`) instead of dropping the row. `version: "any"` without `lock: "skip"` and `limit`, an unrecognised version string, and a `version` key in `set` are OKM1120. `version` on a table that is not `versioned()` is OKM1120. A path-tenancy parent column cannot change in the same update as the version check. The check and the bump are the trait: raw SQL that writes the row bypasses both. `conflict` does not say whether the row is stale or gone. A queue delivers at least once, so the handler has to be idempotent. A hot queue whose heartbeat rewrites the row on a short interval fits a table that is not `versioned()`.
- **`sortable()` keeps a dense integer position (D254).** A move is O(n) per group: it rewrites every row in the group. Fractional keys are not used. `one()` is not reordered onto `position`. `via()` is OKM1060. Naming the group column in `set` is OKM1120, including when the value is the one already stored. A delete leaves a gap until the next `move`. Adding `position` to a table that already has rows is `add-column-required`. A position that is already negative is flipped by the next move in that group. The group's advisory lock is its own statement. The max, and a move's renumber, run in the next statement, after that lock is held.

## Typed raw

- **Typed raw SQL scans static strings only (F7-3).** `okm raw sync` reads string literals and `` `...` `` templates with no `${}`. A template literal with `${}` is not scanned, and dynamic SQL stays on the `raw(handle, cls, "read" | "write", fragment)` form. The runtime stale check is a column-count and decode check, not a catalog hash compare: run `okm check` in CI. Typed raw has no archive filter and no hidden-column guard.

## Observability

- **`okmodel/otel` uses the observers that already exist (D267).** `onRoute` becomes a span that starts and ends in that call, so it has no duration. `db.query.summary` is the fingerprint, and it is set from `inspect()`, because the route event does not carry one. Statement text is off unless `statement: true`. Parameters are never attributes. A tenant id is not an attribute. `onError` is an error the caller does not receive, such as `afterCommit`. A query that throws to the caller is not that event. The exception is the error name and the OKM code when the error has one, with no message and no stack. Overlapping top-level transactions pair spans last-in, first-out because the transaction event has no id, and a rollback can be marked on the wrong span.

## CLI

- **`okm dev` opens a database and returns.** With a target named `dev` it prints `target dev`. Otherwise it creates PGlite under `<out>/dev-db` (default `.okm/dev-db`), runs `select 1`, closes it, and prints that directory. It does not watch the schema, does not reload, and does not apply migrations.
- **`okmodel/safety` is an opt-in import.** The startup graph does not load it. Importing `okmodel/safety` registers the final-verification registry (`registerRule`, `verify`, `safety.property`, `registerPresets`). Until a rule is registered, the planner hook is a no-op. Built-in tenant, guarded, and hidden checks still run without that import.

## Not tested

These surfaces exist in the tree and may pass local or labeled jobs, but this release does not claim CI proof for them:

- **Real Neon.** Live Neon checks skip when credentials are unset. CI does not hold those secrets.
- **Native Windows.** The Windows job packs and runs CLI smoke without Postgres. Three surfaces stay unknown. The audit note stays in the repository and is not part of the published package. A full Windows Postgres suite is 0.10.
- **The GitHub Action on real GitHub.** The composite action and its dogfood workflow are in the repository. A sticky plan comment on a real pull request outside that dogfood is not a required gate.
- **Long soak and performance runs.** Kill-storm and topology tests have settle bounds. Multi-hour soak and production-load performance numbers are not gates.

## What works

`.hidden()` stays out of default selects and includes. `.sensitive()` redacts values in logs, errors, `inspect()`, and OpenTelemetry spans. On a table that has a sensitive column, a unique, foreign-key, check, generic driver, or aborted-connection failure keeps the value out of `error.cause` (`detail`, parameters, `args`, `where`, and `internalQuery` stay off), including when postgres.js omits `table` on the error and still attaches `parameters` / `args` on the cause. Tables without sensitive columns keep today's cause. `connect({ errors: { includeValues: true } })` is the explicit opt-in. `one()`, `many()`, `manyThrough()`, `morph()`, and `morphMany()` work. A relation value that is not one of those throws OKM1061.
