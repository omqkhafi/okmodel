# D280 — `okm import drizzle` reuses the pull emitter (P113)

- **Status:** accepted
- **Area:** tooling
- **Supersedes:** none

---

`okm import drizzle <path>` loads that module with the project's own `drizzle-orm`, read through `getTableConfig` and `getTableColumns`. The import runs the file, and the command help says so. okmodel does not depend on `drizzle-orm`. When the package cannot be resolved from the project, the command is OKM1856 and the fix says to install it there. The rows become a catalog and `emitPull` writes one table file per table plus the schema file, the same writer as `okm pull` (D275). An existing file is OKM1855 and nothing is written. `--out` is the other directory. There is no database. SQL names stay. TypeScript fields follow the Drizzle property names, and the table binding follows the export name, via provenance `source` (`field:` and `export:`), which is not part of the catalog hash. A project with no `okmodel.config.ts` writes `schema.ts` and `tables/` in the working directory. Every table in one Postgres schema is imported, and the report's first line is `namespace <name>`. `schema()` still compiles `public`, so a name other than `public` is set with `defineConfig({ namespace })` (D277). Tables in a second schema are listed, not guessed into the one namespace. Printed under `not imported`, and not written: composite foreign keys, `relations()`, custom column types, views, policies, a standalone sequence, a `serial` sequence (`serial`, `smallserial`, and `bigserial` are written as `integer`, `smallint`, and `bigint` not null, without that sequence), and anything `table()` still cannot say. Nothing in that list is dropped without a line. No new catalog kind and no new builder. `drizzle-orm` may be a devDependency for the fixture only. Nothing new is reachable from the runtime entry or from `connect()`. Issue #315
