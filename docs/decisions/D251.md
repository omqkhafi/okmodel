# D251 — Top-N per parent stays one lateral join; window helpers load on the first select that has one (P94)

- **Status:** accepted
- **Area:** product
- **Supersedes:** none

---

Audit of §13 tools 2 and 12: a to-many include already took `orderBy` and `limit`, and the limit was already inside the lateral subquery, so it was already per parent rather than a total. Empty parents already came back as `[]`. The gap was the tie-break: with `orderBy` set, the primary key was not appended, so `LIMIT` on equal keys was not stable. With `orderBy` omitted, the primary key was already the order. The lateral join stays. A window over the whole child set would be the wrong shape and the more expensive one, because an index can stop after N. The primary key is now appended ascending for every primary-key field the caller did not name, on the root lateral and on a nested to-many. `select`, a nested include, a preset, and the tenant predicate compose. `matches` and `relevance` inside the include compose, because the include planner, which already loads on the first include, reports whether a related `where` or `orderBy` needs the operator compiler. The search rewrite is not walked and is not widened. `search` is not an include key. The nested rows are present. The result type names the selected columns of the first include and does not add the nested relation. Tool 12 is `rowNumber`, `rank`, `denseRank`, and `runningTotal` in `select` on `find` or `one`, tagged with `Symbol.for("okmodel.window")`, the same shape as `bucket`. `partitionBy` is optional. `orderBy` is required. `as` is the result key and must not be a column. `rowNumber` and `runningTotal` append the primary key inside the window. `rank` and `denseRank` do not, so a tie stays one rank. `runningTotal` follows the column the way `sum` does, and a text column is OKM1124. The SQL loads from `window.ts` on the first `find` or `one` whose `select` is not all field names. A plain select does not load it. Ordering by the `as` name emits the select ordinal from that chunk. The `orderBy` type stays column names: widening it would sit on the query-200 instantiation path. `page` refuses a window when the call runs (OKM1120). Its type still accepts one, because narrowing `select` on `page` took query-200+page+aggregate+through to 24,937 instantiations and 6,959 types, above 24,792 and 6,931. Leaving the shared select type in place measures 24,424 and 6,923 (368 and 8 under those ceilings). The 8 types are within 3 percent of 6,931.
