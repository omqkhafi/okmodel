# D165 — Opt-in features are objects that carry their own logic (tenancy first)

- **Status:** accepted
- **Area:** runtime
- **Supersedes:** none

---

Wiring column tenancy into `schema()`, the client and the predicate emitter grew the no-tenancy startup graph by 7,178 minified and 1,969 gzip (83,043 / 27,666 to 90,221 / 29,635), five times the stop line, because `schema()` is synchronous and a plain option object (`tenancy: { key, type, strategy: "column" }`) has no code, so all the code had to be static. That would leave 779 / 365 bytes under the cap for P25 to P29. Decision: a strategy is an object imported from its own subpath that carries the logic, as traits do (D163). For column tenancy: `import { columnTenancy } from "okmodel/tenancy"` and `schema({ tenancy: columnTenancy({ key: "tenantId", type: "uuid" }) })`; the object adds the tenant column, widens uniques, builds composite foreign keys, supplies the scope predicate and the `for()` / `unscoped()` client methods, while core keeps only small hooks that do nothing when no tenancy is set. Other strategies (`schemaPerTenant`, `databasePerTenant`) are separate objects in the same subpath later, so an app ships only the one it uses. The same rule applies to archivable, validation, presets and any other opt-in feature of P25 to P29: a plain option object may only select behavior that already lives in core, and anything bigger travels with an imported object. If the redesigned P24 is still over the stop line after one more measurement, it stops again with numbers and the cap becomes a decision with Ali.
