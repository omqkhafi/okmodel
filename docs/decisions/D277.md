# D277 — Several catalogs share a database and not a history (P115)

- **Status:** accepted
- **Area:** product
- **Supersedes:** none

---

`schema()` still compiles `public`. `defineConfig({ namespace })` places the catalog, and apply creates that schema and sets the session search path so `okm_meta` lands there. `public` is unchanged. `connect()` still reads unqualified `okm_meta` and does not see another namespace. That check stays off the startup path. `external(table)` is `withOwner(table, "external")` in its own module, re-exported from `okmodel/pg`. The featureless app does not import it. `okm catalog export` writes JSON from the schema source: `catalogHash` is the physical identity, and `logical` is `namespace`, `name`, and `format` (R5). The file has column names and types. It has no function and no connection URL. `defineConfig({ external })` is one path per snapshot. `okm check` and `okm migrate check` verify each external table when `external` names a snapshot. A `withOwner` mark with no snapshot list stays hands-off. A stale or missing snapshot is OKM1841, with `fieldReason` `stale` or `missing`. A foreign key into another database is OKM1842, kind `invalid`, `fieldReason` `database`. `okm check` lists a cross-catalog foreign key as a `coupling` warning. Keys, relations, codecs, defaults, client id rules, and a sync API stay absent (R1). No new error kind. No catalog hash change for a public catalog. No gate or ceiling moves.
