# D318 — Failed concurrent index cleanup and the empty migrate-check replay (#391 Q4)

- **Status:** accepted
- **Area:** tooling, dialects
- **Supersedes:** none

---

Issue #391. A failed `CREATE INDEX CONCURRENTLY` is dropped before apply returns, so the target does not keep an INVALID index. Cleanup reads `pg_stat_activity` for another session whose active query is `CREATE INDEX CONCURRENTLY` of this index name. A build of a different index on the same table is not that session. When a matching build is still active, the drop is not run. When the drop fails, the error names the index and `DROP INDEX CONCURRENTLY`, and the fix is `DROP INDEX CONCURRENTLY <index>. Then run apply again. Finished steps are not repeated.` A later apply still treats `indisvalid = false` as partial, drops the leftover index, and rebuilds it. A lost connection names the index that may be INVALID. `okm migrate check` prints, after `ok N migrations`, that the replay uses empty tables and does not catch a step that fails only on real data: `NOT NULL` on a populated column, a unique index over duplicates, a check over existing rows, a foreign key validation, or a cast. No new ErrorKind. No catalog hash change. No gate move. Issue #391
