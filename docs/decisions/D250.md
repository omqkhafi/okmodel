# D250 — `find` and `count` take `search` (P97)

- **Status:** accepted
- **Area:** product
- **Supersedes:** none

---

`find({ search })` and `count({ search })` match a column built for search. A string is enough when the table has one such column. `{ for, in, match, language }` names the text, the column, how to match, and the language. `in` is required when there is more than one, and the error lists those columns by name. `match` is `natural` (the default, web-search style), `all-words`, `phrase`, or `advanced` (raw syntax). An omitted language uses the database default. `find` returns the closest rows first, then the primary key. An `orderBy` you pass replaces that order. `count` does not order. `search` combines with `where`, `select`, `include`, and presets. `page` refuses `search` in this version (OKM1120). `one` and `exists` do not take it. `matches(q, { match, language })` stays in `where`. `{ mode, config }` is not accepted. `relevance(q, { match, language })` is the `orderBy` form. `search` stores the same operand as those helpers (`searchValue`) and the SQL reader is the one they already use, so the text is the same. The rewrite loads from `text-search.ts` on the first call that passes `search`. That chunk does not import `matches.ts` or `relevance.ts`, so the featureless app still shakes both. Errors name what you passed and what to do. They do not name the column type, except the raw syntax under `advanced`. Highlighted snippets, a search of a plain text column, a helper that fills a search column from text, and keyset pages ordered by relevance are not built. A named query is a preset or a function that returns `find` options. No new error kind. No catalog hash change. No gate move.
