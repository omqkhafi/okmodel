# D337 — Session timeouts only on a checked direct connection; holders are named by a second session

- **Status:** accepted
- **Area:** product
- **Supersedes:** none

---

A session `lock_timeout` and `statement_timeout` is set only on a connection that passed the pid probe (D215), and `directSession().end()` puts the values back and reads them again before the connection is released. Behind `--allow-pooler` nothing is set on the session (it would be lost or reach another client), each transaction scopes its own timeouts, and a step that cannot share a transaction (`CREATE INDEX CONCURRENTLY` and similar) is refused with OKM1854 before it runs. The apply connection is named `okm apply` through `application_name` in the driver URL, unless the URL names one, so no adapter changes. While an attempt waits, a second session opened on first use runs one catalog query over `pg_blocking_pids`, `pg_stat_activity`, `pg_locks`, and `pg_prepared_xacts` and keeps the last answer. Holders are `okm-apply`, `autovacuum`, `prepared-transaction` (pid 0), `idle-in-transaction`, `active`, or `other`. A holder that appears only after a very short `--lock-timeout` may be missed, and the message then says it could not see who holds the lock. Behind `--allow-pooler` no holders are named. Nothing cancels or ends a session that is not ours. Issue: none filed
