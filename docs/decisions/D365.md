# D365 — A single-file connect bundle keeps the catalog compiler

- **Status:** accepted
- **Area:** runtime
- **Supersedes:** none

---

Amends D360 and D363. `assertCompatible` in `src/runtime/drift.ts` still imports `catalog-compile.ts` when `okm_meta` has a hash and the call has no catalog artifact and no `catalog.hash`. A single-file bundle inlines that import. Before #740 the same path threw OKM1020, so a bundled `connect` to a migrated database failed. Keeping the import is the choice: a connect that works in every bundler beats about 31 KB. There is no new API for it. `armCatalog()` stays the hatch for a direct `.catalog` read. An artifact (`connect({ catalog })`, or `.okm/catalog.hash` with `catalog.json` from `okm build`) skips running the compiler. It does not remove the compiler from the file. The startup graph still stubs dynamic imports, so `catalog-compile.ts` stays off that gate (D360). Sharing a module with `schema()` would pull the compiler's dependencies into that chunk. `enumType` lives in `src/contracts/catalog/enum-type.ts`, and the compiler imports `identityKey` from `identity-key.ts`, so `object.ts`, `identity-key.ts`, `json.ts`, and `types.ts` stay with the lazy compiler. The stubbed source list matches the full startup graph. The pull-request size report prints the single-file bundle and the metafile inputs that contain the compiler. It does not gate them. Method: `bun build scripts/app-connect-bundle.ts --target=bun --minify` (single file, gzip level 9, metafile) on Bun 1.4.4. Review of #740, `fdc0500` to `ad6732f`: 423,571 bytes (gzip 131,254, 150 inputs) to 454,535 (gzip 140,245, 161 inputs), +30,964 minified and +8,991 gzip. At `ad6732f`, `src/dialects/pg/catalog-compile.ts` was 15,500 bytes and was one of those inputs. The same method on this tree, entry `scripts/app-connect-bundle.ts`, measures 454,502 bytes, gzip 140,010, 162 inputs, and the compiler input is that file. No new `ErrorKind`. No catalog hash change. No public field. Issue: none (PR only)
