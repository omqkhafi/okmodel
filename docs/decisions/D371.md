# D371 — A stop inside the watch handler does not wait for itself

- **Status:** accepted
- **Area:** runtime
- **Supersedes:** none

---

Amends D368. `stop()` from outside the subscription still marks the watch stopped and waits until the handler, `onError`, and query already running have finished. After that wait, nothing from that watch runs. A `stop()` from inside that subscription's own handler or `onError` does not wait for the call that contains it: it marks the watch stopped, drops the timer, the pending wait, and the hub registration, and resolves. The running handler finishes, and nothing from that watch runs after it. The two callers are told apart with `AsyncLocalStorage`, loaded by `import("node:async_hooks")` when a watch is opened or on the first `stop()`, so the startup graph does not gain a source. A runtime without `AsyncLocalStorage` keeps the outside wait for both callers, and the watch page says to abort the `signal` option from inside the handler. Handlers gain no new argument. Poll-mode subscriptions still pass epoch 0 into the shared read. No new `ErrorKind`. No catalog hash change. No public field. Issue: none (PR only)
