# D371 — A stop inside the watch handler does not wait for itself

- **Status:** accepted
- **Area:** runtime
- **Supersedes:** none

---

Amends D368. `stop()` from outside the subscription still marks the watch stopped and waits until the handler, `onError`, and query already running have finished. After that wait, nothing from that watch runs. A `stop()` from inside that subscription's own handler or `onError` does not wait for the call that contains it: it marks the watch stopped, drops the timer, the pending wait, and the hub registration, and resolves. The running handler finishes, and nothing from that watch runs after it. The two callers are told apart with `AsyncLocalStorage`, read synchronously from `process.getBuiltinModule("node:async_hooks")` when a watch is opened. There is no `node:` import. The package floor is Node 22.18, and `getBuiltinModule` has been synchronous since Node 22.3 (and 20.16), so the oldest supported Node has it. Bun, Deno, and workerd with `nodejs_compat` have it too. A runtime without the method keeps the outside wait for both callers, and the watch page says to abort the `signal` option from inside the handler. The startup graph does not gain a source. Handlers gain no new argument. Poll-mode subscriptions still pass epoch 0 into the shared read. No new `ErrorKind`. No catalog hash change. No public field. Issue: none (PR only)
