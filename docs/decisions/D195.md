# D195 — A backfill is a batched step in the migration file, and apply runs one target

- **Status:** accepted
- **Area:** product
- **Supersedes:** none

---

A `backfill` step stays plain SQL. The header is `-- backfill table=<table> key=<col[,col]> batch=<n>`. `$1` is the exclusive lower bound and `$2` is the inclusive upper bound; null opens that side. The runner finds each boundary with a keyset query on the primary key, including a composite key and `uuid`, and never with `count(*)`. The statement is idempotent. Planner output for a D131 removal and for the volatile-default fill uses `where` the old value or `where` the column is null. A table with no primary key is OKM1546 at plan time. There is no `backfill()` export and no `okm backfill` command. Apply runs the step outside the migration transaction, one transaction per batch, under `statement_timeout` and `lock_timeout`, with the existing lock-timeout retry and a pause between batches. Defaults are `defineConfig({ backfill })`: 1,000 rows, no pause, 30 seconds. `batch=` overrides the batch size. Each committed batch writes `okm_backfill` on the target; apply creates that table if it does not exist. A finished step is still an `okm_history` row. `okm_history` is not changed. A rerun resumes from the stored key. A protected target is refused on every batch unless `--allow-protected`. Column tenancy is one pass; tenant iteration is M5. `TargetRunner` takes one target, its units, retries, and checkpoints, and returns a per-target report. `okm migrate apply` calls it with a list of one. Bounded concurrency, canary, class flags, and the control database are M5. The row estimate is not stored. No byte moves on the runtime entry, the featureless app, or the connect entries, and no type-cost ceiling moves. Found in P52. Issue #80
