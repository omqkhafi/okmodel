# D316 — A NOT VALID not-null constraint is its own state in introspection (PG18)

- **Status:** accepted
- **Area:** product
- **Supersedes:** none

---

PostgreSQL 18 accepts `ADD CONSTRAINT … NOT NULL col NOT VALID`. `attnotnull` is then true while rows with NULL may exist. Introspection (`COLUMNS`, `OUTSIDE_COLUMNS`) reads the `pg_constraint` row (`contype` `n`, `convalidated` false) through one expression, `unvalidatedNotNullSql` in `src/dialects/pg/not-null.ts`, which `src/tooling/describe/nullability.ts` also uses (no describe code enters the dialect). A column with such a constraint is `nullable: false` and carries the new optional `ColumnDefinition.unvalidatedNotNull`, the constraint name. The field is absent for every other column, so the serialised document and the catalog hash of every existing catalog are unchanged; `withUnvalidatedNotNull` (`src/contracts/catalog/not-null.ts`) sets it, only on a NOT NULL column, and sits outside `column()`; the document reader and the rename helpers keep it. A schema cannot declare it. 15 through 17 have no such row: the expression is NULL and nothing changes. Consumers: **plan** (`okm push`, `generate`, apply, `okm check`, the migrate-check replay) compares the field as part of the column definition. Schema NOT NULL against an unvalidated live constraint is one step, `ALTER TABLE … VALIDATE CONSTRAINT "name"`, kind `validate-constraint` (class expand, `SHARE UPDATE EXCLUSIVE`), the existing step class and lock of the check and foreign-key `NOT VALID` / `VALIDATE` pair (`safe.ts`). Schema nullable against it is `DROP NOT NULL`, which removes the constraint. There is no rewrite through a temporary check: that path is for adding NOT NULL. The linter reports the step as OKM1531 with the reason `validates a NOT NULL constraint`, because a stored NULL makes it fail. **drift** (`okm check`) reports it through the plan as OKM1520 and adds one line per column, `<table>.<column> is NOT NULL NOT VALID (<constraint>) in the database; rows with NULL may exist.`, even when no row holds NULL: the constraint is still weaker than the schema. **pull** declares the column `.nullable()` with a comment naming the constraint and lists it under `not validated` in the report. A plain `notNull` would claim what the data may violate. **export** (`okm catalog export` snapshots come from the schema source and do not change) and the live check of a dependent catalog read the column as nullable and name the constraint in the OKM1841 message. **describe** is unchanged (F7-1). Not done: introspection still does not record `convalidated` for check and foreign-key constraints, so a `NOT VALID` check or foreign key reads as validated (follow-up, not in this change). No new code, ErrorKind, or catalog hash change for an existing catalog. The new field is an additive optional property on the exported `ColumnDefinition` type. The startup graphs do not move (featureless app 88,437 / 28,440 and the runtime entry 5,288 / 2,026, both as before). No decision is reversed. Issue: none filed (see the pull request)
