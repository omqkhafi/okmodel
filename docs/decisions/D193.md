# D193 — Safe rewrites run only on a table that already exists

- **Status:** accepted
- **Area:** product
- **Supersedes:** none

---

On a table present in the before-catalog, the planner emits the safe form. A table created in the same plan keeps the plain statements. An index is `CREATE INDEX CONCURRENTLY` or `CREATE UNIQUE INDEX CONCURRENTLY`, and a drop is `DROP INDEX CONCURRENTLY`, outside a transaction, lock `SHARE UPDATE EXCLUSIVE`. A check or foreign key is `ADD CONSTRAINT … NOT VALID` then `VALIDATE CONSTRAINT`. Postgres documents `SHARE UPDATE EXCLUSIVE` for validate, plus `ROW SHARE` on the referenced table for a foreign key, and `SHARE ROW EXCLUSIVE` on that table when the foreign key is added. `SET NOT NULL` adds `CHECK (col IS NOT NULL) NOT VALID` under a generated name, validates it, sets not null, then drops the check. A volatile default (`gen_random_uuid()`, `uuidv7()`, or a catalog function marked volatile) adds the column nullable, sets the default, fills existing rows with one `UPDATE` (batching is P52), then that not-null sequence when the column is required. The fill is a backfill action, so a protected target refuses it unless `--allow-protected`. The `SET NOT NULL` of that new column stays kind `add-column`, so the plan stays expand. A stable or constant default, and a call the catalog cannot classify, stay a plain `ADD COLUMN`. A unique constraint or primary key builds the unique index concurrently, then `ADD CONSTRAINT … USING INDEX`. Brief `ACCESS EXCLUSIVE` steps run under the existing `lock_timeout` retry. Resume of a failed concurrent index drops the invalid index (`pg_index.indisvalid`) and rebuilds, and does not repeat a finished step. OKM1534, OKM1535, OKM1536, and OKM1537 are errors and fire only when the SQL is not this form. OKM1538 stays a warning. A validate that follows `widen-check` does not fire OKM1531. OKM1706 and OKM1823 stay declaration-time and are not copied into the linter. No gate, cap, or ceiling moves. Found in P50b. Issue #123
