# D169 — P25 stops over its allowance; archivable reuses the tenancy rewrite and carries its methods

- **Status:** accepted
- **Area:** runtime
- **Supersedes:** none

---

`archivable()` works and its tests pass on real Postgres, but the featureless startup graph grew to 87,449 / 28,944 (+2,093 / +583 over 85,356 / 28,361), against an allowance of 1,100 / 320 (D162 stop line). Where it sits: entry chunk +577 (schema slots for cascade checks and partial uniques), main chunk +1,516 (about 878 for `archive`, `restore`, `withArchived`, `onlyArchived` and the OKM1052 throw, about 280 for the active-set predicate in the planner, the rest the scope helper and inspect slot); the archive statement builder is a separate 7.4 KB lazy chunk and not counted. Accepting this would leave 3,551 / 1,056 for P26 to P29 (about 888 / 264 each), too little for transactions and relations extras. Decision: one redesign, no cap change. (1) The partial uniques and the cascade checks move into the object's `apply` and run in the same single rewrite pass tenancy already uses (D166), so core adds no schema slots. (2) `archive`, `restore`, `withArchived`, `onlyArchived` are supplied by the object through one generic table-handle hook shared with tenancy's `for()` / `unscoped()`, not written in core; OKM1052 is thrown by the lazy execution chunk. (3) Only the active-set predicate stays in the planner, next to the tenant predicate, because every statement passes there. Allowance stays 1,100 / 320. If the redesign is still over, it stops again with numbers and the choice (accept, or raise the cap) goes to Ali; Cursor does not decide it. The connect entries crossed their gates in this attempt (postgres.js 40,537 / 14,093, PGlite 38,246 / 13,473, `pg` 41,212 / 14,374, Bun.sql 40,113 / 13,934); gates move only under D160 at the final numbers, and only if they still exceed the old gate after the redesign. The 200-table query probe is 6,967 of 7,100 (1.9% under, inside the 3% watch). Found in P25
