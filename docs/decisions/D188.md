# D188 — P39 closes with no code change; sync contracts stay sync

- **Status:** accepted
- **Area:** product
- **Supersedes:** none

---

P39 measured the startup graph and stopped at its own stop line: no lazy move saves 200 gzip bytes on the entry without turning a synchronous call into an asynchronous one. The candidates and their gzip effect on the featureless app (connect entries in brackets): catalog build cluster -5,017 (not in connect), `sha256` -1,493 (-175), `array-literal` -608 (0), `nearest` -401 (-403 postgres.js, -399 PGlite), `words` (reserved words) -403 (-451, -432), `filters` -226 (0), `enum` -158 (0; entry file -178). Every one except the `enum` hook sits behind a call that is synchronous today (`schema()`, `.catalog`, `throwNamed`, `fitIdentifier`, `filters()`, `.array()`, `assertIdentifier`), and `plan.ts` and `client.ts` are the plain `find` path whose `sql()` and `inspect()` return values, not promises. Decision: those calls stay synchronous. `schema()` building and validating at call time, and failing at the call site, is part of the contract (D138, D162); a lazy chunk would make it a promise. No gate, cap or ceiling moves. The connect headroom stays at 11 bytes (postgres.js) and 8 bytes (PGlite) and is not widened in advance: 0.3 features load as lazy chunks behind opt-in objects (D162 to D165, D171) and must leave the featureless startup graph and every connect entry unchanged; a step that cannot do that stops with exact bytes and the cap question goes to Ali. The `enum` registration hook (-158 / -178) is not worth a step by itself and is taken only if a later step already touches `enum.ts`. P39 has no issue and no branch. Found in P39
