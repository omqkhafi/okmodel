# D223 — The extra tenant unique keeps its TypeScript name key (P81, QA-L4)

- **Status:** accepted
- **Area:** product
- **Supersedes:** none

---

The unique beside a tenant table's composite primary key is required by §9.2 and is not dropped. Tenancy stores it under the object key `{declared primary fields joined by _}_{tenant field}`, and the columns are those fields plus the tenant field. The constraint name is `{sql table}_{that key}_key`. Table `tasks`, casing snake, primary field `id`, tenant field `tenantId`: `tasks_id_tenantId_key` on `(id, tenant_id)`. The primary key is `tasks_pkey`. A column `.unique()` uses the TypeScript field alone, so `title` is `tasks_title_key` on `(tenant_id, title)`. An index uses SQL names, so `(tenant_id, title)` is `tasks_tenant_id_title_idx`. `archivable()` runs after tenancy and turns those uniques into partial unique indexes. The index name key is the SQL column names joined by `_`, so the same primary columns become `tasks_id_tenant_id_idx` with predicate `(archived_at IS NULL)`. `renameTable` and `renameColumn` keep the stored constraint name and nameKey. The new schema compiles the name from the current TypeScript fields. The planner pairs the same shape, ignoring nameKey, and emits `RENAME CONSTRAINT` when the name changed. `tasks` renamed to `items` renames `tasks_id_tenantId_key` to `items_id_tenantId_key`. Field `id` renamed to `taskId` with `.renamedFrom("id")` renames the column to `task_id` and the constraint to `tasks_taskId_tenantId_key`. Neither path drops the constraint. A name key made of SQL names would change `catalogHash` for every existing tenant table and plan a rename. The generator is unchanged.
