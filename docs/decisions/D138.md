- **Status:** accepted
- **Area:** ci

After D137's lazy loading, the app-fixture gate measures the startup graph (what loads before the first successful query: 72,669 min / 23,980 gzip, gate 74,688 / 24,000); the total graph with the lazy chunks is reported next to it and not gated, so a lever cannot hide bytes. P15B may add at most 12,000 / 3,800 over that gate (86,688 / 27,800). The app fixture's CI cold import (34.4 ms; earlier samples 31 and 20.7 ms, 10.2 ms local) includes `schema()` work at import (pure-TS SHA-256, catalog build) and CI variance, so it is printed and not a failure; the 25 ms CI gate (D134) stays on the runtime entry and any local app figure above 15 ms is a finding. Lever recorded for P16: compute the catalog hash and serialisation lazily on first use instead of inside `schema()`, evaluated together with the fast catalog loader. First-include latency (dynamic import plus planning) is reported from P15B. Named prepares ship as the option `prepared: "named"` (43 to 70% faster at p50 over a direct connection, about 110 bytes min); unnamed stays the default, and the docs must say named statements are not for transaction-mode poolers.
