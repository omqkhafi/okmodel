# D184 — P30 follow-up accepted; two findings go to 0.2.1

- **Status:** accepted
- **Area:** product
- **Supersedes:** none

---

The follow-up commit (`11310fd`) makes `batch` refuse `restore` and any write with `expect` (OKM1121, before any statement), adds `batch-refusals`, `snapshot-reads`, `raw-sql-paths` and `codes-not-reached` tests, and fixes the spec text for OKM1110, OKM1191 and OKM1702: each is not thrown in 0.2 (the one engine-dependent feature `uuidv7()` is OKM1812 when `requires` is declared; every read is one statement; no public runtime path takes raw SQL, enforced by a test that fails if one appears). Featureless app 88,938 / 29,770 (no change), gates and cap unmoved. Two findings are not release blockers and go to a 0.2.1 patch, tooling-only so no runtime bytes: (1) `t.id()` defaults to `uuidv7()`, and on Postgres 15 to 17 with `requires` undeclared the DDL fails with the raw driver error `function uuidv7() does not exist` and no OKM code. The migration tooling (`okm migrate apply` / `check`, which read the server version) raises OKM1812 with the fix (`requires`, or `t.id({ default: "uuidv4" })`) before running DDL; nothing is added to `connect()` because the connect gates have 9 and 6 gzip bytes left. Until then it is a known limit and the README already says the default needs Postgres 18. (2) The types accept `restore` and `expect` inside `batch`; only the runtime refuses. Narrowing the types costs probe instantiations; it is measured in 0.2.1 and done only if it stays inside the probe ceilings, otherwise it stays runtime-only and documented. Found in P30 follow-up
