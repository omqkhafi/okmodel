# D329 — A plan read against a target keeps the offline plan, and every optional read of the target is bounded

- **Status:** accepted
- **Area:** product
- **Supersedes:** none

---

Decided with Ali on 2026-11-21 after the audit of #709. **Live compare.** A plan with a reachable target seals both catalogs to the server's check text. A sealed picklist reads `= ANY (ARRAY[...])`, which the picklist planner does not parse, so the reachable plan lost `backfill-expand` and `backfill-contract` that the offline plan (D131, D195) writes. The sealed plan now passes the authored catalogs along (`PlanRequest.authored`). The picklist planner reads the authored text, so a reachable and an unreachable target give the same steps and the same SQL. **D301 amended.** OKM1531 also exempts the planner's own `ADD CONSTRAINT … NOT VALID` then `VALIDATE` of a picklist swap (`narrow-check`) when a `backfill-expand` or `backfill-contract` step on the same table sets that column earlier in the same migration and no other write on the table follows it. A `VALIDATE` with no such backfill, a write in the gap, a backfill of another column, and every other validate stay OKM1531. **Optional reads.** `okm generate` and `okm migrate plan` read a target only to seal catalogs and to print row estimates. Neither read decides a step, so each uses a 3 second connect timeout (`OPTIONAL_CONNECT_SECONDS`), and a connection failure, a connect timeout, or a missing `postgres` package skips it. A skipped read prints one line on stderr, `note: I could not reach the target, so this plan has no row estimates and no live comparison.` (D330 rewords the sentence), once per command, in a human run only: `--json` drops it so the envelope and a merged stream are unchanged. A server refusal such as a bad password still throws. Exit code and stdout are as before, and D194 stands: an unreachable target prints the offline lock and does not fail. A closed port fails at once. **First migration.** A plan against an empty previous catalog has nothing to compare with and never connects, so `okm generate init` needs no driver; `apply`, `check`, and `pull` keep their error for a missing `postgres` package. **OKM1510 text.** The fix `okm generate` prints names each code that fired and its safe form, and says an acknowledged override is a `-- okm-allow CODE: reason` line that `okm generate` writes when you answer its question in a terminal (D323). The registry text of OKM1510 says the same. Tooling only. No public API, `ErrorKind`, exit code, flag, or catalog hash change. No gate or ceiling moves
