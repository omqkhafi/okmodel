# D269 — Neon is two modes on one entry, with its own connect gate (P107)

- **Status:** accepted
- **Area:** adapters, runtime
- **Supersedes:** none

---

`okmodel/pg/neon` uses `@neondatabase/serverless` as an optional peer. It is not a runtime dependency. `mode: "websocket"` is the default: a pool, `transactions: "interactive"`, unnamed prepared statements. `mode: "http"` is one request per statement, `transactions: "batch"`, and `prepared: "none"`. `batch()` is the HTTP transaction. `tx()` on HTTP is OKM1111. Neither mode streams, listens, cancels, or describes. A positive `timeout` is OKM1120. A transaction-mode pooler does not promise session state. With one small compute this pooler reused a backend, so a custom `SET`, `LISTEN`, and `PREPARE` stayed visible on the next statement, and a second connection saw the `SET`. That reuse is not a guarantee. `connect` returns a promise for a string, a pool, and a topology. A read replica can lag the primary. `route: "replica"` stays on a replica, and a miss stays a miss. `okm driver test neon` marks COMMIT loss `unsupported` (`no socket to cut`): the harness cut is a TCP relay, and this driver speaks WebSocket or HTTP. A result that never arrives is still `outcome_unknown` (OKM1401). Live checks skip when the credentials are unset.
