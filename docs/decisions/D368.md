# D368 — Watch epoch, stop, truncate, and an unreachable canary

- **Status:** accepted
- **Area:** runtime, dialects, tooling
- **Supersedes:** none

---

A live read is shared only with a flight that started at the current wake count. The hub increments that count when a notification wakes a subscription, and again when a listen connection reconnects. A flight started earlier is not joinable, so a wake is never answered by rows read before it. Identical subscriptions still share one query when no wake lands during the read. A different scope does not share. `stop()` marks the subscription stopped and then awaits the handler already running, including the throttle wait it started. After that await, no handler, `onError`, or query from that subscription runs. A thrown handler still settles `stop()` and goes to `onError`.

A watched table installs four statement triggers: insert, update, delete, and truncate. They call one function. Truncate carries no transition table. A tenant function notifies `''` for truncate before it reads `okm_new` or `okm_old`. The names stay in the `okm_watch_` family, including introspection and drop.

An unreachable canary stops later stages before any other database is migrated. The run reports it unreachable and exits 5 when that is the only problem. `plan --fleet` records the canary name and does not rewrite it on apply. When that named database is unreachable, apply uses the smallest reachable database that is still behind or failed, and the report names both and says why. Fleet drift uses the fleet's 30 second first-connect timeout. No new `ErrorKind`. No catalog hash algorithm change. No new OKM code. Issue: none (PR only)
