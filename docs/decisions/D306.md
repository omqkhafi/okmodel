# D306 — Tenant indexes lead with the tenant key (Q3)

- **Status:** accepted
- **Area:** product
- **Supersedes:** none

---

Decided with Ali on 2026-10-18. Three levels, nearest wins. `indexes` on `columnTenancy()`, `compositeTenancy()`, and `rlsTenancy()` defaults to true and prepends the tenant key (the first key, for composite) to every index on a tenant table. `tenantIndexes: false` turns that off for one table. `.global("reason")` opts one index out; an empty reason is OKM1060. `.scoped()` opts one index in. An index that already leads with the key is not prepended twice. A `using …` tail is not rewritten. A unique index becomes unique per tenant, so two tenants may share a value. The catalog, `okm generate`, and `describe()` show the resolved columns. OKM1706 stays when prefixing is off for that index. An existing table whose index columns change is `CREATE INDEX CONCURRENTLY`, then `DROP INDEX CONCURRENTLY` — not a blocking rebuild. Indexes that already lead with the key do not change, so that project sees no migration. No new ErrorKind. No catalog hash change for a schema whose indexes already lead with the key. Issue #390
