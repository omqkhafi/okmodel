# D299 — `okm migrate baseline` adopts an existing database

- **Status:** accepted
- **Area:** tooling
- **Supersedes:** none

---

Tooling only. `okm migrate baseline` and `baseline(target)` from `okmodel/migrate` record the head snapshot as applied history on a live database without DDL. Before writing, the command introspects the target and plans managed objects against the head catalog. A difference is OKM1858 and prints the plan that would reconcile them; nothing is marked applied. Objects present in the database and absent from the model (other tables, triggers, extensions, functions, and the same kinds) are listed as unmanaged, never dropped or altered, and appear in the human report and in `--json`. A target that already has OKModel history is OKM1857. A repeat on the same `baselined@<migration id>` and catalog hash is a no-op (`already baselined`). The history mark is `baselined@<id>`; status and apply treat it like `provisioned@`. The operation is `history-repair`, so a protected target needs `--allow-protected`. `--dry-run` prints what would be recorded. Writes only `okm_meta` and `okm_history` (and creates those tables when absent). No new ErrorKind. No catalog hash change. No runtime-entry or featureless-app gate move. Issue #368
