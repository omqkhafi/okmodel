# D366 — Fleet migrations: one config key, canary then groups, state in each database

- **Status:** accepted
- **Area:** tooling
- **Supersedes:** none

---

`fleet` on `okmodel.config.ts` is the only fleet key. There is no `fleets` map. A target is `{ name, url, tags? }`, from an array, an async function, or an env list. Regions are `groups` and `tags`. The runner is the CLI and `applyFleet` / `ensureHead` on `okmodel/migrate`. There is no daemon and no central registry. Each database keeps `okm_meta` and `okm_history`. Re-running is the retry.

Defaults: the canary is the smallest database that is still behind or failed (size comes from the status pass), then everyone else at parallel 4 and per host 2, stopping at the first migration failure. A failed canary stops later stages. `maxFailures` is `0`, a count, a percent of started targets, or `"all"`. Unreachable is not a failure. A percent or a count lets running targets finish and starts no new ones. Exit 4 is the contract gate (OKM2211), exit 1 is any migration failure, exit 5 is only unreachable, otherwise 0.

`plan --fleet --out` writes `okm.fleet/1` with heads and steps and no URLs. `apply --plan` refuses a database whose head changed (OKM1933). A blocking or rewrite step caps per host at 1. A contract step is refused unless every target, counting unreachable as behind, already has the previous expand, or `--allow-protected` is set for the fleet. Per-target protection, fill, lock-wait, and the direct-URL rule stay on the single-database apply path.

D105's rollout flags (`--canary`, `--concurrency`, `--class`, a default of three failures) are not this API. Schema-per-tenant, `dbFor(name)`, and a hosted registry are out of this decision. No public `ErrorKind` change. No catalog hash change. Issue: none (PR only)
