# D185 — P31 (0.2.1) accepted; batch types stay runtime-only; apply-time engine check

- **Status:** accepted
- **Area:** runtime
- **Supersedes:** none

---

`okm migrate apply` and `okm push` scan the migrations for `default uuidv7()` before any statement (after the advisory lock, before `okm_meta`) and ask the server for its version only when a hit exists. On Postgres 15 to 17 without a `uuidv7()` function it stops with OKM1812 and creates nothing; the message names the column, the migration, the server version and both fixes (`schema({ requires })` on 18, `t.id({ default: "uuidv4" })`). A server below 18 that already has its own `uuidv7()` function is accepted, so 0.2.1 does not refuse a setup that worked in 0.2.0; a function created inside the same migration run does not count. The scan reads every migration passed to apply, not only unapplied ones (the result is the same). Code is in `src/tooling/migrate/engine.ts`; nothing in `connect()` or the runtime entry, featureless app and every connect entry +0 / +0. `okm migrate check` does not exist in 0.2 (P53A); when it lands it calls `assertUuidV7Available`. Batch types: narrowing so the compiler refuses `restore` and `{ expect }` in `batch` was measured and is not built. The full form (second overload per write) moves `query-200-validate` to 27,366 against a ceiling of 25,631; the one-generic form moves `query-200` to 18,443 against 17,300; the brand-only form (+2 / +1) covers `restore` and `.expect(n)` but not the `{ expect }` option. Decision: runtime-only stays; the half-enforced brand is not built, because a rule that looks enforced and is not is worse than a documented runtime rule. A printed `query-200+batch` probe row (no ceiling) is added. Headroom correction: the connect gzip gates have 11 bytes (postgres.js, 14,589 of 14,600) and 8 bytes (PGlite, 13,972 of 13,980), not the 9 and 6 of D184 (those were computed from the earlier D181 figures).
