# D140 — P16 outcomes: config import path, enum as a catalog object, composite probe ceiling

- **Status:** accepted
- **Area:** dialects, contracts
- **Supersedes:** none

---

(1) `defineConfig` is exported from `okmodel/migrate` (tooling), not from `okmodel`, so tooling stays out of the runtime bundle; spec §3.1 now imports it from there, and P17 reviews every public subpath name before the 0.1 freeze. (2) Enum is a catalog object, not a side channel: kind `type` (identity `(namespace, name)`, already in the §5.7 table), ordered labels in the canonical definition, a dependency edge from each column that uses it, introspection from `pg_type` and `pg_enum`, planning with `CREATE TYPE`, `ADD VALUE` as a marked non-transactional step and the D131 recreate for removal. P16 stored labels in `.okm/declarations.json` and `schema().catalog` still raises OKM1020 for an enum column, so `t.enum` does not work end to end; a new step P16A, before P16B, fixes it and removes the side channel. (3) The query composite probe on 200 tables (find, filter, include, orderBy and writes) now has its own types ceiling of 7,100 (measured 6,478, about +10%), separate from the inferred-schema baseline (5,199 of 6,500, unchanged); any prompt that grows it by more than 3% reports it, and instantiations stay under 17,300; further growth is by decision (D133). (4) The lazy catalog hash is accepted as sound design, but P16 did not measure a before and after (CI app cold import 25.2 ms, local 10.1 ms against 2.1 ms for the runtime entry), so P17 profiles app cold import by module and fixes the largest item. (5) Type cost of emitted types is measured on the real output of `okm build` in P16A (consumer ceiling 700, D133). Found in P16
