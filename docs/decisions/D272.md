# D272 — A client-generator id can be supplied with `{ allow: ["id"] }`

- **Status:** accepted
- **Area:** runtime
- **Supersedes:** none

---

Adopts the P100 proposal for one call shape. `insert({ id, name }, { allow: ["id"] })` writes that id and does not run the generator for that row. Without `allow`, a supplied id stays OKM1190. A list row that omits `id` is still generated. The same id again is `unique` (`23505`) unless `onConflict` is set. `allow` does not open a database default (`gen_random_uuid()`, `uuidv7()`): the runtime is OKM1190. Update does not change the key. A primary key with no client fill stays refused when named in `allow`, including `.primaryKey().guarded()`. A guarded field that is not the key still opens. The list overload adds optional `id` only when `allow` is exactly `["id"]`. A longer list does not open `id` in the type. The single-row `{ allow }` overload is unchanged. The type may still accept `allow: ["id"]` on a database-default id; that is a known limit, and the row type gains no flag. The generic list overload, the same `Partial<Pick<Row, Allow>>` as the single row, is not built: on the spike it was query-200 17,252 / 6,379, extensions 17,286 / 6,499, composite 24,449 / 6,933 (2 types over 6,931), validate 25,721 / 6,604 (90 instantiations over 25,631), presets 19,367 / 7,258, and tx 24,457 / 7,054. The check lives in `write.ts`, which loads on the first write. No new error kind. No catalog hash change. No gate or ceiling moves.
