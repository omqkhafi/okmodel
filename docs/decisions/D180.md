Presets are in (PR #109, 0.2.0-next.19): featureless app 88,723 / 29,553 (+330 / +168 over P27b, inside the stop line of +600 / +180), runtime entry 5,288 / 2,026 (unchanged), connect entries 40,695 / 14,390 (postgres.js), 38,455 / 13,763 (PGlite), 41,419 / 14,668 (pg), 40,320 / 14,243 (Bun.sql), all under their gates; no gate, cap or probe ceiling moves. `query-200` is 17,062 / 6,259 (+143 / +40) under 17,300 / 7,100, `query-200-validate` 25,031 / 6,452 and `query-200+page+aggregate+through` 24,212 / 6,770 under their ceilings. How it is built (D162 to D165, D171): the core only records a chain (`tasks.pending().ownedBy(id)` is a linked list of `[before, name, args]` on the handle) and dispatches to a lazy `presets.js` chunk when a statement is planned; reads, writes and archive each import it only when the chain is not empty, and the planner accepts one private tagged operator, `and`, which joins the caller's `where` and the presets' predicates after the tenant predicate and the active set. Choices made, accepted: (1) the builder has one method, `where`; `or([...])` goes inside it, and there is no method that removes or replaces a predicate (D125, D126). (2) A preset does not count as the filter `update` and `delete` require; `where` or `.all(reason)` is still needed (OKM1102), and `archive` and `restore` follow. `insert` ignores the chain. (3) OKM1040 is reused for a duplicate name (table and trait, or two traits), and its fix names both sources. (4) A reserved name is a type error in `table()` and `trait()`, OKM1040 in `trait()` when built, and OKM1040 for a table at `connect()` before the first query, not in `schema()`: the check needs the 23-name list in the startup graph, which measured +530 / +166 on top of the dispatch and would pass the stop line. (5) `inspect()` names the preset, the fields it filters, who defined it and where; it does not print predicate text, because values are parameters; `sql()` holds the predicate. (6) A preset read's `sql()` and `inspect()` are asynchronous, because the chunk loads when the statement is planned. (7) A table's own presets are typed on the table's declared columns, not on columns a trait adds. (8) `PresetQuery` is exported from `okmodel/pg`, and `registerPresets()` from `okmodel/safety`. Found in testing and fixed: `aggregate` wrote the `where` it was created with and so ignored presets; its statement builder now receives the call it builds for. Not measured: no probe row uses presets, so their type cost is not gated (P29 adds a gated presets probe row). D179 outcome: `decodeDuration` and `decodeTimeZone` read what Postgres sends and keep the ISO forms; a real-Postgres test writes and reads both types. The round trip found a second bug on the write side: Postgres refuses a leading minus, so a negative `Temporal.Duration` failed on `insert`; it is now written with a sign on each field. The featureless app did not change for this commit (an app that declares neither column does not bundle the codecs). Left in `known-limits.md`: mixed signs (`1 day -01:00:00`), a non-default `IntervalStyle`, and a seconds offset on `timetz`.
