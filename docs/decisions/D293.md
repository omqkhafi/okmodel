# D293 — Roles apply, PUBLIC execute, pooler URLs (B-30, B-31, B-25, B-41)

- **Status:** accepted
- **Area:** product
- **Supersedes:** none

---

Tooling only. No new public runtime API. No new error kind. No catalog hash change (roles, grants, and default privileges stay outside the startup hash, D208). No runtime-entry or featureless-app gate move. Apply creates every managed role as the connecting user before `SET ROLE` to the migration role, so a second `CREATE ROLE` is not refused. Before `SET ROLE` or `OWNER TO` it grants itself membership (`WITH SET TRUE` on Postgres 16+; a plain grant on Postgres 15, where `CREATE ROLE` leaves no membership). When it can, it grants `CREATE` on the database and makes the migration role the schema owner so `GRANT USAGE ON SCHEMA` is not a silent no-op. A missing `CREATEROLE` or `SET` option is a clear `forbidden` error. A failed role unit rolls back and stays re-runnable. With `defineConfig({ roles })`, generated and user functions revoke `EXECUTE` from `PUBLIC` and grant it only to the app role (not reporting); without `roles`, behavior is unchanged. Migrate strips the `pgbouncer` query parameter before the URL becomes a startup parameter; other pooler hints are not interpreted. The pooler pid probe reads eight times and holds another backend between reads so a default PgBouncer (`server_round_robin=0`) is refused; URL heuristics stay. A direct connection is never a false positive. Managed-provider admin roles (RDS, Cloud SQL, Supabase) wait for M-4. Issue #341
