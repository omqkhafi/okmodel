# D230 — The Postgres suite is four shards, and the pooler proof is not on that path

- **Status:** accepted
- **Area:** product
- **Supersedes:** none

---

A labelled pull request was waiting on `suite / 15` and `suite / 18`. Across the last five labelled runs the Postgres suite step was 554–644s and the job was 602–689s. Checkout, setup Bun, install, and build were each about a second. Starting Postgres was 18–29s. Installing pgbouncer was 10–16s and the pooler proof was 2–3s, and both ran after the suite on the same job. `tarball / 18` was 40–46s. `gate / check` did not need the suite: it finished in about 3s while the suite was still running, after lint, types, test, runtimes, temporal, and package. The long step is one database running every file. The files that stalled that run (isolation 74s, selection 70s, consistency 63s, tx 54s, then compatibility, the driver suite, topology conformance, and routing) are pinned to four shards, `isolation`, `selection`, `consistency`, and `tx`. Every other file is dealt in sorted order. Each shard has its own topology, so schemas and roles cannot collide. The shard that imports `dist/` is the only one that runs `bun run build`. Bun's download cache is restored from `bun.lock`. The Postgres image is pulled once per job. pgbouncer and the pooler proof are a `pooler / <version>` job beside the shards. `fail-fast` stays false. A pull request still runs 15 and 18, and release and weekly still run 15 through 18, through the same `versions` input. No test file is dropped. `gate / check` now needs `suite` and `tarball`. A slice that should have run must be `success`, including a Postgres slice while `needs: postgres` is present. Without the label those two are skipped and the gate allows the skip. The required check name is unchanged. No runtime change. The runtime entry stays 5,288 / 2,026.
