# D234 — Unique and foreign-key names use every SQL column (P87, QA-L4)

- **Status:** accepted
- **Area:** dialects
- **Supersedes:** none

---

`constraint()` spells a unique or a foreign key from every SQL column, after `casing` and `sqlName`. The stored `nameKey` stays the token the caller already passed. A primary key stays `{table}_pkey`. A check keeps `nameKey`: a picklist check is the SQL column, and a named check is the author's name. Indexes already use SQL columns. A name longer than 63 bytes keeps the hash suffix. `defaultNameKey` is the one column join. Table `tasks`, casing snake: the extra unique is `tasks_id_tenant_id_key` with name key `id_tenantId`. `title.unique()` is `tasks_tenant_id_title_key` with name key `title`. The foreign key is `tasks_org_id_tenant_id_fkey` with name key `org_id`. Composite tenancy spells `documents_id_organization_id_workspace_id_key`. A path endpoint unique stays on the declared primary key only, so two tenants cannot share that id. Column or composite tenancy is the choice when they must. `renameColumn` and `renameTable` still keep the old name. The planner pairs the same shape, ignores `nameKey`, and emits a rename when the identity name differs. It does not drop the object. A second plan is empty. A table created with PostgreSQL's default `UNIQUE (a, b)` adopts with no steps when the schema matches. On Postgres 15.19 and 18.6, `ALTER TABLE … RENAME CONSTRAINT` took AccessExclusiveLock on the table and ShareUpdateExclusiveLock on the constraint index. A concurrent SELECT and INSERT waited and were cancelled at lock_timeout 400 ms (402–403 ms). The statement itself was 1 ms. `ALTER INDEX … RENAME` took only ShareUpdateExclusiveLock on that index. The same SELECT and INSERT finished in 1 ms and were not blocked. The statement was 0–1 ms. Both versions matched. Constraint rename stays class `contract`, lock `ACCESS EXCLUSIVE`, with the existing 5 s lock timeout and retry, and no new warning. Index rename stays class `contract` and is labelled `SHARE UPDATE EXCLUSIVE`. `mapPostgresError` matches the error's columns to the catalog object and returns the stored name key. A composite whose stored key is only the SQL column list returns the TypeScript fields. With no columns, the stored name key is the reason. An index reason stays the full index name. `connect()` passes that schema into the lazy `mapPostgresError` call. Matching stays in the errors module. Replay ignores `nameKey`, which Postgres does not store, so a check does not drop and recreate the constraint. The reference app migration `0004_sql_names` renames the constraints whose SQL names changed. `.unique()` and `index()` do not grow a `name` option: `column.ts` and `table.ts` are on the featureless-app path.
