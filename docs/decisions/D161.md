# D161 — `filters()` is synchronous and validates; `parse()` is asynchronous

- **Status:** accepted
- **Area:** product
- **Supersedes:** none

---

P22 made `filters()` return a promise so its code could load on first use. Measured: a fully synchronous `filters()` adds 971 minified and 288 gzip bytes to the startup graph (parser 344 / 109, OKM1123 check with its text 347 / 110, relation check 280 / 69), and the real parser will grow with every operator, so the parser cannot live in the startup graph. But the promise was in the wrong place: `filters()` is called once at module level, where a promise forces top-level `await`, and OKM1123 is a build-time error in the spec. Decision: `filters()` is synchronous, stores the spec and runs the OKM1123 and relation checks when called (a throw, about 179 gzip bytes); only `parse()` is asynchronous and loads the parser on first use, which costs nothing in a request handler that is already async (`const q = await taskFilters.parse(request.query)`). Spec 10.2 is updated. Found in P22
