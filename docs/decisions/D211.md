# D211 — Hand-edited migration SQL is linted per statement

- **Status:** accepted
- **Area:** dialects
- **Supersedes:** none

---

The linter splits each step with a pure lexer in the tooling layer. It removes `--` and nested `/* */` comments. It keeps `'...'` with doubled quotes (`standard_conforming_strings` on), `E'...'` with backslash escapes, `"..."` identifiers, and `$tag$` dollar quotes. A different tag inside a dollar quote does not close it. Statements split on a top-level `;`. An unterminated string, identifier, block comment, or dollar quote is one opaque tail, and the lexer does not throw. Each statement is linted. The place is `step N` when the step has one statement and `step N statement M` (from 1) when it has more. Step numbers stay. Earlier and later steps are read the same way, so a later `USING INDEX` and a validate after `NOT VALID` are seen in another statement of that step and after a comment. `-- okm-allow CODE: reason` stays on the step. It silences that code on every statement of the step that triggers it. A code no statement triggers is OKM1510 (D192). `DO` and `CALL` are OKM1542 with the reason `the body is not analysed`, silenced only by `-- okm-allow OKM1542: reason` (D99). A dollar-quoted body of `CREATE FUNCTION` or `CREATE PROCEDURE` is not linted as statements. `ALTER COLUMN … TYPE` matches the same rules as `SET DATA TYPE`, with and without `USING` (OKM1524, OKM1527, OKM1533, OKM1538). A blank line inside a quote, a dollar quote, or a block comment stays in the step. A blank line outside still separates steps. `okm migrate plan`, `okm migrate apply`, and `okm migrate check` use this linter, so an error is OKM1510. Check and apply read the files. Plan lints the plan it generates. The planner still writes one statement per step, and a generated migration lints as before (D193, D196). Reference-app migrations had no findings before and have none after. No new error code. No gate, cap, or ceiling moves.
