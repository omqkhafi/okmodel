# D262 — A bare `t.id()` stores `gen_random_uuid()`

- **Status:** accepted
- **Area:** product
- **Supersedes:** none

---

Amends D148, D153, and D154. Those decisions stored `uuidv7()` for a bare `t.id()` and for an omitted `defaults.id`. `uuidv7()` exists only on Postgres 18. Supported majors are 15 to 18, so that default fails with OKM1812 on 15 to 17. The default is now `uuidv4`, which emits `gen_random_uuid()` and works on every supported version. `t.id({ default: "uuidv7" })` and `defaults: { id: "uuidv7" }` stay the time-ordered database default and still need Postgres 18 (`minPostgres: 18`, D261). Pick `uuidv7` for a large write-heavy table: the ids are time-ordered and the index stays local. Random ids are the default elsewhere. The client generators `uuidv4`, `uuidv7`, and `okid` are unchanged. An existing catalog whose id default is `uuidv7()` plans `ALTER TABLE … ALTER COLUMN … SET DEFAULT gen_random_uuid()`. The lock is `ACCESS EXCLUSIVE`. The statement does not rewrite the table. The linter is clean. Keep the old behaviour with `defaults: { id: "uuidv7" }`. OKM1812 stays for an explicit `uuidv7()` below 18. Schema build and apply use `uuidv7NeedsPostgres()` (`uuidv7() needs PostgreSQL 18 or higher. minPostgres: 18.`). No second floor parser. No new error kind. No public type change. Id flags are unchanged. No gate move. Measured after rebasing onto D261: runtime entry 5,288 / 2,026, cold import 3.931 ms.
