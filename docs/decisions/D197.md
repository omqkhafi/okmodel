# D197 — Startup compatibility uses the stored class; the serialised catalog loads once

- **Status:** accepted
- **Area:** contracts
- **Supersedes:** none

---

`connect()` keeps the hash fast path: equal catalog hashes return without reading `okm_history` or `.okm/catalog.json`. When the hashes differ, startup reads `okm_history` and uses the `class` column as stored. It does not plan the SQL again. Ahead by expand migrations succeeds. Ahead by a contract migration, or behind the app, is OKM1520. The message names the migration. The fix says to apply that migration or change the deploy order. `requireMeta` is unchanged: a missing hash is still skipped unless the option is set. `okm migrate status` prints the same situations: `current`, `behind by expand`, `behind by contract`, `ahead by expand`, `ahead by contract`, and `failed at step N (resume with okm migrate apply)`. The command stays read-only on a protected target. A `catalog.hash` file makes the mismatch path load `.okm/catalog.json` instead of rebuilding the catalog from the schema. Concurrent connects in one process share one parse. A missing file, or a hash that does not match, is OKM1027. No new error code. The loader stays on the mismatch path, so the featureless app graph and the connect startup graphs do not gain it. No gate, cap, or ceiling moves. Found in P53b.
