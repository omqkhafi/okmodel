# D304 — Validation refuses unknown write keys (R1)

- **Status:** accepted
- **Area:** product
- **Supersedes:** none

---

With `validation: true`, `acceptKeys` threw away unknown write keys (`continue`), so a typo on insert was a silent no-op and a typo-only update became OKM1120 "update set is empty." Decision: validation throws the same OKM1120 as the core write path (key, table, accepted names, did-you-mean). No pass-through of unknown keys to the write planner — the check lives in the validation engine when validation runs. `{ validate: false }` and `validation: false` keep the core path. Same surface as D291: insert, insert list, update (mixed and typo-only), upsert / `onConflict`, first-or-create, `tx`, and `batch`. Standalone `insert.validate`, `insert.check`, `insert.pick(...).validate`, `insert.pick(...).check`, `insert.omit(...).validate`, `insert.omit(...).check`, and `update.validate` use the same refusal. An unknown key throws OKM1120 before rule issues are collected, so `check` does not return them. `insert["~standard"].validate` throws that OKM1120. It does not return `{ issues }` for an unknown key. A failed rule on that surface still returns `{ issues }`. No new ErrorKind. No public API change. No catalog hash change. No gate or ceiling moves.
