# D246 — First-or-create reads the winner in a second statement; a repeated update target is OKM1120 (P92)

- **Status:** accepted
- **Area:** product
- **Supersedes:** none

---

Both tools were already in the runtime. `insert` with `{ on, return: true }` and `update` of a list already had their public types, so those types are unchanged. The audit found two gaps. First-or-create was one statement: a data-modifying CTE that unions the insert with a select of the existing row. That CTE shares one snapshot, so a concurrent insert that commits while the statement waits is invisible and the loser returns no row. §5.3 allows 1–2 statements. The insert is now `INSERT … ON CONFLICT (target) DO NOTHING RETURNING`. When an input key is missing from that result, a second statement selects those keys. `READ COMMITTED` gives that statement a new snapshot, so both callers get the one row and the existing row is not overwritten. The lookup runs only on that path. Insert rows win when both appear. A partial unique on an archivable table adds `and t."<archivedAt>" is null`, or `and t.archived_at is null` when casing is `"snake"`. A primary-key conflict does not. Tenant tables keep D221: the target includes the tenant key, and the keys are taken after the stamp. `.sql()` shows the planned insert only. Inside `tx()` both statements use the reserved connection. Inside `batch()` the lookup is a second batch, and a failure's index maps back to the operation. The lookup chunks at 2,048 parameters. The per-row update list was already one `UPDATE` with `CASE` per field, chunked the same way as insert, tenant-scoped, and `{ count }` when nothing is returned. A miss is not an error: `count` is the rows changed, the same shape as a single-target update. An empty list plans no statement and returns `{ count: 0 }`. Guarded fields stay OKM1190. A hidden field stays writable, as on a single update (§6.7). Naming the same resolved target twice, including an `id` and a `where` of that same id, is OKM1120 (`update on <table> lists the same target twice.`, fix `List each row once.`). An empty `set` on a list item is OKM1120 `update set is empty.`. The new code stays in `write.ts`, `conflict.ts`, and `batch.ts`, which already load on first use. No public type change. No new error kind. No catalog hash change. Measured with `bun run size` inside `bun run check`: runtime entry 5,288 / 2,026, cold import 1.802 ms. PGlite 40,204 / 14,197, cold 15.833 ms, stubbed 3.174 ms. node-postgres 41,893 / 14,728, cold 11.881 ms, stubbed 3.077 ms. Bun.sql 41,387 / 14,467, stubbed 2.675 ms. The PGlite connect sample in this run is above the 15 ms local reference; the stubbed sample is not, and cold import is not gated. Connect minified bytes match. Gzip moved by at most 6 bytes. Bun.sql is +5 and the startup chunk stays 40,522 bytes with the entry at 865, so that move is minifier identifier assignment. Headroom under the app gate 90,900 / 30,170 is 186 / 22. query-200 is 17,171 instantiations and 6,328 types (129 under 17,300). A where value that is a class instance is compared by its own text: Temporal uses `toString`, `Date` uses `toISOString`, and bytes use hex. A value with no stable text gets a token unique to that call, so two different values are not reported as one target. A list of one item skips the check. The returned row is matched to the input key by encoding it again, so a timestamptz or date unique still returns the existing row, including when the other caller committed it. An empty `set` is OKM1120 (`update set is empty.`). No gate moves. Issue #210
