# D252 — Descendants walk the parent column; sync locks, then writes (P96)

- **Status:** accepted
- **Area:** dialects
- **Supersedes:** none

---

`descendants(id)` and `ancestors(id)` are one recursive statement on a self-relation. `many` walks from parent to child. `one` walks the other way. `relation` is required when more than one self-relation has a different foreign key (OKM1120, and the fix lists the names). `depth` is an integer of steps from the start, or omitted to walk the whole tree. `depth` 0 returns nothing unless `self` is true, which returns the start row. A row whose id is already on the path is not entered (`<> all(seen)`). There is no silent depth cap. A missing id returns no rows, including with `self`. The root has no ancestors. `where`, `select`, and `orderBy` match `find`. `limit` matches `find`: it bounds the rows after that order. No `limit` and no `.all(reason)` takes `limits.find`, or is OKM1101. A `limit` above `limits.max` is OKM1101, and `.all(reason)` reads past it. `depth` does not bound rows. The default order is depth, then the primary key. There is no `include`. `where` and a preset filter the rows that come back and do not cut the walk short. Tenancy and the active set apply on the start row, on every step, and on the result, so an archived row is not crossed. A primary key of more than one column besides the tenant key is OKM1120. The statement starts with `WITH`, which the router classifies as a write, so the walk runs on the primary. `ltree` is not read. The extension mechanism defines types, operators, and functions. It cannot change this statement. A later index can. No new extension pack. `sync(id, relation, ids)` sets a to-many relation to exactly those ids. Two statements, one transaction. The first locks the parent row. The second adds and removes links. A single statement took the lock and still inserted from the snapshot it had when it started waiting, so two syncs of one parent could hit the join-table primary key. The second statement starts after that wait and sees the committed links. A join table gains and loses link rows and does not delete the related row. A one-to-many sets or clears the nullable foreign-key columns and leaves the row. The tenant column is not cleared. A non-nullable foreign key is OKM1120 before any write, because clearing the link would delete the row. A `one` relation is OKM1120. A join column with no null, default, identity, or generated value is OKM1120. A client-filled id is that case. Duplicate ids count once. An unknown related id, or an unknown parent, writes nothing and throws `not_found`. The missing-id message gives the count, not the values. The result is `{ added, removed }`, sorted by text. `expect(n)` throws `not_found` when the number of changed links is not `n`, after the statements, the same as `update`. Inside `tx()` the throw rolls back. `sync` does not set `~plan`, so a batch refuses it with the existing OKM1121. Presets apply to the parent row only. No new error kind. No catalog hash change. No gate move. The walk and the sync load on first use (`tree.ts`, `sync.ts`). The walk and the sync share the loader `page` and `aggregate` already use. `expect` is a branch on that loader, so `sync` does not carry its own handle. `plan.ts` and the public types add no runtime bytes. The reserved preset names live in the preset chunk, which the stubbed gate does not include.
