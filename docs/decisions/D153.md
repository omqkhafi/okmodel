# D153 — Id generators: `uuidv4` now, OKID in 0.2

- **Status:** accepted
- **Area:** product
- **Supersedes:** none

---

(1) `t.id()` keeps `uuidv7()` as its database default and gains `t.id({ default: "uuidv4" })` and `"none"`: `uuidv4` emits `gen_random_uuid()`, which is built in from Postgres 13 (the `uuidv4()` alias only exists in 18, so we do not emit it); P17G ships it, replacing the name `random` used in its first prompt. (2) OKID joins as an id option in 0.2 (P19), brought in as a vendored copy of okengine's `src/okid.ts`, `okid-shared.ts` and `okid-extended.ts` (about 380 lines, Apache-2.0 on both sides) because okmodel has zero runtime dependencies; okengine stays the source of truth and okmodel carries a header, okengine's test vectors and a check that fails when the copy drifts. It uses only the global `crypto.getRandomValues`, no `node:` imports, so it runs on Node, Bun, Deno and edge runtimes; CI runs it on Node, Bun and Deno, and `engines.node` is declared (undeclared today). (3) OKID is generated by the application, not by Postgres (no OKID function exists until functions land in 0.3), so it is an application-side default: it does not enter the database catalog hash and does not produce a migration when its prefix or length changes. (4) The id column is `text`. A sortable OKID orders as time only under byte order, so the column uses `COLLATE "C"`; the catalog has no column collation today (only a reserved-word list mentions it), so P19 adds collation to the catalog, create, diff and introspection. (5) The builder shape (`t.id({ ... })` options for okid, prefix, sortable, length) is proposed by P19 in its report and then written into the spec. (6) OKID is an application identifier, not a secret; sortable ids expose creation time, and the docs say so. Found when planning ids for 0.2
