# D260 — Search errors, tree updates, claim rows, and the fixes that do not fit (0.7 QA)

- **Status:** accepted
- **Area:** product
- **Supersedes:** none

---

A malformed advanced search (`42601` whose text contains `tsquery`) is OKM1120 and names the search input. A missing text search configuration (`42704`, "text search configuration ... does not exist") is OKM1122, including `public.english`. Other syntax errors stay `driver`. The mapping is in `mapPostgresError`, which loads on the first driver error. `morphTo(name, type, id)` with a null name, a null type, or an id that is not a non-empty string is OKM1120. An empty string name or type stays OKM1020. `update` of a tree parent foreign key to the row's own id is OKM1120 when `where` is that row's primary key. A tenancy column in the key may be absent. A filter that is not the key is not checked. `update` with `limit` and `returning: true` returns the updated rows and honors `select`. The default result stays `{ count }`. The overload is on `TableApi.update`. An include `select` that names a hidden column is OKM1120, the same as `where` and `orderBy`. A default include still omits the column. Bun.sql retries a statement whose error is `Connection closed` up to twice, so the query after a backend killed during `.stream()` does not fail. A statement the server terminates (`57P01`) is not retried. The retry loads from `bunsql-extra.ts`. `connect(pool)` then `db.close()` on PGlite marks that client closed. `seal` in the PGlite adapter sets the flag and does not close the caller's pool. Later calls are kind and code `unavailable`. `client.ts` is unchanged. An id of 2^64 is kind and code `invalid` on Bun.sql as well. `refuseInt8` sits beside `send`: a canonical integer outside the signed int8 range is a rejected query with SQLSTATE 22003, mapped like the other drivers. The check is not in the shared codec. `bunsql-extra.ts` already imports `send`, so the check is not in that lazy chunk. A numeric value written as that same integer is refused on Bun.sql too. No new error kind. No catalog hash change. No gate move. Measured after these two checks, against the figures above: runtime entry 5,288 / 2,026, cold import 1.897 ms, unchanged.
