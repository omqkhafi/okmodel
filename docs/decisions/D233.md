# D233 — View isolation and the operators `parse` applies (P85)

- **Status:** accepted
- **Area:** product
- **Supersedes:** none

---

`isolation()` still checks every tenant table, then reads tenant views and materialized views. Both tenants' rows are inserted into the underlying tables, a materialized view is refreshed, and a row of tenant B fails the check. The report is `{ checked, views, skipped }`. A global view is listed with the reason from `global("reason")`, in the same list as a global table. A view that hides the tenant key is still OKM1820 unless it is `global("reason")`. The check does not insert into a view. `filters().parse` applies `not` (a scalar or null), `containedBy`, `overlaps`, `hasKey`, and `hasAnyKey` beside the thirteen it already applied. A `relations` allowlist becomes `has` over those fields. A name that is both a column and a relation stays the column. The allow type is that operator set, so `path`, `matches`, `similar`, `wordSimilar`, `or`, `and`, `none`, `every`, and the write operators are a type error. Those stay out: the inner comparison, the regconfig, the extension schema, or a client boolean tree is not one tag `parse` can apply. Hidden fields stay OKM1123 when `filters()` is called. `filters()` stays synchronous (D161). Passing the relation map through the existing closure grew the featureless app by 2 minified and 6 gzip.
