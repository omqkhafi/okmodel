# D254 — `versioned()` and `sortable()` (P98V)

- **Status:** accepted
- **Area:** product
- **Supersedes:** none

---

`versioned()` adds `version integer not null default 1`, guarded and sealed. An update passes the version it read (`update({ where, set, version })`, and each list item the same). The check and the bump are one statement: matching rows are locked, and the write runs only when every one is still at that version. A miss stays `{ count: 0 }`. A stale row is category `conflict` and writes nothing. The message names the fields and the version, and says to reread and retry. No new error kind. `inc` and the other atomic operators still bump `version`. `returning` includes the new version. A claim (`lock: "skip"` and `limit`) that passes an integer `version` updates free rows at that version and conflicts only when nothing was updated and a free row is at a different version. `version: "any"` with that same `lock` and `limit` skips the check (O-5, issue #393). The statement selects the primary key `ORDER BY` that key, `LIMIT`, and `FOR UPDATE SKIP LOCKED`, then `UPDATE ... FROM` that set with the caller's predicate repeated, so the lock runs once and the write never changes more than `limit` rows. It bumps `version` by 1 and returns the new rows. A miss is an empty array, not `conflict`. Run the claim in `READ COMMITTED`. Under `REPEATABLE READ` or `SERIALIZABLE` the same race can raise SQLSTATE 40001 instead of dropping the row. `version: "any"` without `lock: "skip"` and `limit`, an unrecognised version string, and a `version` key in `set` are OKM1120. First-or-create and `onConflict: "ignore"` do not change the existing row. An upsert, `.all()`, a missing `version` other than `version: "any"` on a claim, `version` on a table that is not versioned, and a path-parent change in the same update are OKM1120. `delete`, `archive`, and `restore` do not check or bump `version`. `sortable(groupBy?)` adds `position integer not null` with no default, guarded and sealed. Positions are dense positive integers, unique per tenant and group. Fractional or rank keys were the other option: one row changes, but two moves into the same gap can pick the same key unless a unique index rejects one, the keys are not dense, and the gap eventually needs a rebalance. Integer renumbering lets the unique index reject a duplicate and keeps `1..n`, and a move rewrites the rows whose positions change. Moves in one group wait on one advisory lock, taken in its own statement before the renumber reads the group. The unique index is checked per row and is not deferrable, so the move writes the new positions as negatives and flips them to positive in the same transaction. A position that is already negative is flipped too. `via()` is OKM1060, because the tenant key is not a column and the index could not separate tenants. The index names the tenant columns itself (D168). On an archivable table it is partial (`archived_at IS NULL`). `move(id, { before })` or `{ after }` returns `{ position }`. A missing id is `not_found`. An anchor in another group is OKM1120. Changing the group column is OKM1120. New rows insert at `max(position) + n`. The lock statement runs first and the max is the next statement in that transaction, so an insert that commits while the lock is waited for is visible. Several groups in one insert lock in sorted key order, then read each max. An insert outside `tx()` is still one atomic batch. A delete leaves a gap. Adding `position` to a table that already has rows is `add-column-required`. `find` and `page` order by `position`, then the primary key, when `orderBy` is omitted. `one()` is not reordered. `move` is declared by augmenting `TableExtras` from `okmodel/traits`, not by a per-table conditional on `TableApi`. `version` on `UpdateTarget` is optional. The runtime requires it on a versioned table. The hash function does not change. A schema that calls either trait hashes differently because the column, and the position index, are catalog objects. The featureless app does not import `okmodel/traits`. The check loads from `version.ts` on the first versioned update, and the move loads from `sort.ts` on the first insert or move.
