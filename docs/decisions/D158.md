# D158 — Gates after the 0.2 operators, and the room left for P21 to P29

- **Status:** accepted
- **Area:** product
- **Supersedes:** none

---

P20 (the operator set) took the app startup graph from 82,041 / 26,716 to 82,679 / 27,196 and every connect entry to within 1% of its D157 gate (postgres.js 39,679 / 13,693; `pg` 39,821 / 13,866; Bun.sql 38,722 / 13,426); the operator SQL is a chunk loaded on first use, but the planner and the fit check are static. By the D155 rule the first commit of P21 moves the gates to measured +3%, rounded down: app startup 85,100 / 28,000; postgres.js connect 40,800 / 14,100; `pg` 41,000 / 14,250; Bun.sql 39,800 / 13,800; PGlite stays. The hard cap for 0.2 is still 91,000 / 30,000 (D143), which leaves 8,321 / 2,804 bytes for nine steps (P21 to P29: provenance and safety, field exposure, traits, tenancy, archivable, validation, relations, presets, transactions), about 900 bytes each if spent evenly. That is not enough for all of them to ship their code in the startup graph, so from P21 each step reports its growth before it builds, loads feature code on first use where it can (as P20 did for operator SQL and as `okmodel/ids` does), and stops and asks if a step would take more than its share instead of moving the cap. Also recorded: P20 removes the old `json` column-builder export from `okmodel/pg` (`json` is now the write namespace with `json.set`; the column is `t.json()`, and `jsonb` is unchanged), a breaking change for anyone who imported it, listed in the changelog and the 0.2 release notes.
