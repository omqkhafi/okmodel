# D256 — `.stream()` walks keyset batches on every driver (P98)

- **Status:** accepted
- **Area:** adapters
- **Supersedes:** none

---

`.stream()` does not open a server cursor and does not read the `stream` capability. That flag still means the driver can open one (postgres.js, node-postgres, and Bun.sql yes; PGlite no). A server cursor stays a later opt-in. The postgres.js `FETCH` loop in D245 stays unbuilt. Each batch is the keyset `page()` already plans: the caller's `orderBy`, then each primary-key column the caller did not name, ascending, nulls last. No `orderBy` means the primary key ascending. The default batch is 1000. `.stream({ batch })` takes an integer from 1 to 2147483647 (OKM1121 otherwise, OKM1120 for any other key). `limit` on the find is the total. `.all(reason)` with no limit streams the whole set. Both together still honor `limit`. `limit` 0 yields nothing and runs no query. A table with no primary key is OKM1120 (`stream() needs a primary key on <name>. A keyset batch orders by that key.`). `search` and a window in `select` are OKM1120. `one()`, `count()`, and `exists()` are OKM1120. `select`, `include`, presets, tenancy, and the archive set are the same as `page()`. Nullable sort keys follow `page()`. Early `break` finishes the current batch, which is an ordinary query, so the connection returns to the pool. Rows another transaction commits during a long stream can be seen or missed. The snapshot is `tx({ isolation: "repeatable read" })`. `signal` goes to every batch. If it is already aborted before a batch, the stream throws `cancelled` (`The stream was cancelled.`) and does not start that query. `timeout` is one deadline from the start of iteration. Between batches, a passed deadline throws `timeout` (`The stream timed out.`). On a driver that can cancel, each batch's statement timeout is the time still left, further capped by the session statement timeout when that is shorter and positive. PGlite and Bun.sql do not take a positive statement timeout, so the budget is checked before each batch and a batch already running finishes. A non-positive timeout is OKM1121. No new error kind. The startup hooks are the stream arguments on the read handle and the pin forwarded by `callOptions`. `read-stream.ts` and the router's pin check load with the stream and the topology chunk (D248). On `connect({ primary, replicas })` the first batch is routed like a find. Later batches stay on that endpoint (`onRoute` reason `stream:<name>`) and a connection failure does not move. Inside `tx()` every batch uses the transaction connection. `versioned()` and `sortable()` shipped as D254. `morph` shipped as D255.
