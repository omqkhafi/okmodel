# D288 — Bun.sql sessions stay isolated; a committed write stays committed (B-03, B-04)

- **Status:** accepted
- **Area:** product
- **Supersedes:** none

---

The Bun.sql adapter no longer parks the last released handle for the next checkout. Every release returns the handle to Bun's pool after `RESET ALL` and `pg_advisory_unlock_all()`, or destroys it when the session is gone. Parking existed only so the harness reset check reused `pg_backend_pid()`; that check now asserts advisory locks on the released pid without requiring reuse. A reset or release failure after the statement or `COMMIT` completed does not fail the call on Bun.sql, node-postgres, or Neon: the connection is destroyed and the successful result stands, so `afterCommit` runs. postgres.js already swallowed reset failures. A failure after the send and before the result stays `outcome_unknown` (OKM1401), is not retried, and does not run `afterCommit`. Bun.sql still stamps `Connection closed` and `connection must be a PostgresSQLConnection` with SQLSTATE `08006`. node-postgres stamps `Client has encountered a connection error and is not queryable` as `CONNECTION_CLOSED`. No new public API, error kind, or catalog hash change. No gate moves. Measured: runtime entry 5,288 / 2,026 (unchanged), featureless app 90,718 / 29,426 (unchanged), Bun.sql connect 39,504 / 13,754 (was 39,717 / 13,839). Issue #335
