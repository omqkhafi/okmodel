# D263 — Fail closed after a backend kill, and settle postgres.js calls (0.7 QA)

- **Status:** accepted
- **Area:** adapters
- **Supersedes:** none

---

A reserved Bun.sql handle snapshots `closures` after `reserve`. That counter only grows. `dropped` still resets to 0 after a drain, so it cannot detect the reconnect. The next `execute` or `batch` on that handle, when the count has moved, rejects `DriverError("Connection closed", { sqlstate: "08006" })` before any statement on the new connection. The kind is `unavailable` and `retryable` is true. A scoped find does not come back empty. postgres.js copies `onclose` onto `sql.options` at startup and reads that property when a connection closes, so assigning it later is seen. The wait set lives on that options object, one set per pool. A wait with no call deadline is rejected with the same 08006 error only after every slot in that pool has closed, or immediately when the reserved connection that wait uses closes. A queued `sql.reserve()` is started again after a close, because postgres.js takes that reserve off its queue and drops it without settling (`ReadyForQuery` nulls a reserve `initial`). A wait with a deadline is not on the close hook. It ends at that deadline. One helper. No new retry. The first call after a backend kill on an idle connection stays `unavailable` with `retryable: true`. Bun.sql still retries a client read once at transaction depth 0. postgres.js and node-postgres do not. A `42601` is OKM1120 when the message contains `tsquery` or the statement contains `to_tsquery` (advanced, natural, all-words, and phrase all do). Other syntax errors stay `driver`. No new message strings. No new error kind. No catalog hash change. No public API change. The postgres.js incremental gate is 16,000 minified bytes, was 15,500, for this close rule. Known limit, not fixed: an unhandled rejection from `fetchArrayTypes` when the backend dies during connect. `ReadyForQuery` returns `fetchArrayTypes()` with no `.catch()`. That function awaits `new Query` of `select b.oid, b.typarray from pg_catalog.pg_type …`. If the server terminates that backend before the query finishes, `closed()` rejects it with `write CONNECTION_CLOSED <host>:<port>` and the rejection is unhandled. Repro: default `fetch_types: true`, several queries in flight, `select pg_terminate_backend(pid) from pg_stat_activity where pid <> pg_backend_pid()`. `fetch_types: false` skips the query and also changes decoding for array types the caller did not register, so it is not set. Known limit, worked around: a queued `sql.reserve()` is dropped without settling when a connection slot closes. Repro: `max: 2`, hold one connection, queue `sql.reserve()`, `pg_terminate_backend` on the other backend. okmodel starts that reserve again.
