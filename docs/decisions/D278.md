# D278 — `okm pull` writes functions, triggers, and views, and says what the scratch run proved (P112)

- **Status:** accepted
- **Area:** tooling
- **Supersedes:** none

---

`okm pull` writes `fn()`, `trigger()`, `view()`, and `materializedView()` into the schema file, with the same rules as D275: read-only on the selected namespaces, never overwrites (OKM1855), deterministic, nothing dropped without a line. A view is the SQL-string form with the columns and the `pg_get_viewdef` text, not `q.from`. A view and a `BEGIN ATOMIC` body take edges from `pg_depend`, which introspection already stored. A plpgsql or SQL-string body gets `dependsOn` candidates by matching pulled table names with the migration SQL lexer. A matched view or function is an ordering edge only, because `dependsOn` accepts tables and columns. A view query is matched the same way, so the scratch replay creates a view after the view it names when `pg_depend` recorded no column edge (`count(*)`). Pull then replays the objects on a scratch schema, in the catalog's dependency order, with `check_function_bodies` on, and drops that schema. A SQL function or a view whose dependency is missing fails creation and is `unverified`. A plpgsql function that is created is `candidate-only`: creation does not prove the body. A SQL function or a `BEGIN ATOMIC` body that is created is `verified`. The report and a comment above the declaration say which. A pulled plpgsql function lists `dependsOn`, including an empty list, so OKM1824 passes. Aggregates, procedures, event triggers, and rules stay under `not pulled yet` with a count, because the catalog has no kind for them. Policies, roles, and grants stay there too. No new catalog kind, no new builder, no new error code. Nothing new is reachable from the runtime entry or from `connect()`. Issue #314
