# D313 — `aggregate({ having })` (F8-4)

- **Status:** accepted
- **Area:** product
- **Supersedes:** none

---

`aggregate()` with `groupBy` takes `having`: the `where` predicate form over aggregate names. The names are `count` (always there, whether or not `count: true` is set) and each `select` name (D311). A list-form aggregate (`sum: [...]`) has no flat name, so `having` cannot reach it. The value is an object of names (joined with `and`) or `or([...])` of such objects; per-name values are a bare value (equality), `null`, or an operator. It writes `having <aggregate expression> <op> $n` between `group by` and `order by`, so it works with `bucket()` groups and `limit` as well. Each operand is encoded by the shared `where` writer (`emitOperand`, with the aggregate expression as the reference): `count`, `countDistinct`, `sum`, and `avg` compare with a number or a numeric string (anything else is OKM1121), `min` and `max` compare as the column they read. Operators: `eq`, `not`, `lt`, `lte`, `gt`, `gte`, `between`, `inList`, `notIn`, `or()`, and the text patterns (`startsWith`, `endsWith`, `contains`, `like`, `ilike`) on a text `min` or `max`. Another operator is OKM1121 before any SQL. A NULL aggregate (a `sum` over only NULLs, a `max` of a NULL-only group) matches no comparison, as in SQL, and `null` matches it. An all-`undefined` object is no `having`; an empty `or([])` matches nothing, and an empty `or` branch is refused, as in `where`. Refused with OKM1120 before any SQL: `having` without `groupBy`, and a name that is not an aggregate of the call (the error lists the accepted names). No decision is reversed: D125's bare-object rule applies unchanged. Types: `having` is typed from `count` and the `select` names, with the same value types as `where` (a `sum` over a nullable column is `T | null`); an unknown name is a type error. The select overloads carry that guard on the call, and a call without `select` types `having` as `count` only, so the type-cost ceiling stays (`query-200+page+aggregate+through` 24,647 / 7,010 against 24,792 / 7,146). `having` without `groupBy` is a runtime refusal; requiring `groupBy` in the types added a third union branch that measured 26,929 instantiations, over the ceiling. Dialects: `having` is standard SQL and native on Postgres, SQLite, and MySQL/MariaDB; Postgres is the only dialect in this repository. Capability key `query.having`. All the code is in the lazy `aggregate` chunk, plus `export` on `emitOperand` and `isTextColumn` and a trailing `ref` parameter on `emitOperand` in the planner. The featureless app goes from 88,437 / 28,440 to 88,437 / 28,445; the runtime entry stays 5,288 / 2,026; no gate moves. Ordering by an aggregate stays out of scope. No new ErrorKind. No catalog hash change. Issue #509
