# D204 — P63 consistency is one client-wide watermark

- **Status:** accepted
- **Area:** runtime
- **Supersedes:** none

---

The watermark lives on the topology handle, one per `connect()`. The root, `for()`, `unscoped()`, `using()`, and `reserve()` share it. The router is a shared pool and cannot see which `db.for()` client issued a statement. A per-`for()` watermark needs bytes in `client.ts`, so it stays deferred. The client-wide watermark is the conservative 0.5 behaviour: a write on any of those clients moves the watermark for all of them. Carrying a position across processes stays deferred (spec section 25). After a write commits, the watermark is `pg_current_wal_insert_lsn()` read after the commit, before the write's promise resolves. Autocommit `execute` and `batch` read it on the primary pool. Any primary connection is a safe upper bound. `tx()` reads it on the reserved connection immediately after a successful `COMMIT`. A `ROLLBACK` or a failed commit changes nothing. The read is not inside the transaction, and `COMMIT` and the select are not one message. One extra round trip is accepted. It runs only when replicas are configured and `routing.consistency` is `"session"` (the default). `"eventual"` and a lone primary do not read it. The watermark is monotonic: LSNs compare as `BigInt` from the `X/Y` hex form, and a smaller reading is ignored. A failed position read marks the handle position-unknown. The generation increments every time that flag is set. A primary probe raises the watermark and clears the flag only when it started in that generation and the flag is still set; a probe already in flight only refreshes the lag baseline. Automatic reads use the primary (`fallback:position-unknown`, or OKM1844 with `fallback: "error"`) until the next successful position read, from a later write or from a primary probe. `route: "replica"` and `using("replica")` are OKM1843 while the position is unknown. A replica serves a read when its last seen replay position is at or beyond the watermark. That cache is a lower bound, so a hit needs no round trip. Otherwise one on-demand `pg_last_wal_replay_lsn()` runs through the same `ReplicaState` seam as the probe, then the next candidate, then the fallback. Healthy replicas that miss the watermark or `maxLag` report `fallback:behind`. `routing.maxLag` is a string: `"5s"`, `"500ms"`, `"2m"`, `"16MB"`, `"512KB"`, `"1GB"`, or `"4096B"` (`KB` is 1024). A bare number is OKM1120. Byte lag is the primary insert position, sampled on the primary probe and refreshed on write, minus the replica replay position. Time lag uses `pg_last_xact_replay_timestamp()` only while the replica is behind the primary. A caught-up replica has lag zero, so an idle primary does not make replicas look stale. The timestamp column is on the replica probe only when `maxLag` is a duration, and that SQL stays in the lazy chunk. `maxLag` applies to automatic reads and to `route: "replica"` and `using("replica")`. Positions need `replication.position`, already detected per endpoint at connect. A primary or a replica without it cannot be checked: after a write, automatic reads use the primary and a required replica is OKM1843. `maxLag` excludes a replica without position support. A read with no write yet and no `maxLag` still uses replicas. `"eventual"` needs positions only for `maxLag`. `ReplicaCandidate.lag` is that byte lag, or `null` when either position is unknown. The wrote flag is gone. Cursor pages are separate operations, each checked against the watermark. `consistency` and `maxLag` leave the OKM1061 list. `routing` accepts `probe`, `select`, `fallback`, `consistency`, and `maxLag`. The consistency stage is async. The shared scratch list is copied off before the await. A successful `COMMIT` is observed on the reserved connection wrapper in `topology.ts`. `transaction.ts` is unchanged. Nothing was added to the connect entries, `client.ts`, `plan.ts`, or the runtime entry. Startup minified bytes are unchanged from D203.
