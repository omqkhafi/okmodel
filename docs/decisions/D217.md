# D217 — M2 Depth is four trains, and Access is first

- **Status:** accepted
- **Area:** product
- **Supersedes:** none

---

M2 ships as 0.6 Access, then 0.7 Query depth, then 0.8 SQL lane, then 0.9 Tooling. Access is first because tenancy and grants are the isolation boundary the later trains have to obey, and the deferred 0.5.x items sit on that same code. The OKE `store.sql` prototype starts after 0.6, on the public API only. That replaces the start D209 recorded after 0.5. Step ranges: 0.6 is P80–P89 (P80–P86 are scheduled; P87–P89 are not), 0.7 is P90–P99, 0.8 is P100–P109, 0.9 is P110–P119. Each train ends with a gate step and a release commit, like P66. P86 releases 0.6.0. The later gates release 0.7, 0.8, and 0.9 when their prompts are written, and each does the D115 hygiene before `bun run bump release`. Lazy loading: every M2 feature loads lazily, or the step stops with the numbers first and does not move a gate. That is the D201 rule for the whole of M2. After 0.5.1 the featureless app has 13 gzip bytes left (90,851 / 30,157 against 90,900 / 30,170) and each connect entry has about 20. P80 measures where the bytes go and proposes gate options. Ali approves that proposal before P81. No gate moves in this decision. Assigned from the deferred list: 0.6 takes hidden columns in `where` and `orderBy` (QA-S1, D215; a decision with examples first, recommendation refuse with OKM1120 and an opt-in per column), tenant `onConflict` on a (tenant key, column) unique (OKM1104), QA-L4 constraint names and a rename design for the extra unique beside the composite primary key (§9.2 still requires it), the materialized-view `refresh()` handle (§5.7), the Bun.sql and PGlite timeout and signal race as a lazy design (QA-M3, D216 numbers), strategies `path` and `composite` (§9.1), strategy `rls` (§9, §9.4), column-level grants and the read-only reporting role (§5.7, D207), ownership (`ignored` and `owner:`, §5.1), the application role's `SELECT` on `okm_meta` (D208), the read-only view isolation check (D207), and `filters()` operators and relations beyond D215. 0.7 takes tools 2, 4, 5, and 7 to 15 (§13), `versioned` and `sortable` (§8), `morph` (§6.2), and `.stream()` (§10). 0.8 takes the SQL builder lane, typed raw SQL with an explicit class (§16, D205), `explain()` and the dev inspector with routing reasons (§5.4, §15.1), `okmodel/otel` (D80), the Neon adapter (§4), `okm driver test` (§4.2, §20), and typed `fn` calls and builder views if the budget allows (D190). `okmodel/pg/pg` and `okmodel/pg/bun` shipped in 0.2 (D156) and are not planned again. 0.9 takes the linter and safe rewrites still missing after 0.4 (§19.1), `okm pull` and plpgsql dependency verification on a scratch database (§5.7, §19.4), several catalogs, `external()`, and catalog export (§3.6), extension packs and the rest of `okm ext` (§4.1), the GitHub Action (§19.8), the programmatic schema API (D26), `okm import drizzle` (§19.4), and the M2 gate. `schemaPerTenant` and `databasePerTenant` stay M5. `table({ policies })` stays `later` except for the part `rls` ships (§6.4, §9.4).
