# D181 — P29 transactions ships at +215 / +225; races proved on four drivers; choices accepted

- **Status:** accepted
- **Area:** product
- **Supersedes:** none

---

`tx`, `batch`, row locks, `afterCommit`, advisory locks, per-call `{signal, timeout}` and `connect({timeouts, hookm})` are in (PR #110, 0.2.0-next.20). Featureless app 88,938 / 29,778 (+215 / +225 over P28, stop line +1,400 / +400), runtime entry 5,288 / 2,026 (unchanged), connect entries 40,990 / 14,591 (postgres.js, gate 14,600), 38,957 / 13,974 (PGlite, gate 13,980), 41,402 / 14,770 (pg, gate 14,920), 40,251 / 14,285 (Bun.sql, gate 14,470); no gate, cap or existing probe ceiling moves. Room under the 91,000 / 30,000 cap is 2,062 / 222, and the postgres.js and PGlite connect entries have 9 and 6 gzip bytes left, so any growth in client or connect code now needs a cap decision with Ali. Probes: `query-200` 17,078 / 6,271, `query-200-validate` 25,047 / 6,464, `query-200+page+aggregate+through` 24,231 / 6,795, all under their ceilings; two new gated rows at measured +3% (D176): `query-200+presets` 19,180 / 7,128 (ceilings 19,755 / 7,341) and `query-200+tx` 24,283 / 6,948 (ceilings 25,011 / 7,156). The presets row shows a chain of two presets with arguments plus `find` costs about +2.1K instantiations over `query-200`. A first typing of `tx` that passed the table-name union as a type argument cost +629 on `query-200`; a `Root` flag computed inside the callback type cost +16. How it is built (D162 to D165, D171): the core only dispatches; `transaction.ts`, `batch.ts`, `lock.ts` and `hookm.ts` load on first use. `tx()` reserves one connection and gives the callback a facade pool over it, so every code path keeps its affinity. A transaction that had a statement fail refuses to commit even when the callback caught the error. Nested `tx()` is `SAVEPOINT okm_tN`, `ROLLBACK TO`, `RELEASE`. Retry only on kinds `serialization` and `deadlock`, a fresh transaction per attempt, jittered pause, one deadline for all attempts. A connection lost at COMMIT is `outcome_unknown` (OKM1401), never retried, and nothing is sent on it after. Races on real Postgres on postgres.js, node-postgres, Bun.sql and PGlite where each can (38 cases each): serializable conflict with retry, real deadlock, `skip` and `nowait`, statement killed by timeout and by abort, cut commit and cut batch through a TCP proxy, pool reuse, savepoints. Skips: PGlite has one connection, no `cancel` and no socket to cut; Bun.sql has no `cancel` and no notices. Choices accepted: (1) `timeout` is milliseconds as a number, as `connect({timeout})` already is; the spec example `"5s"` is changed. (2) A nested `tx()` takes no options (OKM1121). (3) `batch` takes writes only; a read in the list is OKM1121 (spec edited). (4) A table named `tx` or `batch` is shadowed by the method. (5) `rls` tenancy is not built; inside `tx()` the tenant is the column predicate on every statement. (6) A `batch` inside `tx()` emits no `hookm.onTransaction` phase; a savepoint opened by `tx()` does. (7) `find({lock})` on the root client compiles and is OKM1830 at runtime. (8) On PGlite and Bun.sql a `tx({timeout})` or `tx({signal})` cannot kill a statement waiting on a lock; the callback is released and the rollback queues behind it (known limit for 0.2). (9) `idleInTransaction` is a client-side timer, not the server setting. Found by the cut-commit test and fixed in the adapters: postgres.js crashed on a write to a closed reserved socket; node-postgres needed an `error` listener and `release(true)`; Bun.sql parked a lost connection; all three keep a `lost` flag, send nothing after it and drop the connection. Not built or not tested: Neon, D1 and other batch-mode drivers (no adapter in the repo). Found in P29
