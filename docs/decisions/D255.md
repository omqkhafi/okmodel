# D255 — `morph` is a closed list and a flat union (P98M)

- **Status:** accepted
- **Area:** product
- **Supersedes:** none

---

`morph("commentable", ["tasks", "lists"])` on the table that holds `commentableType` (text, the target's table name) and `commentableId`. The id matches each target's one primary-key column. A tenant key is not that column. Include is `true` and returns the matching target row, or null when the row is missing or the stored type is outside the list, as a flat union discriminated by the type field. `morphMany("comments", "commentable")` on each target is an ordinary many: include, limit, order, and `has` / `none` / `every` follow `many`, including the per-parent limit. `morphTo(name, type, id)` sets both columns. One without the other is OKM1121. A type outside the list is OKM1120. An unknown target, a missing column, a key of more than one column, or an id type that does not match is OKM1020, OKM1021, or OKM1022 and names the table and the column. The relation is not a catalog object, so two schemas that differ only by it hash the same. Deferred, and OKM1120 when called: `has` / `none` / `every` on the morph, `select` / `where` / `orderBy` / `limit` on that include, a nested morph include, `sync` of a morph, and a tree walk through a morph. A preset on the target table does not filter the include. A preset on the query does. No new error kind. No gate move. The resolver lives in `morph.ts` and tree-shakes the way `manyThrough` does. Include SQL is the existing include chunk. The half-set check is the existing write chunk. The startup hook is the table lookup and the tenant fields passed into `resolve` in `schema.ts`.
