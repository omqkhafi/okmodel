A table is a name, its columns, and the relations you want the client to follow. Declaring it is what makes the client typed. A unique or a foreign key is spelled from the SQL column names, so a rename of the column's SQL name renames the constraint and does not drop it.

## Declare the table

<Tabs items={["Identity", "Relation"]}>

<Tab value="Identity">

`t.identity()` is the primary key. An insert leaves `id` out. The row comes back with it, as a string.

```ts title="schema.ts"
import { schema, table, t } from "okmodel/pg";

// The insert leaves id out. The row comes back with it as a string.
const authors = table("authors", { id: t.identity(), name: t.text() });
export const app = schema({ tables: [authors] });
```

`t.identity({ as: "number" })` is the same key, and the id comes back as a number.

</Tab>

<Tab value="Relation">

`authorId` points at `authors`. `one` and `many` name the two directions. A query can then include the author on a note. A to-many include takes a limit, and that limit is the first related rows of each parent. A column that references its own table is the parent `descendants` walks.

```ts title="schema.ts"
import { many, one, schema, table, t } from "okmodel/pg";

const authors = table(
  "authors",
  { id: t.identity() },
  { relations: { notes: many("notes", "authorId") } },
);
const notes = table(
  "notes",
  { id: t.identity(), authorId: t.bigint().references("authors") },
  { relations: { author: one("authors", "authorId") } },
);
export const app = schema({ tables: [authors, notes] });
```

## One relation, several tables

A comment that points at a task or a list is `morph("commentable", ["tasks", "lists"])` on the comment, next to `commentableType` and `commentableId`. Use it when one table points at a closed list of others and you want the matching row back. Include returns the task or the list, or null when the row is missing or the stored type is outside the list. Each target declares `morphMany("comments", "commentable")` for the comments that point at it. That reverse many takes a limit, an order, and `has`, `none`, and `every`. `morphTo("commentable", "tasks", id)` sets the type and the id together. Setting one without the other is refused. A type outside the list is refused. `has`, `none`, and `every` on the morph itself are refused, and so are `select`, `where`, `orderBy`, and `limit` on that include. See [known limits](/docs/reference/known-limits).

```ts title="morph.ts"
import { connect } from "okmodel/pg/postgresjs";
import { morph, morphMany, morphTo, schema, table, t } from "okmodel/pg";

const tasks = table(
  "tasks",
  { id: t.text().primaryKey(), title: t.text() },
  { relations: { comments: morphMany("comments", "commentable") } },
);
const lists = table(
  "lists",
  { id: t.text().primaryKey(), name: t.text() },
  { relations: { comments: morphMany("comments", "commentable") } },
);
const comments = table(
  "comments",
  {
    id: t.text().primaryKey(),
    body: t.text(),
    commentableType: t.text(),
    commentableId: t.text(),
  },
  { relations: { commentable: morph("commentable", ["tasks", "lists"]) } },
);
const app = schema({ tables: [tasks, lists, comments] });

export async function attach(url: string, taskId: string): Promise<void> {
  await using db = connect(url, { schema: app });
  await db.comments.insert({
    id: "c1",
    body: "ship it",
    ...morphTo("commentable", "tasks", taskId),
  });
  const rows = await db.comments.find({ limit: 20, include: { commentable: true } });
  if (rows.length < 0) throw new Error("the morph did not run");
}
```

## Traits

`versioned()` adds `version`. An update passes the version you read, and the write bumps it. Use it when two editors must not overwrite each other. A stale write is a conflict and changes nothing. A miss stays `{ count: 0 }`. `inc` and the other atomic writes still bump `version`. `delete`, `archive`, and `restore` do not check it. An upsert and `.all()` are refused. `sortable("laneId")` adds `position`. New rows go at the end of that lane. `move` places a row before or after another in the same lane. `find` and `page` order by `position` when you omit `orderBy`. Changing the lane in the same update is refused. `via()` on this table is refused. A delete leaves a gap until the next `move`. See [known limits](/docs/reference/known-limits).

```ts title="traits.ts"
import { connect } from "okmodel/pg/postgresjs";
import { schema, table, t } from "okmodel/pg";
import { sortable, versioned } from "okmodel/traits";

const tasks = table(
  "tasks",
  { id: t.text().primaryKey(), title: t.text(), laneId: t.text() },
  { traits: [versioned(), sortable("laneId")] },
);
const app = schema({ tables: [tasks] });

export async function edit(url: string, id: string, otherId: string): Promise<void> {
  await using db = connect(url, { schema: app });
  const current = await db.tasks.one({ where: { id } });
  if (current === null) return;
  const saved = await db.tasks.update({
    where: { id },
    set: { title: "next" },
    version: current.version,
  });
  const placed = await db.tasks.move(id, { before: otherId });
  if (saved.count < 0 || placed.position < 0) throw new Error("the write did not run");
}
```
