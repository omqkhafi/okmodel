The calls below use one table and one connection. `insert` returns the row. `find` returns a list, so it takes a `limit`. `one` returns that row, or null when none matches. More than one match throws.

```ts title="index.ts"
import { connect } from "okmodel/pg/postgresjs";
import { schema, table, t } from "okmodel/pg";

const notes = table("notes", { id: t.identity(), title: t.text() });
const app = schema({ tables: [notes] });

export async function read(url: string): Promise<void> {
  await using db = connect(url, { schema: app });
  const inserted = await db.notes.insert({ title: "hello" });
  const found = await db.notes.find({ where: { id: inserted.id }, limit: 5 });
  const single = await db.notes.one({ where: { id: inserted.id } });
  if (found.length !== 1 || single === null || single.title !== "hello") {
    throw new Error("the row did not come back");
  }
}
```

`where` is the columns of the table. A field you did not declare is not a valid filter. A request from the client goes through `filters({ allow, sort, relations })`. `parse` applies `eq`, `in`, `notIn`, `lt`, `lte`, `gt`, `gte`, `between`, `startsWith`, `endsWith`, `contains`, `like`, `ilike`, `not`, `containedBy`, `overlaps`, `hasKey`, and `hasAnyKey`. A listed relation becomes `has`. A hidden field is refused.

[Safety](/docs/model/safety) covers fields that are stored but not returned, and writes that need an explicit allow.

## The first rows of a relation

A to-many include takes `limit`. That limit is the first N related rows of each parent, not N rows in total. Use it when each parent should show a short list, such as the three highest-scored comments. The read is still one statement: a lateral join. Pass `orderBy` for the order inside that parent. The primary key follows it, ascending, for any key you did not name, so two rows with the same score stay in the same order. Leave `orderBy` out and the related rows follow the primary key. A parent with no related rows comes back with an empty list. `select`, a nested include, and a preset still apply. `matches` and `relevance` work inside the include. `search` stays on `find` and `count`. A window inside that include's `select` is not in this version. See [known limits](/docs/reference/known-limits).

```ts title="include.ts"
import { connect } from "okmodel/pg/postgresjs";
import { many, schema, table, t } from "okmodel/pg";

const posts = table(
  "posts",
  { id: t.identity(), title: t.text() },
  { relations: { comments: many("comments", "postId") } },
);
const comments = table("comments", {
  id: t.identity(),
  postId: t.bigint().references("posts"),
  body: t.text(),
  score: t.integer(),
});
const app = schema({ tables: [posts, comments] });

export async function read(url: string): Promise<void> {
  await using db = connect(url, { schema: app });
  const latest = await db.posts.find({
    limit: 20,
    include: {
      comments: { orderBy: { score: "desc" }, limit: 3, select: ["id", "body"] },
    },
  });
  if (latest.length < 0) throw new Error("the include did not run");
}
```

## Number the rows

`rowNumber`, `rank`, `denseRank`, and `runningTotal` go in `select` on `find` or `one`. Use them when the row should carry its place in a group, such as a rank inside each status. `partitionBy` is the group. Leave it out to number the whole result. `orderBy` is the order inside the group, and `as` is the name on the row. `rowNumber` and `runningTotal` append the primary key, so a tie stays stable. `rank` and `denseRank` leave a tie tied: two equal amounts share a rank, and `rank` skips the next number. A running total uses the column's type. An integer is a number. A `numeric` column is the decimal string. `page()` refuses a window when the call runs. `lag`, `lead`, and a frame are not in this version. See [known limits](/docs/reference/known-limits).

```ts title="windows.ts"
import { connect } from "okmodel/pg/postgresjs";
import { rank, rowNumber, runningTotal, schema, table, t } from "okmodel/pg";

const tasks = table("tasks", {
  id: t.identity(),
  status: t.text(),
  amount: t.integer(),
});
const app = schema({ tables: [tasks] });

export async function read(url: string): Promise<void> {
  await using db = connect(url, { schema: app });
  const numbered = await db.tasks.find({
    select: [
      "id",
      "status",
      rowNumber({ partitionBy: ["status"], orderBy: { amount: "desc" }, as: "n" }),
      rank({ partitionBy: ["status"], orderBy: { amount: "desc" }, as: "r" }),
      runningTotal("amount", { partitionBy: ["status"], orderBy: { id: "asc" }, as: "soFar" }),
    ],
    limit: 20,
  });
  if (numbered.length < 0 || numbered[0]?.n === undefined) {
    throw new Error("the window did not run");
  }
}
```

## Search your text

Pass the words. Use this when a person typed a query and you want the closest rows, not a scan of a plain text column. When the table has one column built for search, that is the column. The closest rows come back first, then the primary key, so the order stays put. `count({ search })` uses the same match and does not order. An `orderBy` you pass replaces the ranking. `where`, `select`, `include`, and a preset still apply. `page()` refuses `search`. Use `find({ search, limit })` for one ranked list. `one` and `exists` do not take `search`.

```ts title="search.ts"
import { connect } from "okmodel/pg/postgresjs";
import { matches, relevance, schema, table, t } from "okmodel/pg";

const pages = table(
  "pages",
  { id: t.identity(), title: t.text(), body: t.tsvector() },
  { presets: { titled: (q, title: string) => q.where({ title }) } },
);
const app = schema({ tables: [pages] });

function deployNotes(title: string) {
  return { search: "deploy rollback", where: { title }, limit: 20 };
}

export async function read(url: string): Promise<void> {
  await using db = connect(url, { schema: app });
  const ranked = await db.pages.find({ search: "deploy rollback", limit: 20 });
  const phrase = await db.pages.find({
    search: { for: "deploy rollback", match: "phrase", language: "english" },
    limit: 20,
  });
  const scoped = await db.pages.titled("ship").find({ search: "deploy", limit: 20 });
  const named = await db.pages.find(deployNotes("ship"));
  const same = await db.pages.find({
    where: { body: matches("deploy rollback", { match: "phrase", language: "english" }) },
    orderBy: {
      body: relevance("deploy rollback", { match: "phrase", language: "english" }),
      id: "asc",
    },
    limit: 20,
  });
  if (ranked.length + phrase.length + scoped.length + named.length + same.length < 0) {
    throw new Error("the search did not run");
  }
}
```

`matches` and `relevance` take `{ match, language }`. `{ mode, config }` is not accepted. `match` is `natural` (the default, the same kind of text a search box accepts), `all-words`, `phrase`, or `advanced`. `advanced` is the database's own query syntax. `language` is a text search language such as `english`. Leave it out to use the database default. When the table has more than one search column, name it: `search: { for: "deploy", in: "body" }`. The error lists the names when you do not. A highlighted snippet and a search of a plain text column are not in this version. See [known limits](/docs/reference/known-limits).

A named query is a preset, or a function that returns the `find` options, as `titled` and `deployNotes` do above. There is no separate call for one.

## Rows under a row

`descendants(id)` reads every row below `id` in one statement. `ancestors(id)` reads the rows above it. Use them for a tree you walk from a parent column, such as a folder or a thread. Declare a relation from the table to itself. Pass `relation` when there is more than one. The error lists the names. `depth` stops after that many steps. `depth` 0 returns nothing unless you pass `self: true`, which returns the start row. A cycle comes back as rows, because a row already seen is not entered again. A missing id returns no rows. There is no `include`. `where` filters the rows that come back and does not cut the walk short. `ltree` is not required. `sync(id, relation, ids)` makes a to-many relation hold exactly those ids. It locks, then writes. A join table gains and loses link rows. A nullable foreign key is set or cleared, and the related row stays. See [known limits](/docs/reference/known-limits).

```ts title="tree.ts"
import { connect } from "okmodel/pg/postgresjs";
import { many, schema, table, t } from "okmodel/pg";

const nodes = table(
  "nodes",
  {
    id: t.identity(),
    parentId: t.bigint().nullable().references("nodes"),
    name: t.text(),
  },
  { relations: { children: many("nodes", "parentId") } },
);
const app = schema({ tables: [nodes] });

export async function below(url: string, id: string): Promise<void> {
  await using db = connect(url, { schema: app });
  const rows = await db.nodes.descendants(id, { depth: 2, select: ["id", "name"] });
  const above = await db.nodes.ancestors(id, { select: ["id", "name"] });
  const links = await db.nodes.sync(id, "children", []);
  if (rows.length + above.length + links.added.length < 0) {
    throw new Error("the walk did not run");
  }
}
```

## A lot of rows

`stream()` walks the rows in keyset batches. Use it for an export or any read that should not load the whole set at once. It does not open a server cursor. The default batch is 1000. Pass `batch` as an integer from 1 to 2147483647. Each batch is a normal query, so leaving the loop does not hold a connection. The order is `orderBy`, then the primary key. Leave `orderBy` out and the rows follow the primary key. A table with no primary key is refused. `search` and a window in `select` are refused. `limit` is how many rows you want in total. `limit` 0 yields nothing and runs no query. `.all("export")` with no `limit` streams the set. Both together still honor `limit`. `select`, `include`, a preset, and the archive set work the same way they do on `page()`.

A row committed while the stream runs can show up, or not. For one snapshot of the primary, run it inside `tx({ isolation: "repeatable read" })`. That transaction holds the connection. When the client has replicas, the first batch chooses one endpoint and later batches stay there. They do not move to another replica if that one fails. `signal` stops the stream. `timeout` is the time for the whole stream, not a fresh budget on every batch. See [known limits](/docs/reference/known-limits).

```ts title="stream.ts"
import { connect } from "okmodel/pg/postgresjs";
import { schema, table, t } from "okmodel/pg";

const notes = table("notes", { id: t.identity(), title: t.text() });
const app = schema({ tables: [notes] });

export async function each(url: string): Promise<void> {
  await using db = connect(url, { schema: app });
  await db.tx({ isolation: "repeatable read" }, async (tx) => {
    for await (const row of tx.notes.find({}).all("export").stream({ batch: 500 })) {
      if (row.title === "") break;
    }
  });
}
```

## Insert a row, or read the one that is there

`insert` with `{ onConflict: { on, return: true } }` inserts the row. When that unique is already taken, it reads the existing row and does not change it. Use it when two requests may create the same tag, slug, or external id, and both should receive the one row. The lookup runs only when the insert returned nothing. A second request that commits while the first is waiting is still visible, so both callers get the row. An update list that names the same target twice is refused. A target that matches nothing is not an error: `count` is the rows changed. An empty `set` is refused. An empty list runs no statement. See [known limits](/docs/reference/known-limits).

```ts title="create.ts"
import { connect } from "okmodel/pg/postgresjs";
import { schema, table, t } from "okmodel/pg";

const tags = table("tags", { id: t.identity(), name: t.text().unique() });
const app = schema({ tables: [tags] });

export async function once(url: string): Promise<void> {
  await using db = connect(url, { schema: app });
  const row = await db.tags.insert({ name: "ship" }, { onConflict: { on: "name", return: true } });
  if (row.name !== "ship") throw new Error("the row did not come back");
}
```

## Claim a free row

`update` with `lock: "skip"` and `limit` changes up to that many matching rows and leaves rows another transaction already holds. Use it for a worker that should take one pending job without waiting. The database chooses which unlocked rows. There is no `orderBy` on a claim. `limit` without `lock: "skip"` is refused, and `lock: "skip"` without `limit` is refused. `lock: "skip"` on a read is refused: a read uses `lock: "update"` or `"share"` and `wait: "nowait"` or `"skip"` inside `tx()`. `wait` on an update is refused. A claim cannot change a path-tenancy parent in the same statement. `inc` adds to a number or bigint column in the same kind of write. A text column is refused. See [known limits](/docs/reference/known-limits).

```ts title="claim.ts"
import { connect } from "okmodel/pg/postgresjs";
import { schema, table, t } from "okmodel/pg";

const jobs = table("jobs", {
  id: t.identity(),
  status: t.text(),
});
const app = schema({ tables: [jobs] });

export async function take(url: string): Promise<void> {
  await using db = connect(url, { schema: app });
  const claimed = await db.jobs.update({
    where: { status: "pending" },
    set: { status: "running" },
    limit: 1,
    lock: "skip",
  });
  if (claimed.count < 0) throw new Error("the claim did not run");
}
```

## Group by a period

`bucket(column, unit, { tz, as })` goes in `aggregate` `groupBy`, beside field names. Use it for a count per day or per hour. `as` is required and names the result key. Units are `second`, `minute`, `hour`, `day`, `week`, `month`, `quarter`, and `year`. A day or longer comes back as `Temporal.PlainDate`, the local date the period starts. A second, minute, or hour comes back as `Temporal.Instant`. `tz` is required for `timestamptz` and refused for `date`. A timestamp without a zone is refused. `weekStart` applies only to `week` and defaults to Monday. A NULL timestamp is one group: the key is present and the value is null. There is no gap filling, and `aggregate` has no `having`. A grouped aggregate needs `limit`, or `.all(reason)` for every group. An empty `as`, or an `as` that clashes with a group field or with count, sum, avg, min, or max, is refused. See [known limits](/docs/reference/known-limits).

```ts title="buckets.ts"
import { connect } from "okmodel/pg/postgresjs";
import { bucket, schema, table, t } from "okmodel/pg";

const events = table("events", { id: t.identity(), at: t.timestamptz() });
const app = schema({ tables: [events] });

export async function perDay(url: string): Promise<void> {
  await using db = connect(url, { schema: app });
  const days = await db.events.aggregate({
    groupBy: [bucket("at", "day", { tz: "UTC", as: "day" })],
    count: true,
    limit: 31,
  });
  if (days.length < 0) throw new Error("the bucket did not run");
}
```

## How a search column works

The column is a `tsvector`: the document Postgres matches, not the plain text. You fill it when you write, often with `to_tsvector` in `.generated(...)`. `natural` compiles to `websearch_to_tsquery`. `all-words` is `plainto_tsquery`, `phrase` is `phraseto_tsquery`, and `advanced` is `to_tsquery`. Ranking is `ts_rank`, highest first. `find({ search })` emits that same match and that same rank. A highlighted snippet, a search of a plain text column, a helper that writes the `to_tsvector` expression, and a ranked `page()` are not in this version.
