```ts title="view.ts"
import { not, schema, table, t } from "okmodel/pg";
import { view } from "okmodel/view";

const notes = table("notes", {
  id: t.identity(),
  title: t.text(),
});

const openNotes = view("open_notes", { tables: [notes] }, (q) =>
  q.notes.find({
    select: ["id", "title"],
    where: { title: not(null) },
  }),
);

export default schema({
  tables: [notes],
  views: [openNotes],
});
```

## What it does

`views` is one list of `view()` and `materializedView()` from `okmodel/view`. The body is the query API. `q` has only the tables and views named in `tables`. Reading any other name is a type error, and a cycle in that list is OKM1900.

`db.views` is the read handle for both kinds. The client name is the camelCase of the view name, so `open_notes` is `openNotes`. A plain view has `find`, `one`, `count`, and `exists`. A materialized view also has `refresh()`. There is no insert or update.

Column type and nullability come from the expression or the column builder. PostgreSQL stores neither for a view. A column left non-null throws OKM1901 when a row comes back NULL. `okm pull` writes `q.sql` and `.nullable()` on every column for that reason.

Every view is `security_invoker` unless you pass `{ definer: "reason" }`. A definer view also sets `security_barrier`. The reason is not stored.

#### Check option [feature="view.checkOption"]

`checkOption` is `local` or `cascaded` and is enforced by the database. `orderBy` without `limit` is OKM1120.

### view [feature="view.typed"]



`q.sql` is the fallback for a union, a CTE, `LATERAL`, or a recursive view.

```ts title="sql-view.ts"
import { schema, sql, table, t } from "okmodel/pg";
import { view } from "okmodel/view";

const notes = table("notes", { id: t.identity(), title: t.text() });

const titled = view("titled", { tables: [notes] }, (q) =>
  q.sql({
    columns: [
      { name: "id", type: t.bigint() },
      { name: "title", type: t.text().nullable() },
    ],
    query: sql`select id, title from notes`,
  }),
);

export default schema({ tables: [notes], views: [titled] });
```

### materialized [feature="view.materialized"]

#### Refresh [feature="matview.refresh"]

`refresh()` reloads a materialized view. `materializedView()` is created `with no data`. `populate: "now"` (the default) refreshes it in the plan. `populate: "later"` does not. `refresh: "concurrently"` needs a unique index on plain columns: no expression and no predicate, or the declaration is OKM1822. `indexes` is the same `index()` call a table uses. `using`, `with`, and `tablespace` are stored when they are not the database default.

```ts title="materialized.ts"
import { connect } from "okmodel/pg/postgresjs";
import { index, schema, table, t } from "okmodel/pg";
import { materializedView } from "okmodel/view";

const notes = table("notes", { id: t.identity(), title: t.text() });

const noteCounts = materializedView(
  "note_counts",
  {
    tables: [notes],
    refresh: "concurrently",
    indexes: (columns) => [index(columns.title).unique()],
  },
  (q) => q.notes.aggregate({ groupBy: ["title"], select: { n: { count: true } }, limit: 100 }),
);

const app = schema({ tables: [notes], views: [noteCounts] });

export async function reload(url: string) {
  await using db = connect(url, { schema: app });
  await db.views.noteCounts.refresh();
  return await db.views.noteCounts.find({ limit: 1 });
}
```

Postgres does not store `refresh` or `populate`. Introspection leaves them unset, and a later plan does not recreate the view only because they were declared.

### security [feature="view.security"]

The default is `with (security_invoker = true)`, including under column tenancy. `{ definer: "reason" }` omits the invoker option and sets `security_barrier`. `okm doctor` warns OKM1902 when the session role cannot select a base table of a security-invoker view.

### tenancy

A view that reads a tenant table has to expose the tenant key, or pass `global("reason")`. The reason is stored for `inspect()` and is not part of the catalog hash.

```ts title="tenancy.ts"
import { columnTenancy, global } from "okmodel/tenancy";
import { schema, table, t } from "okmodel/pg";
import { view } from "okmodel/view";

const notes = table("notes", { id: t.identity(), title: t.text() });

const openNotes = view("open_notes", { tables: [notes] }, (q) =>
  q.notes.find({ select: ["id", "title", "tenantId"] }),
);

const shared = view("shared", { tables: [notes], tenancy: global("counts are shared") }, (q) =>
  q.notes.aggregate({ select: { n: { count: true } } }),
);

export default schema({
  tables: [notes],
  tenancy: columnTenancy({ key: "tenantId", type: "uuid" }),
  views: [openNotes, shared],
});
```

<Callout type="error" title="OKM1820">
A tenant view that hides the key is `View open_notes reads a tenant table and does not expose tenantId.`
</Callout>

### planning [feature="view.dependencyOrder"]

`CREATE OR REPLACE` is used only when the new columns are the old columns plus appended ones, and the statement restates every option. A replace resets an option that was not restated. A pure column rename is `ALTER VIEW RENAME COLUMN`. Anything else drops and recreates dependents in dependency order. A base column type change drops dependent views and materialized views, alters the column, and recreates them.

### recipes

These three are not emitted. Each needs a proof on the server you run before it becomes a plan step.

**Side-by-side rebuild.** When a materialized view's query changes and nothing else depends on it, build the new query under a temporary name, populate it, then rename the old one aside and the new one into place in one short transaction. If a view depends on it, drop that chain and recreate it in dependency order instead. The rename swap is not atomic with readers of the old name across the two renames, so keep the transaction short.

**Scheduled refresh.** `refresh: { mode: "concurrently", every: "*/5 * * * *" }` is OKM1120. On a server that has the pg_cron pack, schedule `refresh materialized view concurrently` as the database owner. Jobs show up in `cron.job` and `cron.job_run_details`. The view still needs a plain unique index.

**INSTEAD OF.** A trigger with `timing: "instead"` prints `INSTEAD OF`, and it belongs on a view. `trigger({ on })` takes a table today. Declare the trigger in SQL with `q.sql` left unused, or add the view to `on` in a later change once a real server has run an `INSTEAD OF` row trigger against that view.
