---
title: "Procedures"
description: "CALL, OUT arguments, and procedures that commit."
---

A procedure is `fn()` with `kind: "procedure"`. It is not a second builder. PostgREST and Supabase expose functions only (`POST /rpc/<name>`). They do not expose `CALL`. Use a function when an HTTP API has to run the routine. Use a procedure when the app calls it, when it has `OUT` arguments, or when it commits.

`returns` and `volatility` are not procedure options. The identity is the name plus the `IN` and `INOUT` types. `OUT` is not part of the identity. Two routines with the same name and the same `IN` and `INOUT` types are OKM1023, whether they are functions, procedures, or one of each. Changing the kind is drop plus create.

Argument types are column builders. `t.text()`, `t.integer()`, `t.bigint()`. A string such as `"text"` is not accepted.

### Typed body

`(args, query) => [statements]` compiles to `LANGUAGE sql` and `BEGIN ATOMIC`. The callback runs when the catalog is built, not when the module loads. Every parameter is printed as `"procedure"."argument"`. An unqualified parameter that matches a column name is the column, and the argument is silently ignored. The last statement is a query. Its columns are assigned to the `OUT` parameters, in order.

```ts title="close-one.ts"
import { fn } from "okmodel/fn";
import { schema, table, t } from "okmodel/pg";

const accounts = table("accounts", {
  id: t.text().primaryKey(),
  balance: t.integer(),
});

const closeOne = fn("close_one", {
  kind: "procedure",
  arguments: [
    { name: "account", type: t.text() },
    { name: "closed", type: t.integer(), mode: "out" },
  ],
  body: (args, query) => [
    query.accounts.update({
      set: { balance: 0 },
      where: { id: args.account },
    }),
    query.sql("select 1"),
  ],
});

export default schema({ tables: [accounts], functions: [closeOne] });
```

`query.accounts.find`, `aggregate`, `insert`, `update`, and `delete` print SQL. They do not connect. `query.sql` is a statement the printer cannot express.

### Handle body

`(handle) => handle.sql\`...\`` is for plpgsql, including a body that commits. The callback runs when the catalog is built. Interpolating a table records `dependsOn`. `handle.arg("account")` is the qualified parameter. `handle.reads(table)` records a table the text does not interpolate.

### sql text

A string or `sql\`...\`` is stored as written. `okm pull` writes this form. A language other than `sql` and `plpgsql` is not pulled yet.

### run

`procedure.run(db, args, options?)` sends `CALL` in named notation. Each `IN` and `INOUT` value is `$n::type`. Every `OUT` parameter is `NULL::type`, which PostgreSQL requires. The result is an object of `OUT` and `INOUT` values, or `undefined` when there are none. `options` is `timeout`, `signal`, and `onNotice`.

`bigint` and `numeric` results arrive as strings. Configured drivers hand `timestamptz` as text, and the codec returns the mode you declared (`"iso"` is a string, `"date"` is a `Date`). A driver that has already parsed `timestamptz` into a `Date` is accepted before the codec. Bun.sql does not surface notices. postgres.js, node-postgres, and PGlite do, and `onNotice` receives them.

```ts no-check="needs a connected client"
const closed = await closeOne.run(db, { account: "a" });
```

Missing a required argument is OKM1120.

### commits

`commits: true` means the body commits. It is refused, before any SQL is sent, when `run` is inside a transaction (PostgreSQL 2D000, reported as OKM1551). It is also refused with `security: "definer"`, with `searchPath`, with a `BEGIN ATOMIC` body, and when the flag disagrees with `COMMIT` or `ROLLBACK` in the body. `COMMIT` or `ROLLBACK` inside an `EXCEPTION` block is warning OKM2126. The language defaults to `plpgsql` when `commits` is set.

A batch writes a checkpoint, commits every N rows, and can be called again from that checkpoint. Cancelling the call keeps the batches that already committed. The next call reads the checkpoint and continues.

```ts title="take-batch.ts"
import { fn } from "okmodel/fn";
import { schema, table, t } from "okmodel/pg";

const batches = table("batches", { n: t.integer() });

const takeBatch = fn("take_batch", {
  kind: "procedure",
  commits: true,
  dependsOn: [batches],
  body: `begin
  insert into batches (n) values (1);
  commit;
  insert into batches (n) values (2);
  commit;
end`,
});

export default schema({ tables: [batches], functions: [takeBatch] });
```

```ts no-check="needs a connected client"
await takeBatch.run(db, {});
```

`CALL` outside a transaction commits through PgBouncer transaction pooling. `okm call --rollback` is refused when the procedure commits, because a rollback would not undo those commits.

### Transactions

A procedure without `commits` joins the caller's transaction. `db.tx(() => procedure.run(db, args))` rolls the work back with the transaction. A procedure with `commits` must be called on the client, outside `db.tx()`.

Dropping a table that a `BEGIN ATOMIC` body uses is PostgreSQL 2BP01 while the procedure exists. The plan drops the procedure first.

### Security

Every `security: "definer"` routine, procedure or function, is created with `REVOKE EXECUTE ... FROM PUBLIC` in the same transaction, then the grants you declared. The revoke is applied again after every recreate. `search_path` is still required (OKM1823). A definer procedure that touches a tenant table is OKM2125: the owner bypasses row security. OKM2112 still applies when a definer names a forced-RLS table.

```ts title="close-as-owner.ts"
import { fn } from "okmodel/fn";

fn("close_as_owner", {
  kind: "procedure",
  security: "definer",
  searchPath: "public",
  grants: { app: ["execute"] },
  language: "plpgsql",
  dependsOn: [],
  body: "begin null; end",
});
```

`grants` and `comment` use the same options as a function. The SQL is `GRANT ... ON PROCEDURE` and `COMMENT ON PROCEDURE`. `okm access` lists a procedure as `procedure <name>`.

### raises

`raises` names a SQLSTATE the body throws. `run` puts that name on `error.raised`. `error.code` stays the OKM code. `error.sqlstate`, `error.detail`, `error.hint`, and `error.constraint` come from PostgreSQL. An undeclared custom errcode, or a standard-class code, is warning OKM2127.

```ts title="refuse-closed.ts"
import { fn } from "okmodel/fn";
import { t } from "okmodel/pg";

const refuseClosed = fn("refuse_closed", {
  kind: "procedure",
  arguments: [{ name: "account", type: t.text() }],
  raises: { closed: "P0001" },
  language: "plpgsql",
  dependsOn: [],
  body: `begin
  raise exception 'closed' using errcode = 'P0001', detail = 'account', hint = 'retry';
end`,
});

export { refuseClosed };
```

### okm call

`okm call <routine> --arg name=value` reads types and defaults from the declaration and prints JSON. `--rollback` runs the call in a transaction and rolls it back. `--target` selects the target. `--rollback` is refused when the procedure commits.

`schedule` is not an API. pg_cron is not part of the test topology. Install it on the server and register the call there:

```sql
select cron.schedule('close-month', '0 3 * * *', $$call close_one('a', null)$$);
```

### PGlite

`connect` from `okmodel/pg/pglite` installs the same `run` slot. Apply the catalog, then call `procedure.run(db, args)`. PGlite speaks Postgres, so `CALL`, `OUT` arguments, and `BEGIN ATOMIC` use the same SQL. A committing procedure still cannot run inside `db.tx()`.

### Change

The same argument modes and types are `CREATE OR REPLACE`. A different mode, a different type, or a change between function and procedure is `DROP` plus `CREATE` in one migration. Grants and the comment are applied again. Replacing a routine does not leave the old overload behind.
