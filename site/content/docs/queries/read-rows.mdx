`page` returns the next rows, then distinct, stream, and explain.

## Page

`page` returns `{ items, next }`. `next` is `null` on the last page. Pass it back as `after` with the same `orderBy`. The cursor encodes that order.

When `orderBy` names no hidden or sensitive column, the cursor also carries the sort values of the last row, as the database wrote them. A timestamp keeps its microseconds, and a page stays stable while rows are inserted.

When `orderBy` names a hidden or sensitive column, the cursor carries only the primary key of that row. A composite key is a tuple of its columns. The cursor does not carry those sort values. The next page reads them back in the same query, under the same tenant and archive predicates. A row that is gone is `The cursor is no longer valid.`

| Input | Result |
| --- | --- |
| `limit` | Required. The page size. |
| omitted `after` | The first page. |
| `after` | The cursor from `next`. |
| `next` | `null` on the last page. |

### first

`limit` is required. Omit `after` for the first page.

```ts title="first.ts"
import { connect } from "okmodel/pg/postgresjs";
import { schema, table, t } from "okmodel/pg";

const notes = table("notes", { id: t.identity(), title: t.text() });
const app = schema({ tables: [notes] });

export async function first(url: string) {
  await using db = connect(url, { schema: app });
  return db.notes.page({ orderBy: { title: "asc" }, limit: 20 }); // [!code focus]
}
```

### next

Pass `next` back as `after`, with the same `orderBy`.

```ts title="page.ts"
import { connect } from "okmodel/pg/postgresjs";
import { schema, table, t } from "okmodel/pg";

const notes = table("notes", { id: t.identity(), title: t.text() });
const app = schema({ tables: [notes] });

export async function next(url: string, after: string | null) {
  await using db = connect(url, { schema: app });
  return db.notes.page({ orderBy: { title: "asc" }, limit: 20, after }); // [!code focus]
}
```

<Callout type="error" title="OKM1101">
Omitting `limit` is `page() needs a limit.`
</Callout>

<Callout type="error" title="OKM1130">
A cursor this call did not return is `after is not a cursor that page() returned.` A key cursor whose row is gone is `The cursor is no longer valid.`
</Callout>

## Order by a relation

`orderBy` can name more than one relation, and `page` keeps that order. A to-one column is a left join, so a row whose relation is missing stays in the result. A to-many relation orders by `count`, the number of related rows: `{ notes: { count: "desc" } }`. `find`, `one`, `stream`, and `page` accept it. The related table's tenant predicate and archive filter sit on the join, so another tenant or an archived row does not supply the sort value.

A page cursor carries each related sort value with the other sort values. A hidden or sensitive related column uses the primary-key cursor, and the next page reads the value back under the same predicates. A plain hidden related column is OKM1120.

```ts title="order-relation.ts"
import { connect } from "okmodel/pg/postgresjs";
import { one, schema, table, t } from "okmodel/pg";

const projects = table("projects", { id: t.identity(), name: t.text() });
const tasks = table(
  "tasks",
  {
    id: t.identity(),
    title: t.text(),
    projectId: t.integer().nullable().references("projects"),
  },
  { relations: { project: one("projects", "projectId") } },
);
const app = schema({ tables: [projects, tasks] });

export async function byProject(url: string) {
  await using db = connect(url, { schema: app });
  return db.tasks.find({ orderBy: { project: { name: "asc" } }, limit: 20 }); // [!code focus]
}
```

<Callout type="error" title="OKM1127">
orderBy on a relation is not available with distinct or distinctOn.
</Callout>

<Callout type="error" title="OKM1128">
orderBy on a relation is not available in aggregate.
</Callout>

## Distinct

`find` takes `distinct: true` with a `select`. It keeps one row per different combination of the selected fields, and NULL counts as one value. `orderBy` may name selected fields only. `distinctOn` is Postgres only: it keeps the first row of each key, so `orderBy` must start with the same keys and the keys after them pick the row. `include`, `search`, `page`, and `one` refuse both.

| Input | Result |
| --- | --- |
| `distinct: true` | One row per different combination of `select`. Needs `select`. |
| `distinctOn: [fields]` | The first row of each key under `orderBy`. Postgres only. |
| `orderBy` with `distinctOn` | Starts with the same keys. |

```ts title="distinct.ts"
import { connect } from "okmodel/pg/postgresjs";
import { schema, table, t } from "okmodel/pg";

const tasks = table("tasks", {
  id: t.identity(),
  status: t.text(),
  amount: t.integer().nullable(),
});
const app = schema({ tables: [tasks] });

export async function statuses(url: string) {
  await using db = connect(url, { schema: app });
  const kinds = await db.tasks.find({ distinct: true, select: ["status"], limit: 20 }); // [!code focus]
  const biggest = await db.tasks.find({
    distinctOn: ["status"], // [!code focus]
    orderBy: { status: "asc", amount: { dir: "desc", nulls: "last" } },
    limit: 20,
  });
  return { kinds, biggest };
}
```

<Callout type="error" title="OKM1120">
`distinctOn needs an orderBy that starts with status.`
</Callout>

## Stream

`.stream()` walks `find` in keyset batches. It does not open a server cursor. Leaving the loop does not hold a connection.

| Option | Result |
| --- | --- |
| `batch` | An integer from 1 to 2147483647. The default is 1000. |
| `limit` | The total. `0` yields nothing and runs no query. |
| `.all(reason)` | The set, with no `limit`. Both together still honor `limit`. |
| `orderBy` | Then the primary key. Omit it and the rows follow the primary key. |
| `timeout` | The time for the whole stream. On a driver that cannot cancel, the check is between batches. |
| `signal` | Stops the stream. |

`select`, `include`, a preset, and the archive set work as they do on `page()`. A row committed while the stream runs can show up, or not. The snapshot in the next example is a [transaction](/docs/queries/transactions#options). On a client with replicas, the first batch chooses the endpoint and later batches stay there.

### limit

`limit` is the total. `batch` is how many rows each query reads.

```ts title="stream.ts"
import { connect } from "okmodel/pg/postgresjs";
import { schema, table, t } from "okmodel/pg";

const notes = table("notes", { id: t.identity(), title: t.text() });
const app = schema({ tables: [notes] });

export async function titles(url: string): Promise<string[]> {
  await using db = connect(url, { schema: app });
  const out: string[] = [];
  for await (const row of db.notes.find({ limit: 20 }).stream({ batch: 20 })) { // [!code focus]
    out.push(row.title);
  }
  return out;
}
```

### snapshot

`.all(reason)` is the whole set. The call below is one snapshot. What that isolation does is [Transactions](/docs/queries/transactions#options).

```ts title="stream-all.ts"
import { connect } from "okmodel/pg/postgresjs";
import { schema, table, t } from "okmodel/pg";

const notes = table("notes", { id: t.identity(), title: t.text() });
const app = schema({ tables: [notes] });

export async function each(url: string): Promise<void> {
  await using db = connect(url, { schema: app });
  await db.tx({ isolation: "repeatable read" }, async (tx) => {
    for await (const row of tx.notes.find({}).all("export").stream({ batch: 500 })) { // [!code focus]
      if (row.title === "") break;
    }
  });
}
```

<Callout type="error" title="OKM1120">
A table with no primary key is refused. `one()`, `count()`, `exists()`, `search`, and a window are refused.
</Callout>

<Callout type="error" title="OKM1101">
A stream with no `limit` and no `.all(reason)` is refused.
</Callout>

<Callout type="error" title="OKM1121">
`batch` outside 1 to 2147483647 is refused. A `timeout` that is not a number above 0 is refused.
</Callout>

## Explain

`explain` describes a query you already built. Outside production it returns the `EXPLAIN` lines with the statement text and parameters. A hidden or sensitive parameter is `[redacted]` in `params` and in the plan text. Postgres still receives the real parameter, so the plan and its costs stay the ones it chose. An ordinary column stays in both. In production it does not send the statement: `plan` is null and `params` is empty.

```ts title="explain-notes.ts"
import { connect } from "okmodel/pg/postgresjs";
import { explain, schema, table, t } from "okmodel/pg";

const notes = table("notes", { id: t.id(), title: t.text() });
const app = schema({ tables: [notes] });

export async function plan(url: string) {
  await using db = connect(url, { schema: app });
  return explain(db.notes, db.notes.find({ limit: 1 })); // [!code focus]
}
```
