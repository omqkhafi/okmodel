You get a Worker that opens a client for each request, reads and writes a table on Neon, and closes the client when the response is done. It runs over WebSocket or HTTP, chosen by one variable.

## Runtime and driver

| | |
| --- | --- |
| Runtime | Cloudflare Workers with the `nodejs_compat` flag |
| Driver | `okmodel/pg/neon` + `@neondatabase/serverless` |
| Example | `examples/workers-neon` |

A Worker has no TCP socket for postgres.js, so this is the Neon driver. `connect` returns a promise, so the Worker awaits it. `okm` does not run in a Worker. Run migrations from Node.js or Bun on a machine with TCP to Postgres.

## Install

```sh
bun add okmodel @neondatabase/serverless
bun add -D wrangler miniflare
```

`wrangler.toml` must set `nodejs_compat`. `NEON_MODE` is a plain variable:

```toml title="wrangler.toml"
name = "okmodel-workers-neon"
main = "src/worker.ts"
compatibility_date = "2025-10-01"
compatibility_flags = ["nodejs_compat"]

[vars]
NEON_MODE = "websocket"
```

## `db` module and lifecycle

The client lives for one request. A Worker isolate can serve many requests, so do not keep a pool on the isolate. `openRequestDb` calls `connect` with the mode, and the Worker closes the client in `finally` with `ctx.waitUntil`, so closing does not delay the response.

```ts title="src/db.ts" no-check="imports ./schema.js, which re-exports a file outside the example root (shown below)"
/**
 * Per-request Neon client for Cloudflare Workers.
 *
 * Create inside `fetch`. Close with `ctx.waitUntil(db.close())` so the
 * isolate does not hold the pool across requests.
 */

import { connect, type NeonMode } from "okmodel/pg/neon";

import { app } from "./schema.js";

/**
 * Opens a Neon client for one request.
 *
 * @param url - Neon connection string
 * @param mode - `websocket` (default) or `http`
 */
export function openRequestDb(url: string, mode: NeonMode = "websocket") {
  return connect(url, { schema: app, mode });
}
```

`src/schema.ts` re-exports the table that every framework example shares from `examples/shared`:

```ts title="src/schema.ts" no-check="re-exports ../../shared/schema.js, which is outside the example root"
export { app, notes } from "../../shared/schema.js";
```

```ts title="shared/schema.ts"
/**
 * Shared notes table for framework examples.
 *
 * Each example imports this schema. Tests create an isolated database and
 * apply the matching SQL before booting the app.
 */

import { schema, table, t } from "okmodel/pg";

/** Notes table used by every framework example. */
export const notes = table("example_notes", {
  id: t.identity(),
  title: t.text(),
});

/** Schema for the examples. */
export const app = schema({ tables: [notes] });

/** SQL that creates {@link notes} on an empty database. */
export const NOTES_DDL = `
create table example_notes (
  id bigint generated by default as identity primary key,
  title text not null
);
`;
```

In your own Worker, define the table and `schema()` in `src/schema.ts` directly. `db.example_notes` exists because the table is named `example_notes`.

## Connection config

| Setting | Where | Notes |
| --- | --- | --- |
| `DATABASE_URL` | A Worker secret or binding | The Neon connection string. Set it with `bunx wrangler secret put DATABASE_URL`. For local `wrangler dev`, put it in `.dev.vars`. |
| `NEON_MODE` | `[vars]` in `wrangler.toml` | `websocket` or `http`. Unset means `websocket`. Any other value is an error. |

The Worker reads the mode before it opens a client. A value that is not `websocket`, `http`, or unset throws `NEON_MODE must be "websocket" or "http", got "<value>"` on every request, before any client is opened. That includes `GET /health`, so a typo fails loudly instead of falling back. The throw is uncaught, so the request ends as a 500 and the message goes to the Worker's logs. Miniflare shows it in the response body, and a deployed Worker shows Cloudflare's own error page instead. `examples/workers-neon/workers-neon.test.ts` runs the bundled Worker in Miniflare with `NEON_MODE` set to `ws` and asserts the 500 and the message, with no database.

| Mode | Behavior |
| --- | --- |
| `websocket` | A pool over WebSocket. `tx()` runs an interactive transaction. |
| `http` | One HTTP request per statement. `batch([...])` is one atomic transaction. `tx()` is [OKM1111](/docs/reference/errors#okm1111). |

A positive `timeout` on a call, on `tx()`, or on `batch()` is [OKM1120](/docs/reference/errors#okm1120) in both modes. [Drivers](/docs/operate/drivers#neon).

## One route that reads and writes

`GET /notes` returns up to 50 notes ordered by `id`. `POST /notes` takes `{ "title": "..." }` and returns the new row with status 201. `GET /health` returns `{ ok: true, mode }`. A body that is not JSON, or a missing or empty `title`, is a 400 with an `error` message. `id` is a string in the JSON.

The write shows the difference between the modes. In `websocket` mode the insert runs inside `db.tx(...)`. In `http` mode there is no interactive transaction, so the insert goes through `db.batch([...])`, which Neon sends as one atomic HTTP transaction.

| | `websocket` | `http` |
| --- | --- | --- |
| Write path in the example | `db.tx(async (tx) => tx.example_notes.insert({ title }))` | `db.batch([db.example_notes.insert({ title })])` |
| Result | The row the callback returns | An array with one result per statement, in order, so the example destructures `[row]` |
| Several writes that commit together | Several statements in one `tx` callback | Several statements in one `batch` array |
| Later statement needs an earlier result | Use `tx` and read the result in the callback | Not possible in one `batch`. Run them as separate calls, or switch to `websocket` |
| `tx()` | Supported | [OKM1111](/docs/reference/errors#okm1111) |

A single-row insert is atomic on its own in both modes. The example wraps it so the two paths are visible side by side. [Transactions](/docs/queries/transactions).

The request and response shapes are the same in both modes. `GET /health` is the one route that also reports the mode. Every request, including `/health` and a 404, opens a client first and closes it in `finally`. This page has no captured output for these routes (Manual, shape only): the example needs a Neon database, and none was available when the page was written. The bodies the code produces are:

```json
{ "ok": true, "mode": "websocket" }
```

```json
{ "id": "1", "title": "hello" }
```

```json
[{ "id": "1", "title": "hello" }]
```

| Request | Status | Body |
| --- | --- | --- |
| `GET /health` | 200 | `{"ok":true,"mode":"websocket"}` or `"http"` |
| `POST /notes` with `{"title":"hello"}` | 201 | the new row, `id` as a string |
| `GET /notes` | 200 | an array of rows, oldest first |
| `POST /notes` with `{}` | 400 | `{"error":"title is required"}` |
| `POST /notes` with a body that is not JSON | 400 | `{"error":"body must be JSON"}` |
| any other path or method | 404 | `not found` |

```ts title="src/worker.ts" no-check="uses the Workers ExecutionContext type, and imports ./db.js, which needs the schema file outside the example root"
/**
 * Cloudflare Worker: per-request Neon connect, read and write routes.
 *
 * Requires `nodejs_compat`. WebSocket mode supports `tx()`. HTTP mode uses
 * `batch()` and refuses `tx()` (OKM1111).
 */

import { openRequestDb } from "./db.js";

export interface Env {
  DATABASE_URL: string;
  NEON_MODE?: string;
}

function neonMode(value: string | undefined): "websocket" | "http" {
  if (value === undefined || value === "websocket") return "websocket";
  if (value === "http") return "http";
  throw new Error(`NEON_MODE must be "websocket" or "http", got ${JSON.stringify(value)}`);
}

export default {
  async fetch(request: Request, env: Env, ctx: ExecutionContext): Promise<Response> {
    const mode = neonMode(env.NEON_MODE);
    const db = await openRequestDb(env.DATABASE_URL, mode);
    try {
      const url = new URL(request.url);
      if (request.method === "GET" && url.pathname === "/health") {
        return Response.json({ ok: true, mode });
      }
      if (request.method === "GET" && url.pathname === "/notes") {
        const rows = await db.example_notes.find({
          orderBy: { id: "asc" },
          limit: 50,
        });
        return Response.json(rows);
      }
      if (request.method === "POST" && url.pathname === "/notes") {
        let body: unknown;
        try {
          body = await request.json();
        } catch {
          return Response.json({ error: "body must be JSON" }, { status: 400 });
        }
        const title =
          body !== null && typeof body === "object" && "title" in body
            ? (body as { title: unknown }).title
            : undefined;
        if (typeof title !== "string" || title.length === 0) {
          return Response.json({ error: "title is required" }, { status: 400 });
        }
        if (mode === "websocket") {
          const row = await db.tx(async (tx) => tx.example_notes.insert({ title }));
          return Response.json(row, { status: 201 });
        }
        // HTTP mode has no interactive transaction; batch is one atomic unit.
        const [row] = await db.batch([db.example_notes.insert({ title })]);
        return Response.json(row, { status: 201 });
      }
      return new Response("not found", { status: 404 });
    } finally {
      ctx.waitUntil(Promise.resolve(db.close()));
    }
  },
};
```

## Dev and test

Neon is a hosted service, so there is no local Postgres step here. Use a Neon database you can drop, such as a branch, and create the table on it. In your Worker project, add an `okmodel.config.ts` next to `package.json` and run `okm` from your machine with the direct (non-pooler) Neon host:

```ts title="okmodel.config.ts"
import { defineConfig } from "okmodel/migrate";

export default defineConfig({
  schema: "./src/schema.ts",
  database: process.env.DATABASE_URL!,
});
```

```sh
export DATABASE_URL='postgres://user:pass@ep-example.region.aws.neon.tech/neondb?sslmode=require'
bunx okm push
```

`okm push` writes no SQL file and suits a database you can drop. For a database you will deploy, run `bunx okm generate init` then `bunx okm migrate apply`, and commit `migrations/`. `okm` refuses a pooler host unless you pass `--allow-pooler`. [Migrate commands](/docs/reference/cli/migrate).

Then run the Worker. Put the same `DATABASE_URL` in `.dev.vars`, and `NEON_MODE` comes from `wrangler.toml`:

```sh
bunx wrangler dev
```

`wrangler dev` listens on port 8787 by default. Call it from another terminal:

```sh
curl -i http://localhost:8787/health
curl -i -X POST http://localhost:8787/notes -H 'content-type: application/json' -d '{"title":"hello"}'
curl -i http://localhost:8787/notes
```

The statuses and bodies are in the table under One route that reads and writes. To check the mode switch, change `NEON_MODE` in `wrangler.toml` to `http`, restart `wrangler dev`, and confirm `GET /health` reports `"mode":"http"` and the `POST` still answers 201 through `batch`.

The example's tests live in `examples/workers-neon/workers-neon.test.ts`. The bundle test and the `NEON_MODE` test need no database. The live test needs a Neon URL, and it drops and recreates `example_notes` there, so give it a throwaway branch:

```sh
bun run build
bun install --cwd examples/workers-neon
cd examples/workers-neon
bun test ./workers-neon.test.ts
OKM_EXAMPLES_NIGHTLY=1 NEON_URL='postgres://...' bun test ./workers-neon.test.ts
```

Without `OKM_EXAMPLES_NIGHTLY=1` and `NEON_URL`, the live test is skipped. The live test creates the table with the Neon `sql` tag itself and does not run `okm`.

## Deploy and migrate-on-deploy

```sh
bunx wrangler secret put DATABASE_URL
bunx wrangler deploy
```

Apply migrations from a job that has TCP to Postgres, before `wrangler deploy`, with `DATABASE_URL` pointing at the direct Neon host:

```sh
bunx okm migrate apply
bunx wrangler deploy
```

A Worker deployed against a database that has not been migrated fails its first check with OKM1520. A migration that only adds things lets the old version keep serving while the new one rolls out. [Migrations in CI](/docs/guides/migrations-in-ci), [Environments](/docs/migrations/environments).

## Limits and gotchas

- `nodejs_compat` is required. CI checks that `wrangler.toml` contains it.
- Create the client inside `fetch` and close it with `ctx.waitUntil`. Do not hold one across requests.
- In `http` mode use `batch`, not `tx`.
- A suspended Neon compute cold-starts on the first request. OKModel does not treat that wait as a result.
- A transaction-mode pooler does not promise session state. Leave `prepared` unset. [Drivers](/docs/operate/drivers#neon).
- Deno is unsupported, and there is no D1 adapter.

| Symptom | Cause | Fix |
| --- | --- | --- |
| 500 and `NEON_MODE must be "websocket" or "http", got ...` in the logs | The variable is set to something else, and every route throws, `/health` included | Set `websocket`, `http`, or remove it. |
| [OKM1111](/docs/reference/errors#okm1111) on `tx()` | `NEON_MODE` is `http` | Use `batch([...])`, or switch to `websocket`. |
| [OKM1120](/docs/reference/errors#okm1120) on a call with `timeout` | Neon refuses a positive `timeout` | Remove `timeout`. |
| [OKM1520](/docs/reference/errors#okm1520) `The database is behind the app` | The Worker was deployed before `okm migrate apply` | Apply the migrations, then deploy. |
| [OKM1101](/docs/reference/errors#okm1101) `find() needs a limit.` | A read with no `limit` | Pass `limit`, as the example route does. |

## Verification

**Evidence level: CI for the bundle, Nightly for reads and writes.**

- **CI** — `examples/workers-neon/workers-neon.test.ts` runs `wrangler deploy --dry-run`, checks that the compressed upload is under Cloudflare's documented free-plan limit, and checks that `wrangler.toml` contains `nodejs_compat`. A second test runs the bundle in Miniflare with `NEON_MODE` set to `ws` and asserts a 500 whose body carries the `NEON_MODE must be ...` message. Neither needs a database. It runs in the `examples / frameworks` job on pull requests that touch `examples/`, the runtime, the dialects, or the Frameworks pages, and after each merge.
- **Nightly** — the same file's live test runs the bundled Worker in Miniflare (workerd) against a real Neon database. For `http` and then `websocket` mode it calls `POST /notes` (201) and `GET /notes`. It runs only on the scheduled run, with `OKM_EXAMPLES_NIGHTLY=1` and the `NEON_URL` secret. A pull request does not run it, and it is skipped when either is missing.
- **Not covered** — a deployed Worker, `okm push` and `okm migrate apply` against Neon, and cold starts of a suspended compute.
