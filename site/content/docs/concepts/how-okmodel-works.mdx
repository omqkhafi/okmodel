One `schema()` call is the source. The types, the queries, the migrations, the drift check, and the check constraints are read from that object.

## The problem

A table that lives in three places drifts. The type names one column, a query sends another, and a migration creates a third. Nothing in the project is left to notice.

## How OKModel handles it

`schema()` compiles the tables and returns one value. That value holds the catalog, and it holds the table names the client is typed from. `connect` requires this value. Each table becomes a set of calls on the client.

`okm generate` and `okm migrate plan` diff the previous catalog snapshot against the catalog this call just built. A check is SQL text stored on the table. `okm check` and `okm migrate check` read that same catalog.

`defineConfig` is the tooling: targets, paths, and roles. `connect` is the runtime. The schema is the model both of them read.

## Limits and trade-offs

The catalog hash does not depend on table order. The emitted interfaces do. Swapping two tables leaves the hash the same and changes the order of those interfaces. That split is [The schema](/docs/schema/the-schema).

Roles and grants are not fields of `schema()`. When the config names `roles`, the tooling attaches them before a plan or a check. `connect` hashes the schema catalog without those privileges.

A query is planned when you call it. The schema does not store the SQL of `find`.
