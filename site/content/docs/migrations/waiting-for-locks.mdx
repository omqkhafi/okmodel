---
title: Waiting for locks
description: How okm migrate apply waits for a lock, what it retries, and how it names the session that holds the lock.
---

A step that needs a lock somebody else holds waits for it. `okm migrate apply` does not wait forever and does not give up at the first refusal. It tries again in a new transaction until `--lock-wait` is spent, and when it gives up it says who holds the lock.

Postgres: native. Proof passes (`apply waits, retries, and succeeds when the holder commits inside the window`).

## What is retried

Only SQLSTATE `55P03`, lock not available. A deadlock (`40P01`), a statement timeout (`57014`), and every other error stop the step at once.

Each attempt is a new transaction that starts with a local `lock_timeout`. An attempt that fails rolls back, so a retry never repeats half a step. A step that cannot share a transaction, such as `CREATE INDEX CONCURRENTLY`, retries as a new statement. Its `lock_timeout` is a session setting. It is set only on a connection that passed the [pooler check](/docs/reference/errors#okm1854), and it is put back and read again when apply ends. Behind `--allow-pooler` a session setting can be lost or reach another client, so apply refuses such a step before it runs.

| Flag | Meaning | Default |
| --- | --- | --- |
| `--lock-timeout <duration>` | How long one attempt waits for a lock. | `1s` |
| `--lock-wait <duration>` | How long a blocked step keeps retrying, in total. `0` tries once. | `2m` |

A duration is `500`, `500ms`, `30s`, or `2m`. A bare number is milliseconds. `--lock-timeout` covers the time to get a lock. It does not cover the time a long statement takes once it has the lock: that is `--statement-timeout`.

## When it gives up

```text
Migration 0001_alter failed at step 1: I could not get a lock after 7 attempts over 1.5 s.
Held by pid <pid> (lock-holder), idle in a transaction for <age>.
I did not touch any of them.
Nothing was changed.
```

Apply names up to five holders, one query on `pg_locks`, `pg_stat_activity`, and `pg_blocking_pids`. It recognises another `okm apply`, autovacuum, a prepared transaction (it has no pid, so the line gives its name), and a session that is idle in a transaction. It never cancels or ends a session. The pid is there for a person to decide.

On a terminal, each holder's last query follows, cut to one line. It is never in `--json` and never in a log. A role that cannot read another role's query is told so.

The step stays as written and nothing is recorded, so running `okm migrate apply` again is safe. Finished steps are not repeated.

## In `--json`

A run that never waits prints exactly what it printed before. A run that waited and then finished adds `attempts` and `waitedMs` to `data`. A step that gave up adds `attempts`, `waitedMs`, and `blockedBy` to its entry in `errors`, with `retryable: true`. The exit code does not change.

```json
{
  "retryable": true,
  "attempts": 7,
  "waitedMs": 1500,
  "blockedBy": [
    { "pid": 4242, "application": "lock-holder", "state": "idle in transaction", "ageMs": 61000, "kind": "idle-in-transaction" }
  ]
}
```

`kind` is `okm-apply`, `autovacuum`, `prepared-transaction`, `idle-in-transaction`, `active`, or `other`. A prepared transaction has `pid` 0.

Fail fast with `--lock-wait 0`:

```bash
bunx okm migrate apply --lock-wait 0
```

## Large tables

Some steps do more than wait for a lock. A `blocking` step holds a lock that keeps readers and writers out for the whole build and has no online form. A `rewrite` step rewrites the table under `ACCESS EXCLUSIVE`. A migration file marks such a step with a `-- weight:` line:

```sql
-- class: expand
-- name: tasks_id_exclusive

-- class: expand
-- kind: add-constraint
-- action: ddl
-- lock: ACCESS EXCLUSIVE
-- weight: blocking
alter table "public"."tasks" add constraint tasks_id_exclusive exclude using btree (id with =);
```

On a table of up to 100,000 rows nothing changes. Over that, `okm migrate apply` and `okm push` stop before their first step, with `Nothing was changed.`, and print the estimate, unless you pass `--allow-blocking`:

```bash
bunx okm migrate apply --allow-blocking
```

The flag means downtime, not data loss. It is not `--allow-protected`, which is about steps that can lose data, and one does not imply the other.

The row count is taken on the target when apply starts, not when the plan was printed, so a table that grew in between is counted as it is. Postgres counts at most 100,001 rows in 2 seconds, so a bigger table reads as `100,001 or more` and its estimate says `at least`. `okm migrate plan` prints the same estimate on the lock line, from `pg_class.reltuples`, or the bounded count when the table has never been analyzed.

The duration is an estimate, good to an order of magnitude: about 45 seconds per million rows for `blocking`, and about 1.3 seconds per million rows for a `rewrite` that changes a column type. It was measured on real servers and is not a promise for yours.

`--lock-timeout` and `--lock-wait` cover getting the lock. They do not cover the build that follows, which runs under `--statement-timeout`.

In `--json`, a step has `weight`, and with a target it also has `estimatedRows` and `estimateMs`. The refusal is `OKM1847`, with `retryable: false` and exit code 4.
