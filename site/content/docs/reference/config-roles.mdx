---
title: "Roles"
description: "Roles, logins, and keyed grants. The config holds names, never a password."
---

`roles` names the migration role, the application role, and any other role. Keys are free. `migration`, `app`, and `reporting` keep their meaning. The config holds no password and no URL.

```ts
roles: {
  migration: { name: "okm_migrate", env: "MIGRATE_DATABASE_URL" },
  app: { name: "okm_app", env: "APP_DATABASE_URL", connectionLimit: 20 },
  reporting: { name: "okm_read", env: "REPORTING_DATABASE_URL" },
  worker: { name: "okm_worker", env: "WORKER_DATABASE_URL" },
}
```

`env` is the name of the variable that holds that role's URL. With `env`, `okm roles apply` creates a login role when the name is missing. Without `env`, it creates a `NOLOGIN` group. An existing role keeps the database's login flag and its password.

## Cycle

1. Add `roles` to `okmodel.config.ts`.
2. Set each URL variable. `okm roles generate` prints random URLs once, or writes them to a git-ignored file with mode 0600.
3. `okm roles apply --admin-env ADMIN_DATABASE_URL` creates missing roles. The admin URL is the variable, never an argument.
4. `okm migrate apply` checks that every named role exists, then grants.
5. The application connects with the app URL.
6. `okm roles status` reads attributes, one login each, and unmanaged roles. JSON has no secrets.
7. To rotate, add a second login (`okm_app_b`), grant it the same privileges, move traffic, then retire the first. There is no built-in rotate.

`okm roles set-password <role> --admin-env NAME` is the only password change. The password is a client SCRAM-SHA-256 verifier. If the server refuses a client verifier, it says so and the next invocation passes `--plain`. There is no silent plaintext fallback.

A password under 16 characters, or a password that is the same half twice, asks `[c]` continue, `[g]` generate, `[x]` cancel. A local host does not ask. Without a terminal, pass `--accept-weak-password` or `--generate` with `--env-file`.

## Grants

Grants sit on the object. Keys are role keys.

```ts
table("docs", {
  id: t.text().primaryKey(),
  title: t.text(),
}, {
  grants: {
    app: "write",
    reporting: { select: ["id", "title"] },
    audit: ["select"],
  },
})
```

`"read"` is select. `"write"` is select, insert, update, and delete. A materialized view is `"read"` or `"maintain"`. `"all"` is refused. Objects without `grants` keep the baseline: `app` receives DML, and `reporting` receives select. Objects this catalog does not manage, and roles it does not declare, are not changed. `PUBLIC` is explicit and needs `--allow-protected`. There is no `WITH GRANT OPTION`.

Default privileges are not emitted. An identity column needs no sequence grant. A `serial` column does. Grant the parent of a partition, not the children. `TRUNCATE` ignores row security.

A non-owner refresh of a materialized view is `MAINTAIN` when `minPostgres` is 17 or later. On 15 and 16 the plan adds `okm_refresh_<name>()`, `SECURITY DEFINER`, with `search_path` pinned, and grants execute to the role.

## Providers

| Provider | What a real run showed |
| --- | --- |
| Neon | PostgreSQL 19.0. The admin login is a `neon_superuser` member, not a superuser. It refuses a client SCRAM verifier, so use `--plain`. The pooled URL is a transaction pooler. Roles created through SQL are visible on a replica within about 2 seconds. |
| Supabase | PostgreSQL 17.12. The login role `postgres` is not a superuser. It accepts a client verifier. Pooler logins need the `role.projectref` username. `statement_timeout` defaults to 2 minutes. |
| Amazon RDS | Not verified. |
| Heroku | Not verified. |

Roles are cluster-wide, so they are created by `okm roles apply`, not inside a migration. Migrations use a direct URL. `okm doctor` warns when the migration URL looks pooled. A single idle client that keeps one backend pid is not proof: a transaction pooler does that until several clients run at once. When a step needs a session setting outside a transaction, and no URL signal matched, okmodel opens eight clients together. Each runs a few statements while the others run and reads `pg_backend_pid()`. A pid that changes, or fewer backends than clients, means pooled. One stable pid per client is proven direct, and only then is the session form used. The same probe runs for `okm doctor` and for a login result the password check cannot classify. A URL that already matches a pooler signal is not probed.
