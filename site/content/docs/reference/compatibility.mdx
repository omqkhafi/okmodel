---
title: Compatibility
description: Driver, error, and transaction results for postgres.js, node-postgres, Bun.sql, and PGlite.
---

The same suite runs against postgres.js, node-postgres, Bun.sql, and PGlite. `pass` means the case ran and matched. `skip` means the adapter does not offer that behaviour. `fail` means it ran and did not match. `not-run` means the suite did not reach it. The command is [`okm driver test`](/docs/reference/cli/check#driver-test). The cells below are generated from `tests/driver-suite.test.ts` and `tests/error-suite.test.ts`. The floor is [Minimum Postgres](/docs/schema/the-schema#minimum-postgres).

Supported majors are Postgres 15, 16, 17, and 18. The floor is 15: Postgres 13 is past end of life, 14 ends in November 2026, and 15 gives us features we can use later. `connect()` refuses an older server with OKM1803. `minPostgres` is 15, 16, 17, or 18. `requires: { postgres: ">=17" }` is the same floor and is deprecated. Identity columns need Postgres 10. A bare `t.id()` stores `gen_random_uuid()`, which is built in from Postgres 13. An explicit `uuidv7()` needs Postgres 18. A pull request runs Postgres 18 when the diff touches dialects, migrate, or runtime. `bun run verify` runs the suite on this machine. A push to main, the nightly run, and a release cover each supported major. A failure on an older major in this list stays in the run.

Postgres: native. Since 18. Proof passes (`proof:type.uuidv7`).


PGlite runs in the check job. The in-process wire server runs in the check job. postgres.js, node-postgres, and Bun.sql run in the postgres job (`REQUIRE_DOCKER=1`). Bun.sql runs only under Bun. A skip means the adapter did not declare the capability that case needs. node-postgres and Bun.sql do not describe a statement without running it. Bun.sql does not surface RAISE NOTICE and does not abort an in-flight statement. PGlite has no socket to cut, so COMMIT loss (`r2.commit-loss`, `r2.batch-commit-loss`) is `unsupported` in `okm driver test`, with that reason. It is not a silent skip.

postgres.js is tested at 3.4.9 and on 4.x (4.1.1). The peer range is `^3.4.9 || ^4.0.0`. The Postgres job runs the adapter suites on the locked 3.4.9, then the same postgres.js cases again on 4.1.1: `tests/driver-suite.test.ts`, `tests/error-suite.test.ts`, `tests/tx-suite.test.ts`, `tests/postgresjs-write-count-pg.test.ts`, and `tests/acquire-timeout-pg.test.ts`. 4.x keeps `count` on the result class. The adapter copies that field onto the result before it reads the command tag. Neon, node-postgres, and Bun.sql are unchanged.

`timeouts.acquire` defaults to 10 seconds on postgres.js and node-postgres when the key is omitted. node-postgres uses that value as the pool connection timeout on every call, including one waiting on an ordinary statement, and fails the wait as OKM1846. It does not keep a separate 5 second cap. postgres.js fails a queued call that has not been sent, including `find`, `insert`, `count`, and `tx` behind a `tx()` or `reserve()`, as OKM1846. A call behind an ordinary statement is written onto that connection and runs when the statement finishes. postgres.js pipelines ordinary calls onto a connection, so they have no pool wait for `acquire` to bound (use `timeouts.statement` or a call `timeout` to bound a slow call, or a transaction or `reserve` to get the pool wait). Opening a new postgres.js socket uses the driver's `connect_timeout` of 5 seconds, which is not `acquire`. The row below is the reserve case. A `pass` there is that checkout. It does not say a Bun.sql `find`, `insert`, or `count` has an acquire deadline, and it does not say a postgres.js call behind an ordinary statement does. Bun.sql does not bound the pool wait. `acquire` applies to `reserve` and `tx`, and a `find`, `insert`, or `count` waits in the driver queue. Class-form `raw` uses `timeouts.statement` on postgres.js and node-postgres. A call `timeout` overrides `timeouts.statement`. Bun.sql, PGlite, and Neon refuse a positive statement timeout with OKM1120, including that raw call. Neon WebSocket has the same limit: `tx` honours `acquire`, and `find`, `insert`, and `count` wait in the driver queue.

Neon is not a column in this table. postgres.js and node-postgres pointed at Neon endpoints are not columns either, and those results stay unclassified. `okmodel/pg/neon` has its own connect gate. It is checked locally when its credentials are set and skipped in CI. WebSocket mode is interactive. HTTP mode is `transactions: "batch"`: `tx()` is refused. HTTP mode needs a hostname endpoint: the driver rewrites the host, and an IPv4 address becomes an invalid fetch URL (`fetch() URL is invalid`, kind `driver`, not retryable); a refused or unresolvable hostname is `unavailable`. HTTP mode refuses `searchPath` with OKM1120, message `searchPath`. A transaction-mode pooler does not promise session state. COMMIT loss is `unsupported` (`no socket to cut`) because the harness cut is a TCP relay. A result that never arrives is still `outcome_unknown`.

The public type surface (`scripts/api-surface.ts`) and the consumer fixtures (`*.test-d.ts` files the required typecheck includes) compile with TypeScript 7.0.2 (`tsc`, required, `bun run typecheck`). The same files compile with TypeScript 6.0.3 through the dev-only `typescript-editor` package (`bun run ts6:check`). That run is not part of `bun run check`. Nothing in `src/` imports the TypeScript compiler API. TypeScript 7.0 has no stable programmatic API until 7.1.
